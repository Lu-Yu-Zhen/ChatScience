一、板块定位与冲突处理原则

1.1 板块范围

本板块覆盖墨台的本地后端服务层：进程与启动架构、HTTP API 面、数据持久化、AI 上游链路、知识库检索、安全与沙箱、打包分发、验证体系、运维与日志。

1.2 冲突处理原则

凡策划案（第 5 章 后端设计规划）与已实现内容冲突，一律以已实现为准：

冲突项策划案原始表述已实现实际（以此为基准）裁定
后端语言/运行时Node.js 承载 SDK，或 Rust 外壳 + Node 运行时混合方案纯 Node.js（TypeScript）+ Express，随 Electron 内置 Node 20 运行以 Node/TS 为准，Rust 混合方案不采纳

服务模块划分统一网关、Chat 会话服务、Work 运行时、会话与存储、MCP/插件管理、知识库与数据库、计费与权限（7 模块）按域拆分的 Express 路由 + 服务模块（index/routes/qoder/sandbox/store/notes/kb/ai/research/policy/proc/sse，12 模块）以已实现模块拆分为准；策划案的"统一网关"由 Express 应用与鉴权中间件承担

2.2 启动链路【已实现】

环节实现
后端进程由 Electron 主进程 fork，使用 Electron 内置 Node（非系统 Node）
端口候选PORT_CANDIDATES = [8642, 17462, 27511, 38123, 2917, 3218]
端口回退tryListen 递归尝试；EADDRINUSE 自动试下一个（曾因 3218 触发 Windows EACCES 而改造为候选回退）
鉴权每次启动生成 crypto.randomBytes(24).toString('hex') 随机 token
鉴权校验if (auth !== 'Bearer ' + token) → 401
绑定地址仅 127.0.0.1（不对局域网暴露）
运行时信息写入 runtime.json（实际端口 + token），供验证脚本与调试工具读取
单实例锁requestSingleInstanceLock + second-instance 唤起已有窗口
窗口显示兜底ready-to-show 事件可能先于监听触发 → 3 秒兜底 win.show()
启动冒烟打包产物自检时拉起 exe，20 秒内必须写出 runtime.json，随后 taskkill

四、数据持久化

4.1 双文件分区模型【已实现】

文件内容写入方
data/state.json前端快照（会话、项目、模型、UI 偏好，含轨迹剥离规则）主进程（180ms 防抖差量检测）
data/work.json工作数据（智能体定义 / 技能开关 / MCP 服务器 / 沙箱策略 / 模型工具支持 / 运行历史 / 播种标志）后端（分区串行化 store）
data/runtime.json运行时信息（实际端口、token）主进程
data/app.log / server.log应用与后端日志各自进程

设计要点【已实现】：两文件物理隔离，是"双模式分离、故障互不影响"原则在存储层的落地。

4.2 写入机制【已实现】

机制实现
原子写tmp + rename（杜绝半写状态损坏）
差量检测防抖180ms 周期比对状态差异，无差异不写盘
分区串行化 storestore.ts 用 promise chain 保证读-改-写不交错；分区：agents / skills / mcpServers / sandboxPolicy / modelToolSupport / runHistory / seeded
种子增量合并内置智能体按 id 增量合并（每次启动执行，无变化不写盘）——修复了"改名不生效"问题（原 seeded 标志会拦住种子逻辑）
大字段剥离快照同步剥离 data / argsRaw；result / reasoning 截断 2048 字符；SNAP_TRIM_BYTES = 6MB

4.3 遗留问题【部分实现】

问题现象影响
状态落盘延迟180ms 轮询差量，AI 流式输出完成瞬间的最终文本可能延迟一个周期落盘（切换对话会立即触发保存）极端情况下异常退出丢最后一帧
二进制文件不落盘file.data（附件二进制）仅存内存，不落盘（隐私与体积考量）重启后知识库文件需重新上传

待实现：把关键状态改为事件驱动立即落盘（保留防抖作为兜底），或引入 WAL 式增量日志。

4.4 沙箱目录布局【已实现】

data/sandbox/<scope>/
├── work/          ← Agent 可见写区（SDK cwd 与 run_code 进程 cwd 指向此处）
├── out/           ← 产物输出区（Agent 写在这里的产物被回传前端）
├── .hooks/        ← 断网等注入钩子
└── .meta.json     ← 沙箱元数据（scope、创建时间、策略快照等）

scope 语义【已实现】：

  • global — 全局共享沙箱
  • conv-<id> — 会话独立沙箱

工作区模式差异【已实现】：会话绑定本地工作区后，SDK 的 options.cwd 与 run_code 的进程 cwd 同步切换到该工作区；canUseTool 的写入守卫根同步切换；但 _run_*.py 等运行脚本仍写沙箱目录，不污染用户工作区。

4.5 数据库演进方案【待实现】

策划案要求 SQLite 保存元数据与消息。当前 JSON 方案在以下场景会碰到瓶颈：

瓶颈触发条件
全文件读写会话数 > 数千，或单会话消息 > 数万条
无索引查询按时间/关键词检索历史消息
无事务多分区并发写入

演进方案（渐进式，非推倒重来）：

步动作
1抽象存储接口（Store 接口已存在，需扩展为泛型 KV + 集合接口）
2引入 SQLite（better-sqlite3，同步 API 契合当前代码风格）存消息与会话元数据
3保留 JSON 存配置类数据（智能体定义、沙箱策略等低频小数据）——避免过度工程
4提供一次性迁移脚本（读 JSON → 写 SQLite），并在启动时校验
5文件系统继续负责文献/数据/仿真文件/快照（不适合入库的大对象）

6.3 向量检索升级方案【待实现】

策划案要求"文档解析、分块、向量化与检索"，支持文献/实验记录/表格/稿件多类型，按项目与个人/团队空间隔离，给出容量配额。

升级方案（混合检索架构）：

层技术选型理由
分块保留现有 600 字符 / 80 重叠，增加语义分块（按标题层级与段落边界切分）提升检索粒度合理性
词法检索保留 BM25精确术语、公式、专有名词命中可靠
向量检索本地嵌入模型（如 bge-m3 / text-embedding-v3）→ 向量存 SQLite（sqlite-vec 扩展）或独立的轻量向量索引文件本地优先原则，不依赖云端；bge-m3 中文与多语言表现好
混合排序RRF（Reciprocal Rank Fusion） 融合 BM25 与向量两路结果无需调参，鲁棒
重排（可选）交叉编码器重排 top-K精度提升，成本可控
多类型解析复用已实现：PDF（pdf.js 前端 + 后端抽取）、DOCX（mammoth）、XLSX（xlsx）、Markdown/HTML已有基础
空间隔离索引文件按 scope（个人 / 项目 / 团队）分目录与沙箱 scope 模型一致

容量配额【待实现】：配额检查在 /api/kb/index 入队前执行，超限返回明确的配额错误（含当前用量与上限）。

七、安全与沙箱

7.1 纵深防御体系【已实现】

产品采用多层防御 + 诚实的边界声明策略（而非宣称不可绕过的隔离）：

层机制强制力
网络层仅绑定 127.0.0.1（不暴露局域网）强
鉴权层每次启动随机 24 字节 token，Bearer 校验，无 token → 401强
进程隔离contextIsolation: true + sandbox + IPC 白名单强
执行层shell: false + argv 数组（不经 shell 拼接）强（唯一不可绕过层）
路径层assertInside + sanitizeRelPath，防 junction/symlink 逃逸；写入守卫根随工作区切换强
写入守卫canUseTool 对 Write/Edit 强制路径白名单较强
命令拦截canUseTool + policy 静态扫描 16 类危险模式弱（可绕过）
资源限制超时强杀、并发信号量、输出上限、文件大小上限中
断网代理黑洞 + socket monkeypatch + 可选静态导入拦截弱（声明式，不可强制）

8.3 打包期专属故障（重要经验）【已实现】

症状：打包版 Work 模式全部请求失败、选工作区无任何反应。

根因：打包版 server 从未启动。qoder.ts 顶部静态 require('@qodercn-ai/qodercn-agent-sdk')，而 SDK 是纯 ESM 包——系统 Node 24 的 require(esm) 能加载（开发环境正常），但 Electron 33 内置 Node 20 不支持，ERR_REQUIRE_ESM 使 server 模块加载失败。

后果链：所有 /api/* 无人监听 → onPort 不触发 → 界面静态可开但一切后端能力为空。

修复：改为动态 import() 惰性加载（loadSdk()，进程内缓存一次；CJS 中动态 import 在 Electron 内置 Node 20 可用），runWorkTurn / ping / buildScienceServer 改为 await 注入。

叠加陷阱（TypeScript 特有）：tsc 在 CommonJS 输出中会把一切 import()——包括变量指示符——统一改写为 require() 包装，重新引入 ERR_REQUIRE_ESM。

解法（已实测有效）：用 Function 间接层构造真实 import()，编译器无法识别、原样保留：

const dynamicImport = new Function('specifier', 'return import(specifier);');
sdkPromise = dynamicImport(SDK_PACKAGE_SPEC).then(m => m.default || m);

已实测：编译产物中确认无任何对 SDK 的静态 require；SDK 经该通道加载成功（query / tool / createSdkMcpServer / accessToken 均为 function）。
