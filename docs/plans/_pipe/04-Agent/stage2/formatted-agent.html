一、板块定位与冲突处理原则

1.1 板块范围

本板块覆盖 Work 模式的智能体系统——即策划案所称的「墨道」：Agent 运行架构、底座接入、智能体定义体系、模型与权限策略、工具生态、技能系统、上下文隔离、调度与迭代循环、会话机制、工作区模式、可观测性、能力边界。

1.2 已实现 vs 策划案：核心差异总览

这是六个板块中差异最大的一个。策划案描绘的是"墨道七类科研子智能体 + 主智能体调度 + 审辨迭代循环 + fork/检查点"的完整蓝图，而已实现的是一个基于 Qoder Agent SDK 的、以"单智能体 + 技能白名单"为核心的可用 Work 体系，且已通过 69+ 项真实验证。

维度策划案设计已实现实际判定
智能体数量主智能体 + 七类子智能体4 个内置智能体（并列，无主从调度关系）已实现 4 个为准，七类列为待实现
调度架构主智能体动态调度子智能体，子智能体不可互相调度无调度层；用户在界面上手动选择一个智能体执行任务；SDK 内部循环驱动以已实现为准；动态调度列为待实现
上下文隔离子智能体强边界隔离，上下文单向权限，工具经主智能体审核中转无子智能体，故无隔离层；隔离体现在 settingSources: [] + strictMcpConfig + tools 白名单（隔离本机配置污染）已实现的隔离是"与宿主环境隔离"，非"智能体间隔离"
审辨迭代循环评审智能体打分 → 不达标回环重做 → 可配置迭代上限无；Agent 单次运行至 maxTurns 上限即结束待实现
检查点 / forkcheckpoint / rewind / fork 分支无；仅有 SDK 原生 resume（会话恢复）待实现
模型选择每个智能体独立选模型，resolveModel 回调路由模型档位系统：每个智能体可设 5 档（auto/ultimate/performance/efficient/lite），走 SDK 平台模型池已实现档位为准；自定义模型池路由为待实现
工具生态Skill（提示框架）+ 自定义工具（本地函数）+ MCP（外部程序），共 4 组 MCP6 个 in-process 科研 MCP 工具 + 12 个科研技能 + 外部 MCP 服务器接入已实现为准
会话机制session-control + external session-storageSDK 原生 resume（conv.sdkSessionId 持久化）已实现 resume，其余待实现
记忆方式主智能体全局上下文长期保留子智能体产出SDK resume 原生多轮记忆，不手工拼历史以 SDk 原生为准
鉴权—server/qoder.json 中的 PAT（等同账户身份）已实现（需在文档中强调安全）

冲突裁定：本板块全部以已实现为准。策划案的"墨道七类子智能体"作为演进目标架构保留（见第八章），但不得在对外文档中宣称已实现。

2.2 关键设计决策【已实现】

决策内容理由（项目记载）
不自研 Agent 循环Work 模式放弃自研 Agent 循环，改以 Qoder Agent SDK 为底座① Agent 循环、工具调用、MCP、模型路由是通用能力，自研成本高收益低；② 聚焦科研领域价值（技能 + 沙箱 + 科研工具）
隔离三件套（缺一不可）settingSources: [] + strictMcpConfig: true + tools 白名单实测：缺任一项，SDK 会继承本机 qoderclicn 全部配置，泄漏数百个 MCP 工具

技能用 local plugin 目录app/server/skills-plugin 播种 → app/data/skills-plugin支持自定义技能与热更新

3.1 SDK 接入实现【已实现】

项实现

加载方式动态 import() 惰性加载（loadSdk()，进程内缓存一次）
为什么要动态加载SDK 是纯 ESM 包，而 Electron 33 内置 Node 20 不支持 require(esm)；静态 require 会导致 server 完全无法启动（此故障已在打包版实际发生并修复，见后端板块 8.3）

类型策略SDK 类型以官方包为准（自带 dist/index.d.ts）；业务代码不直接 import SDK，统一经 shared/qoder-sdk.ts 重导出
值类型获取type QoderSdkModule = typeof import('@qodercn-ai/qodercn-agent-sdk')（纯类型引用，不触发加载）

14.1 Quick Start（快速开始）

官方地址：https://docs.qoder.com/en/cli/sdk/quick-start

环境要求：TypeScript 需 Node.js 18+；Python 需 Python 3.10+。

安装：

npm install @qoder-ai/qoder-agent-sdk

认证：SDK 通过 PAT（个人访问令牌）认证，适用于脚本、CI 管线、第三方集成。PAT 在 qoder.com/account/integrations 生成——页面关闭后无法再次查看，必须立即复制。

export QODER_PERSONAL_ACCESS_TOKEN="<your-qoder-personal-access-token>"
node agent.mjs

配置认证：TypeScript 用 accessTokenFromEnv()，Python 用 access_token_from_env()。

import { accessTokenFromEnv, query } from '@qoder-ai/qoder-agent-sdk';

const stream = query({
  prompt: 'Hello',
  options: {
    auth: accessTokenFromEnv(),
  },
});

SDK 在启动 qodercli 之前读取该环境变量，并把解析出的访问令牌写入一次性认证载荷。通常不需要通过 env 选项传 PAT；若显式提供了 options.env，SDK 会优先从它读取同名变量。

  安全提示：不得在代码仓库中硬编码 PAT，只能通过环境变量或密钥管理服务注入。

两种输入模式：两个 SDK 均以 query() 为核心入口。当 prompt 为字符串时，一次调用提交一条用户消息，turn 结束后 SDK 关闭会话——适合一次性、无状态任务。若要在同一会话内发送多条消息、并根据响应决定下一步，则向 TypeScript 的 query() 传异步消息流，或用 Python 的 QoderSDKClient 维持长连接。

完整示例：

import { accessTokenFromEnv, query } from '@qoder-ai/qoder-agent-sdk';

for await (const message of query({
  prompt: 'Analyze the codebase, find functions without test coverage, and write unit tests for them.',
  options: {
    auth: accessTokenFromEnv(),
    allowedTools: ['Read', 'Write', 'Edit', 'Glob', 'Grep', 'Bash'],
    permissionMode: 'acceptEdits',  // Auto-approve file edits
  },
})) {
  if (message.type === 'assistant') {
    for (const block of message.message.content) {
      if (block.type === 'text') {
        console.log(block.text);              // AI text response
      } else if (block.type === 'tool_use') {
        console.log(`Tool: ${block.name}`);   // Tool being called
      }
    }
  } else if (message.type === 'result') {
    console.log(`Done: ${message.subtype}`);  // Final result
  }
}

对墨道的落地提示：本项目已按此模式封装 runWorkTurn。示例中的 message.type 分支处理（assistant → 遍历 content 区分 text / tool_use；result → 取 subtype）正是 SSE 桥接层需要复刻的最小集合。permissionMode: 'acceptEdits' 对应本项目权限档位中的相应档位——注意 acceptEdits 只自动接受文件编辑，其他敏感操作仍走权限流程，这与本项目「五档权限 + 四层覆盖链」的设计兼容。

14.2 Agents / Subagents（子智能体注册 — 墨道核心）

官方地址：https://docs.qoder.com/en/cli/sdk/agents

  这是墨道最核心的一篇。 第十三章 E 组「七类科研子智能体 + 主智能体调度」的落地，几乎全部依赖本篇的 options.agents 机制。

内置子智能体：SDK 自带三个 —— general-purpose（通用）、Explore（探索）、Plan（规划）。用 q.supportedAgents() 读取当前可用列表（含插件贡献的 Agent）。

两种注册位置：

字段作用
options.agent指定主会话以哪个 Agent 角色运行（把定义好的 Agent 提升为会话主体）
options.agents注册自定义子智能体供主会话委派（Record<string, AgentDefinition>）

AgentDefinition 全字段：

字段类型必需说明
descriptionstring是用途描述；模型据此判断何时调起该子智能体——写成「什么时候用我」而非「我是什么」
promptstring是该子智能体的系统提示
toolsstring[]否该子智能体的工具白名单
disallowedToolsstring[]否从该子智能体工具集排除的工具
modelstring否模型覆盖；'inherit' 表示继承主会话模型
maxTurnsnumber否该子智能体的最大 API 轮数（防失控）
effort`'low' \'medium' \'high' \'max'`否推理努力级别
permissionModePermissionMode否该子智能体内部工具执行的权限模式
skillsstring[]否预加载到该子智能体上下文的技能名称
mcpServersAgentMcpServerSpec[]否该子智能体可用的 MCP 服务器规格
initialPromptstring否当该子智能体作为主会话 Agent（即 options.agent）时自动提交的首个用户输入

委派机制的关键约束：

约束说明
必须有 Agent 工具主会话要想委派子智能体，其 tools 中必须包含 Agent 工具，否则委派能力不存在
上下文独立子智能体使用独立上下文，不接收父会话的完整历史；父会话传给它的核心信息是 Agent 工具调用的任务提示
工具结果不回灌子智能体的中间工具结果不会直接进入父会话，只有它返回的最终结果进入
不可嵌套子智能体不能衍生自己的子智能体——因此不要在任何子智能体的 tools 中放 Agent
initialPrompt 范围仅对 options.agent 指定的主会话 Agent 生效，普通子智能体不适用

对墨道的落地提示：这是第十三章 D 组（上下文隔离与信息流转）与 E 组（主智能体调度）唯一的实现基础。三点必须写进设计：

  1. 硬性约束——子智能体的 tools 一律不得含 Agent（不可嵌套）；主会话的 tools 必须含 Agent（否则无法委派）。这是 D3「主智能体唯一网关」在 SDK 层面的天然支撑：子智能体直连其他子智能体在能力上就不成立。
  2. description 即路由依据——E 组「七类子智能体」能否被正确分派，取决于每类的 description 是否清晰描写了「何时用我」。建议把它当作路由质量的第一等验收指标，而非文档装饰。
  3. maxTurns 必设——E4「审辨循环」的最大迭代次数、E6「失败兜底」都需要防失控，maxTurns 是第一道闸。
  4. skills 字段（预加载技能）与第十四章「十二个内建科研技能」直接衔接——可用它为每类子智能体预设专属技能集，替代全局技能白名单。详见 14.4。

14.3 MCP Integration（MCP 集成）

官方地址：https://docs.qoder.com/en/cli/sdk/mcp

三种传输方式：

传输配置形态适用场景
'sdk'in-process，createSdkMcpServer() + tool()（Python 用 @tool() + create_sdk_mcp_server()）本项目六个科研 MCP 工具走的就是这条路
'stdio'本地子进程，含 command / args / env外部本地 MCP 服务器
'sse' / 'http'远端 URL + headers远端 MCP 服务器

工具命名规则（贯穿全 SDK）：

mcp__{serverName}__{toolName}

例：服务器名 orders + 工具名 lookup_order → mcp__orders__lookup_order。该全名用于工具白/黑名单、权限回调、hooks 匹配器、子智能体 tools 配置——凡是配置工具名的地方都用全名。

三层工具控制的语义区别（极易混淆，必须分清）：

手段语义后果
tools可见性允许列表不在列表中的工具根本不会提供给模型（模型看不到）
allowedTools预批准工具可见，但匹配即跳过授权提示
disallowedTools拒绝匹配即拒绝；优先级高于 allow

三者可组合。MCP 服务器级还有 allowedMcpServerNames（服务器白名单）与 strictMcpConfig（严格配置校验）。

MCP 工具注解（annotations）：readOnlyHint（只读）、destructiveHint（破坏性）、openWorldHint（开放世界）。这些提示可被上层用于权限决策与 UI 展示。

错误约定：MCP 工具应当返回 isError: true 而不是抛异常——抛异常会破坏协议链路。

OAuth 双路径：

路径机制适用
CLI 驱动mcpAuthenticate 运行时方法TypeScript 侧主动发起
服务器驱动elicit URL + onElicitation 回调Python 侧 on_mcp_oauth_required 入站回调

Elicitation 支持 form 模式（表单填写）与 url 模式（跳转授权）。

运行时方法与缓存破坏原则：MCP 状态、工具列表等在会话内有缓存；增删 MCP 服务器后必须走破坏缓存的路径（如 reloadPlugins 或 MCP 状态刷新），否则模型侧看到的仍是旧的工具集。

对墨道的落地提示：本项目「6 个 in-process 科研 MCP + 外部 MCP + 白名单过滤 + mcp_get/mcp_call 元工具」的结构与官方一致。三点改进建议：

  1. 回归 isError 语义——MCP 元工具调用机制与第十三章 A3「工具错误回传完善」应对齐 isError: true 约定，避免异常穿透。
  2. 补齐工具注解——为 6 个科研 MCP 工具补 readOnlyHint / destructiveHint，使权限层与 UI 能区分「读文献」与「写产物」。
  3. 注意工具名全名规则——白名单与权限规则一律写全名 mcp__<server>__<tool>，这是 A3/A4 审计记录里应落库的键。

14.4 Skills（技能）

官方地址：https://docs.qoder.com/en/cli/sdk/skills

  最容易踩坑的一篇。 官方文档此处存在多处反直觉设计。

第一硬约束 —— SDK 永远加 --disable-builtin-skills：

  SDK 模式下内置技能永不加载，且没有任何 opt-in 开关。

这与 CLI 交互式使用完全不同。含义：如果你希望某些能力通过技能暴露，就必须由你自己通过 options.skills 显式提供——不能依赖内置技能兜底。

options.skills 的三种形态：

取值行为
'all'启用全部已发现的技能
string[]启用指定技能（限定名规则见下）
[]禁用全部技能

插件技能的限定名：插件贡献的技能注册为 plugin:skill 形式，配置时必须用限定名，否则匹配不上。

skillOverrides 的四个档位：

值含义
'on'完整启用
'name-only'仅暴露名称（不注入完整技能内容）
'user-invocable-only'仅允许用户显式调用（模型不可自主调用）
'off'关闭

极易误用的两点：

  1. initializationResult().skills 返回的是发现列表，不是可调用列表。发现 ≠ 可用。UI 要展示「当前会话实际可调用的技能」时，不能直接用这个字段。
  2. string-list 不是安全边界。用 options.skills 传字符串列表不等于限制了技能的权限范围——它只影响加载与否，不构成沙箱。

Agent 级 skills：AgentDefinition.skills 为预加载语义——把指定技能的内容直接注入该子智能体的上下文，而非按需加载。

对墨道的落地提示：本项目「12 内建科研技能 + 自定义技能 CRUD + 启用白名单端到端 + builtin 标记」的设计需要按本篇校正：

  1. --disable-builtin-skills 的后果要写进架构文档——本项目的 12 个技能必须是「自备技能」，且必须在 options.skills 中被显式列出。任何「依赖 SDK 内置技能」的隐含假设都不成立。
  2. builtin 标记的语义需要重新定义——官方语境下「built-in」指永远不加载的那些；本项目的「builtin 标记」实为「随产品分发的自备技能」，建议改称 bundled 以免混淆。
  3. UI 技能列表的数据来源要改——前端若用 initializationResult().skills 渲染「可用技能」，会显示未启用项。应改为：以 options.skills 白名单为源，与发现列表求交集。
  4. 不要把技能白名单当权限边界——第十三章 B 组的权限设计不得依赖 options.skills；真正的边界是 tools / allowedTools / disallowedTools / permissionMode（见 14.3、14.10）。

14.5 Plugins（插件）

官方地址：https://docs.qoder.com/en/cli/sdk/plugins

加载方式：options.plugins 载入本地插件目录；SDK 将其转为 --plugin-dir <path> 启动参数，插件内的 commands、agents、skills、MCP 服务器全部参与本会话的能力发现。

import { query } from '@qoder-ai/qoder-agent-sdk';

const q = query({
  prompt: 'List the commands and agents contributed by the current plugins',
  options: {
    plugins: [
      { type: 'local', path: '/path/to/my-plugin' },
    ],
  },
});

const init = await q.initializationResult();
console.log(init.commands);
console.log(init.agents);
console.log(init.skills);

const plugins = await q.listPlugins();
console.log(plugins);

传多个插件时，--plugin-dir 参数按顺序写入。

插件目录布局：

my-plugin/
  .qoder-plugin/plugin.json    # 声明 name / version / description
  commands/                    # 斜杠命令 → 命名为 <plugin>:<cmd>
  agents/                      # 子智能体 → 命名为 <plugin>:<agent>
  skills/<name>/SKILL.md       # 技能 → 命名为 <plugin>:<skill>
  .mcp.json                    # MCP 服务器

容错行为（重要）：

情况行为
--plugin-dir 路径不存在SDK 模式下静默忽略，会话仍正常初始化
frontmatter 或 .mcp.json 损坏不阻塞 init，只是损坏的命令不出现在 init 响应里

  含义：插件加载失败是静默的。唯一显式诊断手段是 reload 后的 error_count。

会话级覆盖：options.plugins 加载的插件是会话作用域。若本地插件与已安装插件同名，本次会话内本地插件优先——适合插件开发、调试、灰度验证。不触碰用户的全局安装状态。

运行时重载：

const refreshed = await q.reloadPlugins();

console.log(refreshed.commands);
console.log(refreshed.agents);
console.log(refreshed.plugins);
console.log(refreshed.mcpServers);
console.log(refreshed.error_count);   // 本次重载加载失败的插件数

典型场景：插件开发中增删 commands/*.md 后刷新；安装/更新插件后不重启宿主；宿主 UI 需在重载后同步展示资源。

  Python 差异：reload_plugins() 仅在 QoderSDKClient（流式）模式下有意义；一次性 query() 流没有运行时控制通道。

返回结构：

  • listPlugins() 返回 PluginDetails[]，每项含 id / name / source / path / version / scope / enabled / canDisable，以及 resources 汇总（skills / agents / mcpServers / commands / hooks）。
  • reloadPlugins() 返回 commands / agents / plugins / mcpServers / error_count。
  • initializationResult() 没有稳定的插件清单字段——宿主展示插件清单应当用 listPlugins()，不要用 init 结果的 plugins。

options.settings 的插件相关字段：settings.enabledPlugins 控制启用，settings.pluginConfigs 提供插件配置（如 MCP 服务器替换）。

已知限制：

  • 某些 qodercli 版本下，本地插件的 commands/agents/MCP 出现在 init 结果中，但其 skills 可能缺失于发现列表（CLI 侧发现缺陷）。
  • SDK 模式下不存在的 --plugin-dir 被静默忽略，只有 reload 后的 error_count 能诊断。
  • 若 CLI 版本在 reload 时抛出内部 this._plugins 错误，需升级到修复版 qodercli。

对墨道的落地提示：插件是「技能/子智能体/命令」的打包分发单元，与 13.8 的落地路线相关。三点：

  1. 静默失败是主要风险——若未来把七类子智能体做成插件分发，必须自建「加载后校验」步骤（读 listPlugins() 比对期望清单 + 检查 error_count），不能假定加载成功。
  2. <plugin>:<name> 限定名会影响 Skills 白名单——见 14.4，options.skills 中必须写限定名。
  3. init 结果与插件清单要分开取——前端若做「已加载资源」面板，commands/agents/skills 取 init，插件清单取 listPlugins()。

14.6 Authentication（认证）

官方地址：https://docs.qoder.com/en/cli/sdk/authentication

一个会话只能使用一种认证方式：

方式身份适用场景
PAT（个人访问令牌）某个 Qoder 用户脚本、CI、需要该用户权限与数据的宿主应用
Service Account（服务账号）组织级工作负载后端服务、CI、定时任务——不应依赖个人账号
本地 qodercli 登录态当前已登录用户开发者工作站（已登录 Qoder）

PAT 用法：

export QODER_PERSONAL_ACCESS_TOKEN="<your-qoder-personal-access-token>"
import { accessTokenFromEnv, query } from '@qoder-ai/qoder-agent-sdk';

const q = query({
  prompt: 'Summarize the current workspace.',
  options: {
    auth: accessTokenFromEnv(),
  },
});
  • 默认读 QODER_PERSONAL_ACCESS_TOKEN；自定义变量名用 accessTokenFromEnv('MY_QODER_PAT')。
  • options.env 与进程环境同名时，SDK 优先用 options.env 的值。
  • 直接传令牌：accessToken(token)，用于已从密钥管理取到 PAT 的可信后端。

  SDK 不会刷新 PAT。 PAT 失效后必须获取新 PAT 并创建新的 SDK 会话。

服务账号：由 Qoder 组织管理员创建并授权、生成 key。调用方通过 serviceAccount({ serviceAccountKey }) 传入；SDK 与 qodercli 负责获取并刷新短期 Service Account Token（SAT）。

链路：

secret manager
     |
     | Service Account Key
     v
caller reads the key
     |
     | serviceAccount({ serviceAccountKey })
     v
SDK starts qodercli and obtains a short-lived SAT
     |
     `----> authenticate session requests with the SAT

宿主自行换取 SAT（serviceAccount({ fetchServiceAccountToken })）：Service Account Key 留在宿主进程，qodercli 每次需要 SAT 时回调宿主，宿主调用 Token 交换 API 返回新 SAT。

qodercli
     |
     | request a SAT
     v
fetchServiceAccountToken callback in the SDK host
     |
     | call Token exchange with the host-managed Service Account key
     v
Qoder Token exchange
     |
     `----> return the short-lived SAT to qodercli

交换端点：https://openapi.qoder.sh/api/v1/serviceToken/exchange，grant_type: client_credentials，audience: qoder，scope 按需（如 models.read chat.completions），ttl_seconds: 3600。回调需返回 { token, expiresAt? }；取不到有效 SAT 时返回 null 或抛异常，让当前会话显式失败。

认证失败回调：onAuthExpired（TS）/ on_auth_expired（Python），在远端拒绝令牌、令牌过期或 CLI 以认证错误退出时触发，每个 SDK 会话最多触发一次。

Python 认证错误码：

异常code
AuthNotConfiguredErrorauth_not_configured
AuthAccessTokenEnvVarErrorauth_access_token_env_var_not_configured
AuthServiceAccountEnvVarErrorauth_service_account_env_var_not_configured

最佳实践：生产与 CI 用密钥管理提供凭据；不把 PAT / SA key / SAT 写入日志或错误对象；自动化环境显式配置 PAT 或服务账号，不依赖本地登录态；面向用户的应用注册认证过期回调，把失败转成清晰的重新登录提示；凭据更新或轮换后新建会话，不复用已认证失败的会话。

对墨道的落地提示：本项目为桌面应用（单机），当前使用本地登录态最自然。但若规划云端/团队能力（第十三章 F5 云同步、06 板块团队权益），Service Account 路径必须提前设计：

  1. 账号体系缺失是架构级前置——服务账号需要组织管理员创建，这意味着团队能力落地前须先有组织概念（与 06 板块账号体系互为依赖）。
  2. 不要把凭据写进日志——本项目已有审计日志规划（A4），审计记录中禁止包含 PAT / SAT / SA key 原文，只记 tokenSource 一类元信息。
  3. 认证失败要可诊断——注册 onAuthExpired 并把失败转为前端可见的重新登录引导，避免「静默假成功」。

14.7 Model Policy / Model Selection（模型策略）

官方地址：https://docs.qoder.com/en/cli/sdk/model-policy

两种模式，互斥：

模式机制
固定模型（默认）整个会话用一个模型，通过 model 选项指定；省略则用账号默认
动态选择每次 LLM 请求前调用回调返回模型 —— 传 resolveModel 即切换，固定模型设置被忽略

固定模型：

const q = query({
  prompt: 'Analyze this code',
  options: {
    auth: qodercliAuth(),
    model: 'performance',
  },
});

动态选择：

import { qodercliAuth, query, type ModelPolicyProvider } from '@qoder-ai/qoder-agent-sdk';

const resolveModel: ModelPolicyProvider = (context) => {
  return { model: 'performance' };
};

const q = query({
  prompt: 'Analyze this code',
  options: {
    auth: qodercliAuth(),
    resolveModel,
  },
});

按用途路由（官方示例）：

const resolveModel: ModelPolicyProvider = (context) => {
  switch (context.purpose) {
    case 'main':       return { model: 'performance' };
    case 'subagent':   return { model: 'efficient' };
    case 'compact':    return { model: 'lite' };
    default:           return { model: 'auto' };
  }
};

purpose 覆盖：主对话（main）、子智能体（subagent）、上下文压缩（compact）、WebFetch（web_fetch）、图像生成（image_gen）等。

模型参数覆盖：回调可返回 parameters：

const resolveModel: ModelPolicyProvider = (context) => {
  return {
    model: 'ultimate',
    parameters: {
      contextWindow: 200000,
      reasoningEffort: 'high',
    },
  };
};

这些值必须匹配当前模型支持的配置；上下文窗口与思考元数据通过回调入参的 availableModels 暴露（ModelInfo.context_config / ModelInfo.thinking_config）。

超时：回调有默认超时（毫秒），做远程 I/O 时应加大：{ resolveModel, resolveModelTimeoutMs: 800 }。

BYOK（自带 API Key）：回调可返回 BYOK 凭据对象，该请求将被路由到第三方提供方。使用前需确认账号具备 BYOK 权限。

const resolveModel: ModelPolicyProvider = () => ({
  model: {
    provider: 'bailian',
    model: 'qwen3.5-plus-cp',
    api_key: process.env.MY_API_KEY!,
  },
});

可用 provider/model 目录可在运行时获取，供前端渲染选择器与 API Key 输入框。

运行时操作：getAvailableModels() 取当前账号可用模型列表（value / displayName / isEnabled）；固定模型模式下可切换当前模型；可获取 BYOK provider 目录。

错误处理（重要）：

  动态选择模式没有自动回退。 回调超时、抛错、或返回空模型，都会导致本次查询失败。

正确做法是在回调内部兜底：

const resolveModel: ModelPolicyProvider = async (context) => {
  try {
    const policy = await fetchRemotePolicy(context);
    return { model: policy.model };
  } catch {
    return { model: 'auto' };   // fallback, must be non-empty
  }
};

对墨道的落地提示：本篇与第十三章 A7、B1、B2、B3、B4 高度相关，且有一处必须纠正的认知：

14.8 Checkpoint（文件检查点与回滚）

官方地址：https://docs.qoder.com/en/cli/sdk/checkpoint

  注意：这是文件检查点，不是「对话检查点」。它记录的是 session 内被工具修改过的本地文件状态。

开启：

import { query } from '@qoder-ai/qoder-agent-sdk';

const q = query({
  prompt: 'Refactor src/foo.ts into a cleaner implementation',
  options: {
    cwd: '/path/to/project',
    enableFileCheckpointing: true,
    allowedTools: ['Read', 'Edit', 'Write'],
    permissionMode: 'acceptEdits',
  },
});

两个能力必须配合：检查点提供快照，rewindFiles 消费快照。未开启检查点则 rewind 无快照可用。

回滚锚点 = 用户消息的 uuid：

  • 不是 session_id，不是 result 消息的 ID。
  • 仅在产生该检查点的会话上下文内有效；其他会话不能直接用这个 ID 回滚。
  • TypeScript 建议自行生成 uuid（randomUUID()）并通过结构化输入传入，便于 UI 精确映射「回到这条消息之前」。
  • Python 常用做法：从响应流的 UserMessage.uuid 捕获，并配合 extra_args={"replay-user-messages": None}（该参数不是检查点开关，作用是让响应流重放携带 uuid 的 UserMessage，使其可作为回滚锚点）。
import { randomUUID } from 'node:crypto';
import { query } from '@qoder-ai/qoder-agent-sdk';

const userMessageId = randomUUID();

async function* input() {
  yield {
    type: 'user' as const,
    uuid: userMessageId,
    parent_tool_use_id: null,
    message: {
      role: 'user' as const,
      content: [
        {
          type: 'text' as const,
          text: 'Rewrite notes.txt as a two-line summary.',
        },
      ],
    },
  };

  // If your application needs to call rewind later within the same session,
  // keep yielding subsequent user inputs here instead of closing the stream.
}

const q = query({
  prompt: input(),
  options: {
    cwd: '/path/to/project',
    enableFileCheckpointing: true,
    allowedTools: ['Read', 'Write'],
    permissionMode: 'acceptEdits',
  },
});

  Python 提示：需要后续回滚时，必须用 QoderSDKClient 保持同一活跃会话。

Dry Run 预演：执行前先预演，查看是否可回滚、影响哪些文件、增删行数统计。dry run 不修改任何文件，适合确认弹窗与审计日志。

RewindFilesResult 字段：

字段类型说明
canRewindboolean是否可回滚。dry run 模式下失败不抛异常，用该字段表示状态
errorstring?canRewind 为 false 时的诊断文本，可直接展示给用户
filesChangedstring[]?受影响文件的绝对路径列表
insertionsnumber?将被撤销的新增行总数（聚合）
deletionsnumber?将被撤销的删除行总数（聚合）
const preview = await q.rewindFiles(userMessageId, { dryRun: true });

if (!preview.canRewind) {
  // Show the diagnostic message in the UI.
  console.error(preview.error);
  return;
}

// Overall stats across all affected files.
console.log({
  files: preview.filesChanged?.length ?? 0,
  insertions: preview.insertions ?? 0,
  deletions: preview.deletions ?? 0,
});

// Per-file listing — useful for a confirmation dialog.
for (const file of preview.filesChanged ?? []) {
  console.log(`will be reverted: ${file}`);
}

  限制：当前 RewindFilesResult 只返回受影响文件列表与聚合行级统计，不返回逐文件 diff。若需逐文件差异，可在 dry run 后按 filesChanged 读盘与检查点比对，或在执行回滚后用 git/工作区 diff 工具。

执行回滚：省略 dry-run 参数即可。

const result = await q.rewindFiles(userMessageId);
console.log(result.filesChanged);

  回滚只恢复本地文件状态，不回滚对话历史。 模型仍保有前序轮次的上下文；UI 必须自行按 filesChanged 刷新编辑器、文件树或 diff 视图。

失败语义：

调用形式不可回滚时的行为
Dry run（rewindFiles(id, { dryRun: true })）返回 { canRewind: false, error }，便于 UI 展示诊断
执行模式（rewindFiles(id)）TypeScript 中 Promise reject；Python 抛异常。调用方必须捕获并暴露失败

常见失败原因：未开启文件检查点；ID 不是合法的用户消息 UUID；ID 属于其他会话；目标消息没有可回滚的文件快照。

与 settings 的关系：settings 接受 Settings 对象或设置文件路径字符串。

  • 传对象时，SDK 会自动合并 general.fileCheckpointing.enabled = true——无需手写；已有字段保留，已有的 fileCheckpointing 配置其 enabled 会被 SDK 选项覆盖。
  • 传文件路径字符串时，SDK 不重写文件，需自行配置：
{
  "general": {
    "fileCheckpointing": {
      "enabled": true
    }
  }
}

纯回滚场景只设检查点开关、不传 settings 即可。

边界（务必如实声明）：

边界说明
仅本地文件MCP 工具、远端服务、数据库的外部副作用不会被撤销
Bash 写入不算通过 Bash 直接写文件不被视为可回滚的文件快照
目录副作用可能不撤销文件内容可恢复，但目录创建等目录级副作用可能不撤销
绑定会话检查点 ID 绑定会话；恢复同一会话后仍可用，不能跨会话混用

最佳实践：消息发送时保存 user message ID（Python 绑定 UserMessage.uuid 到 UI 消息记录），不要靠反查 UI 文本；回滚前先 dry run 展示影响范围再让用户确认；回滚后按 filesChanged 刷新 UI；失败时把 error 文案直接展示给用户。

对墨道的落地提示：本篇直接支撑第十三章 F2「checkpoint」与 F3「rewind」，且纠正了一个常见预期：

  1. 这是文件回滚，不是对话回滚。F2/F3 在需求描述上若写的是「会话回退到任意历史节点」，与官方能力不一致——官方只回滚文件，对话历史仍保留在前序上下文中。建议把 F2/F3 的措辞改为「文件检查点与文件回滚」，对话回退另作规划（可用 resumeSessionAt + resumeDropsTurn，见 14.15、14.17）。
  2. 用户消息 UUID 必须落库。F2/F3 落地时，前端消息记录必须保存 user message ID。这需要前端配合（与 02 板块联动），不是后端单方面可实现。
  3. UI 需新增 dry run 确认弹窗。canRewind / filesChanged / insertions / deletions 四个字段足以支撑一个清晰的确认对话框，且 dry run 不改文件，风险为零。
  4. 能力边界必须写清楚——Bash 写入不可回滚、MCP 副作用不可回滚。这两条若不声明，用户会误以为「回滚 = 时光倒流」。这应作为第九节「能力边界」的新增条目。
  5. 检查点与外部会话存储互斥（见 14.16）：若未来启用 sessionStore，不得同时开启文件检查点——这是硬性约束，必须在架构决策时二选一。

permissions.ask始终询问规则
permissions.defaultMode默认权限模式
permissions.disableBypassPermissionsMode设为 'disable' 可禁用绕过权限模式
permissions.additionalDirectories额外可访问目录

  若应用会从 settings 读取并应用默认权限模式，建议在执行高危模式前自行做产品级确认。bypassPermissions / yolo 只应出现在明确可信的环境。

MCP 工具策略：把工具级权限策略直接声明在 MCP 服务器配置里，策略随服务器配置走，而非散落在全局工具列表。

mcpServers: {
  repo_tools: {
    type: 'http',
    url: process.env.REPO_TOOLS_MCP_URL!,
    tools: [
      { name: 'search', permission_policy: 'always_allow' },
      { name: 'write_file', permission_policy: 'always_ask' },
      { name: 'delete_file', permission_policy: 'always_deny' },
    ],
  },
}
策略行为
always_allow匹配工具直接允许
always_ask匹配工具进入授权流程
always_deny匹配工具直接拒绝

name 可用 MCP 工具原始名或全名（如 mcp__repo_tools__search）。

对墨道的落地提示：本篇是第十三章 B5「权限授权弹窗通道」与 B6「权限审计」的权威实现依据，直接推翻了一条此前的实现假设：

  1. B5 有了官方通道，但代价是架构变化——官方 canUseTool 本身就是「阻塞式交互通道」：它在服务端暂停并等待宿主返回结果，options.signal 提供取消。但它的运行位置是 SDK 宿主进程，而本项目是「服务端跑 SDK + 前端 UI」的分离结构。因此 B5 的正确落地方式不是自建暂停协议，而是：在 SDK 宿主侧实现 canUseTool，通过既有 SSE 桥接把审批请求推给前端，前端回传结果后再 resolve。这比自研协议更可靠。
  2. options.title / description 可直接做审批 UI 文案——无需自建文案生成。
  3. options.agentID 是 D 组的关键字段——它标识「本次工具调用由哪个子智能体发起」。这正是 D3「主智能体唯一网关」的落地点：在 canUseTool 中按 agentID 应用不同策略，即可在权限层实现网关语义，无需另建调用层。
  4. B6 审计有了标准数据源——除 canUseTool 入参外，还应订阅 SDKPermissionDeniedMessage（type: 'system', subtype: 'permission_denied'），把 decision_reason / decision_reason_type 落库。这补上了 A4 审计中「权限判定依据」这一缺口，且是官方结构而非自造。
  5. 「默认拒绝」是官方行为——未配置回调即不允许任何操作。本项目权限设计应与此对齐，避免出现「未配置即放行」的相反假设。
  6. settings.permissions 可承载本项目的四层覆盖链——allow / deny / ask / defaultMode 与「四层覆盖链」语义相容，建议评估用它替代自建配置结构，降低维护成本。
  7. MCP 工具策略可下沉权限声明——permission_policy 让「写产物」类工具默认 always_ask、「读文献」类默认 always_allow，策略随 MCP 走，比全局列表更内聚。这对 C 组新增的 4 组 MCP 尤其有价值。

Worktree 替换钩子（TypeScript）：WorktreeCreate / WorktreeRemove 是资源替换钩子，不是只读通知。注册 WorktreeCreate 后，回调必须物理创建 worktree 并返回其路径；配对的 WorktreeRemove 回调必须物理删除该 Hook 创建的资源。Qoder CLI 仍负责 session cwd 切换、transcript 迁移、Resume 状态与 Exit 生命周期。

const hooks = {
  WorktreeCreate: [{
    hooks: [async (input) => {
      const worktreePath = await createWorktree(input.name);
      return {
        hookSpecificOutput: {
          hookEventName: 'WorktreeCreate',
          worktreePath,
        },
      };
    }],
  }],
  WorktreeRemove: [{
    hooks: [async (input) => {
      await removeWorktree(input.worktree_path);
      return {};
    }],
  }],
};

createWorktree / removeWorktree 需应用自行实现（执行 Git 或宿主特定的操作），SDK 不提供。

配置：在 options.hooks 中配置。

const result = query({
  prompt: 'perform task',
  options: {
    hooks: {
      PreToolUse: [{ matcher: 'Bash', hooks: [myHook] }],
      PostToolUse: [{ hooks: [auditHook] }],
      SessionEnd: [{ hooks: [logHook] }],

});

matcher 是正则，匹配工具名；省略 matcher 则对所有工具生效：

hooks: {
  PreToolUse: [
    { matcher: 'Bash', hooks: [bashAuditHook] },               // Bash only
    { matcher: 'File.*|Write|Edit', hooks: [fileAuditHook] },  // File operations
    { hooks: [generalLogHook] },                               // All tools (no matcher)

五类典型用法（官方示例）：

① 安全拦截（PreToolUse） —— 拦危险 shell 命令：

const securityHook: HookCallback = async (input) => {
  if (input.hook_event_name !== 'PreToolUse') return {};

  if (input.tool_name === 'Bash') {
    const cmd = String((input.tool_input as any)?.command ?? '');
    if (cmd.includes('rm -rf')) {
      return {
        hookSpecificOutput: {
          hookEventName: 'PreToolUse',
          permissionDecision: 'deny',
          permissionDecisionReason: 'Destructive delete operations are not allowed',
        },
      };
    }
  }

  return {};
};

② 脱敏（PostToolUse） —— 覆盖工具输出，替换 AK / Token 等敏感信息：

const secretRedactHook: HookCallback = async (input) => {
  if (input.hook_event_name !== 'PostToolUse') return {};

  const content = typeof input.tool_response === 'string'
    ? input.tool_response
    : JSON.stringify(input.tool_response);

  const redacted = content
    .replace(/(?:LTAI|AKID)[A-Za-z0-9]{16,}/g, '<REDACTED_AK>')
    .replace(/Bearer\s+[A-Za-z0-9\-._~+/]+=*/g, 'Bearer <REDACTED>');

  if (redacted === content) return {};

  return {
    hookSpecificOutput: {
      hookEventName: 'PostToolUse',
      updatedToolOutput: redacted,
    },
  };
};

③ 截断超长输出（PostToolUse） —— 保留首尾、掐掉中段：

const bashSummarizeHook: HookCallback = async (input) => {
  if (input.hook_event_name !== 'PostToolUse') return {};
  if (input.tool_name !== 'Bash') return {};

  const content = String(input.tool_response ?? '');
  const THRESHOLD = 50 * 1024;
  if (content.length <= THRESHOLD) return {};

  const head = content.slice(0, 8 * 1024);
  const tail = content.slice(-4 * 1024);
  const omitted = content.length - head.length - tail.length;
  return {
    hookSpecificOutput: {
      hookEventName: 'PostToolUse',
      updatedToolOutput: `${head}\n\n[... OMITTED ${omitted} chars ...]\n\n${tail}`,
    },
  };
};

④ 强制继续（Stop） —— 任务未完成时阻止 AI 停止：

const keepGoingHook: HookCallback = async (input) => {
  if (input.hook_event_name !== 'Stop') return {};

  if (!isTaskComplete()) {
    return {
      decision: 'block',
      reason: 'Please continue completing the remaining tasks',
    };
  }
  return {};
};

⑤ 自动批准权限（PermissionRequest）：

const autoApproveRead: HookCallback = async (input) => {
  if (input.hook_event_name !== 'PermissionRequest') return {};

  if (input.tool_name === 'Read') {
    return {
      hookSpecificOutput: {
        hookEventName: 'PermissionRequest',
        decision: { behavior: 'allow' },
      },
    };
  }
  return {};
};

注意事项（重要）：

  • Hook 回调应快速返回，避免阻塞 AI 执行。
  • matcher 匹配 tool_name 字段；正则语法随语言（TS 用 JS 正则，Python 用 re）。
  • continue: false 仅对 PreToolUse、PostToolUse、PostToolUseFailure、UserPromptSubmit、Stop、SubagentStop 生效；观察类事件（如 SessionEnd、CwdChanged）忽略它。
  • 多个 Hook 返回冲突 decision 时，"deny" / "block" 优先（最严格规则胜出）。
  • 多个 Hook 设置 updatedToolOutput 时，最后一个非空值生效。 若需链式变换（先脱敏再截断），应在单个回调内顺序执行。
  • Python SDK 用下划线后缀字段名（continue_）避免与关键字冲突，序列化时自动转换。

对墨道的落地提示：Hooks 是本轮全部 16 篇中对第十三章落地最有直接价值、且成本最低的一篇。它能在不改架构的前提下补上多个此前被列为「待建」的能力：

  1. A4 工具审计 → PreToolUse + PostToolUse。官方示例（审计日志 + 安全拦截合并）可直接复用。这比自建审计层更内聚，且拿到的是官方标准 Hook 输入结构而非自定义事件。
  2. A3 工具错误回传完善 → PostToolUseFailure。该事件提供 error 与 is_interrupt，正是 A3 所需的结构化错误字段。
  3. A2 熔断 / A1 超时 → PreToolUse 拦截 + 计数。在 Hook 内维护失败计数，达到阈值即返回 permissionDecision: 'deny'，即可实现熔断语义，无需改动 MCP 层。
  4. E4 审辨迭代循环 → SubagentStop + Stop。SubagentStop 提供 agent_id / stop_hook_active，Stop 支持 decision: 'block' 强制继续——这是实现「审辨不通过则带反馈重试」的官方机制，比在应用层重建循环更稳。SubagentStart 的 agent_id / agent_type 还可用于 E7「嵌套时间线展示」。
  5. E7 可观测性扩展 → 全套观察类 Hook。SubagentStart / SubagentStop / PreCompact / PostCompact / FileChanged / CwdChanged 提供的正是「多智能体并行嵌套时间线」所需的原始事件，且比现有 SSE 7 类事件更细。建议评估以 Hook 事件为时间线的第二数据源。
  6. 权限审计（B6）→ PermissionDenied。与 14.10 的 SDKPermissionDeniedMessage 互为补充（一个在 Hook 侧、一个在消息流侧）。
  7. 上下文注入 → UserPromptSubmit / SessionStart 的 additionalContext。D4「六步信息流转」中的「取用」环节可借此注入受控上下文，而非全量透传。
  8. 敏感信息脱敏可直接落地——脱敏 Hook 官方示例与本项目「审计日志不得含凭据」（见 14.6）要求完全吻合，建议优先实现。
  9. WorktreeCreate 为并发隔离提供路径——若 E6 需要多个子智能体并行操作同一仓库，可用 worktree 隔离，避免写冲突。注意该 Hook 需自行实现物理创建/删除。

14.14 Cloud Agent（云端智能体，实验性）

官方地址：https://docs.qoder.com/en/cli/sdk/cloud-agent

  状态：实验性 / 不稳定。API 形态可能在次版本间变化，生产路径不得依赖未发布字段。

何时使用：不想管理 qodercli / 捆绑二进制 / 本地运行时；需要跨机器复用的长生命周期 agent（agent 持久化在云端）；希望会话上下文存在云端，使多个进程/主机可恢复。

关键限制（先行声明）：

  本地 CLI 独有能力——MCP 服务器 / settings / hooks / plugins / 本地权限 / 检查点——在 Cloud 运行时全部不支持；传入这些参数会同步抛错。

前置条件：

  • PAT：Cloud 运行时只接受 access-token 认证（accessToken() / accessTokenFromEnv()）；本地登录态或 job token 同步失败。
  • Cloud environment_id：创建会话时必需。
export QODER_PERSONAL_ACCESS_TOKEN="<your-pat>"
export QODER_CLOUD_AGENT_ENVIRONMENT_ID="<your-env-id>"

首次调用：创建 agent + 创建 session：

import { accessTokenFromEnv, query } from '@qoder-ai/qoder-agent-sdk';

const q = query({
  prompt: 'Summarize this repository in one short paragraph.',
  options: {
    auth: accessTokenFromEnv(),
    experimentalCloudAgent: {
      agent: {
        create: {
          name: 'my-cloud-agent',
          model: 'ultimate',
          system: 'You are a concise code assistant.',
          tools: [
            {
              type: 'agent_toolset_20260401',
              enabled_tools: ['read', 'glob', 'grep'],
            },
          ],
        },
      },
      session: {
        create: {
          environment_id: process.env.QODER_CLOUD_AGENT_ENVIRONMENT_ID!,
          title: 'first-cloud-session',
        },
      },
    },
  },
});

运行后从最终 result 消息取 session_id，后续轮次可继续该会话。

内置工具允许列表：tools[].enabled_tools 支持 bash / write / glob / web_fetch / read / edit / grep / web_search。省略 tools 则该 agent 没有任何工具。

挂载文件到会话：文件经 Files API 上传后，用 session.create.resources 挂进会话容器：

session: {
  create: {
    environment_id,
    resources: [
      { type: 'file', file_id: 'file_abc123', path: '/workspace/data.json' },
    ],
  },
}

复用已有 agent：agent: { id: 'agent_xxx' }，跳过 create。

多轮：恢复会话——已有 session_id 后，下一次调用只传 session: { id }，不要再传 agent（会话已绑定 agent，两者同传会同步抛错）。

// Turn 2: continue the same Cloud session

  prompt: 'What is my favorite color?',
  options: {

会话上下文存在云端，脚本可在轮次之间重启或在机器间迁移——只要有 session_id 即可恢复。

Python 高阶用法：QoderSDKClient 提供更高层的 Cloud 会话管理——connect() 创建/解析 Cloud 会话，后续 query() 逐轮复用，无需手动跟踪 session_id。

  Cloud 运行时不支持 client.set_model()、client.reload_plugins()、MCP OAuth 等本地 CLI 控制方法——调用会抛 ValueError。

消费 SSE 事件：Cloud 运行时通过 SSE 推回会话事件流；SDK 把每个事件包装成 cloud agent 事件消息（TS：cloud_agent_event；Python：CloudAgentEventMessage）。

字段说明
eventCloud 事件名（如 user.message / agent.message / session.status_idle）

}

终止态 result 内容：

字段说明

  • agent 与 session 各自把 id / create 视为互斥（TypeScript 由联合类型强制）。
  • 传已有 session.id 时不要同时传 agent。
  • session.create 必须显式含 environment_id。
  • Cloud 运行时不支持本地 CLI 顶层选项：model、agent、MCP 服务器、settings、hooks、plugins、权限模式等会同步抛错。
  • 不支持模型切换、插件重载、MCP OAuth 等运行时控制方法——只能迭代消息与关闭会话。

对墨道的落地提示：第十三章 13.8「其余补充说明」把 cloud-agent 列为「SDK 支持但未接入，需评估是否作为远端算力通道」。本篇给出了评估所需的关键约束：

  1. 与现有能力互斥是核心决策点——Cloud 运行时不支持 MCP / hooks / plugins / settings / 权限 / 检查点。这意味着本项目的六个科研 MCP、十二个技能、权限链、审计 Hook 全部无法在 Cloud 运行时工作。它不是「本地能力的远端版本」，而是另一套能力更窄的运行时。
  2. 定位建议：若未来接入，应定位为「轻量远端任务的旁路通道」（如长时仿真、批量文献处理），而不是 Work 模式的主运行时。主线（墨道）必须留在本地 runtime。
  3. PAT 认证是硬门槛——需要用户在 qoder.com/account/integrations 生成 PAT，与桌面应用的登录态是两套体系。这意味着接入 Cloud 需要额外的产品级认证流程设计（与 14.6、06 板块账号体系联动）。
  4. 实验性状态是排期依据——「API 形态可能在次版本间变化」意味着不宜在此阶段为此投入架构改造。建议保持观望，待官方转正式后再评估。

14.15 Session Control（会话控制）

官方地址：https://docs.qoder.com/en/cli/sdk/session-control

概念：一个 session 对应 CLI 侧一份持久化的对话历史（含上下文、工具调用记录、压缩边界等），由 UUID 标识。init 系统消息包含当前 session_id，它同时是后续 resume/fork 操作的锚点。

创建新会话：

  • 默认：不传任何会话相关字段时，每次创建新会话。
  • 指定 ID：给 sessionId 传值，由调用方决定 UUID（适合宿主自管会话索引）。

恢复会话：

const q = query({
  prompt: 'Continue the previous conversation',
  options: {
    auth: accessTokenFromEnv(),
    resume: 'previous-session-id',
  },
});

不知道 ID 时，用 continue: true（Python：continue_conversation=True）恢复最近修改的会话。

  不要把 resume 与 continue 同时传。

分叉会话：从现有会话派生新会话，保留原有上下文但获得新 session ID，原会话不受影响。

const q = query({
  prompt: 'Based on the prior context, explore a different direction',
  options: {
    auth: accessTokenFromEnv(),
    resume: 'source-session-id',
    forkSession: true,
  },
});

可为分叉后的新会话指定 ID：

options: {
  auth: accessTokenFromEnv(),
  resume: 'source-session-id',
  forkSession: true,
  sessionId: 'my-new-session-id',
}

字段参考：

字段（TS / Python）类型行为
sessionId / session_idstring单独使用：以该 ID 创建新会话；配合 fork 字段：分叉后会话的 ID
resume / resumestring要恢复的会话 ID

获取当前会话 ID：监听 init 系统消息；Python 的 ResultMessage 也带 session_id，两者都可用于记账。

for await (const msg of q) {
  if (msg.type === 'system' && msg.subtype === 'init') {
    console.log('session_id:', msg.session_id);
  }
}

用户数据目录：用户数据目录存放会话历史、资源、日志等用户级 CLI 数据。通过 options.env 设 QODER_CONFIG_DIR 可选择该目录：

const q = query({
  prompt: 'Analyze this repository',
  options: {
    auth: accessTokenFromEnv(),
    env: {
      ...process.env,
      QODER_CONFIG_DIR: '/var/lib/my-agent/qoder',
    },
  },
});

子智能体与会话的关系：子智能体不产生独立的可 resume 会话——它们运行于父会话的上下文内，其消息通过 parent_tool_use_id / parent_agent_id 标识归属（见 14.13）。「子 Agent 独立 session」在本 SDK 中不成立；若需独立可恢复的执行单元，应通过 fork 创建平级会话。

对墨道的落地提示：本篇对第十三章 A5、F1、F5 有直接作用，并纠正了一处需求表述：

  1. 「子 Agent 独立 session」这一表述需修正——SDK 中子智能体没有独立会话，它是父会话内的执行分支，用 parent_tool_use_id 标识。如果需求的原意是「子智能体有独立上下文、能独立恢复」，正确做法是 fork 出平级会话（resume + forkSession），而非给子智能体分配 session。建议据此修订 D1「建立智能体实例概念」的表述。
  2. F1 fork 直接可用——resume + forkSession 即为官方 fork 实现，无需自研。
  3. A5 continue 的边界场景可对齐官方——官方未定义「空会话」「已结束会话」「跨项目 continue」的具体行为，属于 SDK 层未明确定义区域。建议 A5 的实现以「官方行为 + 明确的前置校验」为准，并在文档中如实标注这些边界为「SDK 未定义」。
  4. QODER_CONFIG_DIR 是会话数据落盘位置的关键开关——本项目为桌面应用，若需控制会话数据的存放位置（如跟随用户选择的项目目录、或配合 F4 加密存储），这是官方入口。注意：它影响的是 CLI 侧全部用户级数据，不只是本会话，改它需谨慎评估。
  5. fork 是 F5「多设备会话同步」的备选方案——在没有账号体系的前提下，可以通过导出/导入会话（配合 14.16）实现跨设备迁移，比自建同步协议成本低。但这不解决「同时在线」问题，F5 的完整落地仍依赖账号体系。

14.16 External Session Storage（外部会话存储）

官方地址：https://docs.qoder.com/en/cli/sdk/session-storage

为什么需要：默认 qodercli 把会话历史存在运行机器上。多实例、容器、无服务器部署下，下一个请求可能落到另一台机器读不到原会话。外部会话存储把每个会话镜像到应用自己控制的存储中。

  镜像语义：这是额外的一份副本——qodercli 仍写本地，任何宿主只要有 session ID 就能继续该会话。

适用条件：请求会在服务实例间迁移；本地磁盘临时或不可靠；应用必须控制访问、加密、备份或留存。始终单机运行的应用，本地会话存储通常足够。

工作原理：

first request
  query()
    -> qodercli writes the session locally
    -> the SDK mirrors new session entries to your store

later request, on any host
  query (with resume=session_id)
    -> the SDK loads session history from your store
    -> qodercli continues the session

两条性质：

  • 写入是尽力而为（best-effort）。SDK 后台镜像条目；写入失败会报告，但永不中断正在进行的对话。
  • 条目是不透明的（opaque）。你的存储按原样保存并返回 SDK 定义的 transcript 条目，应用无需理解 qodercli 的本地文件格式。

快速开始：InMemorySessionStore 只在进程内保数据，用于验证接线（查询能存能恢复），无法演示跨主机恢复（进程退出即丢）。要跨主机必须实现真实存储。

import {
  InMemorySessionStore,
  qodercliAuth,
  query,
} from '@qoder-ai/qoder-agent-sdk';

const store = new InMemorySessionStore();
const options = {
  auth: qodercliAuth(),
  cwd: '/path/to/project',
  sessionStore: store,
};

// First query: run and capture the session ID.
let sessionId: string | undefined;
for await (const message of query({
  prompt: 'Remember the number 42.',
  options,
})) {
  if (message.type === 'result') sessionId = message.session_id;
}
if (!sessionId) throw new Error('The first query did not return a session ID.');

// Later query: resume from the store and the model recalls prior context.
for await (const message of query({
  prompt: 'What number did I ask you to remember?',
  options: { ...options, resume: sessionId },
})) {
  if (message.type === 'result') console.log(message.result); // -> "42"
}

  每个宿主必须使用相同的 cwd，SDK 据此识别请求同属一个项目。

在应用中使用存储：给每个需要镜像或恢复的查询传 sessionStore（Python：session_store），然后选择会话识别方式——已知 ID 传 resume；要项目最近会话传 continue: true（需要存储实现会话列举方法）。

实现存储接口：

type SessionKey = {
  projectKey: string; // derived from cwd; identifies the project
  sessionId: string; // the session UUID
  subpath?: string; // set for subagent transcripts, e.g. "subagents/agent-<id>"
};

type SessionStoreEntry = {
  type: string;
  uuid?: string;
  timestamp?: string;
  [key: string]: unknown; // opaque transcript line — store and return unchanged
};

interface SessionStore {
  // Required
  append(key: SessionKey, entries: SessionStoreEntry[]): Promise<void>;
  load(key: SessionKey): Promise<SessionStoreEntry[] | null>;
  // Optional — implement only the features you need
  listSessions?(
    projectKey: string,
  ): Promise<Array<{ sessionId: string; mtime: number }>>;
  delete?(key: SessionKey): Promise<void>;
  listSubkeys?(key: Omit<SessionKey, 'subpath'>): Promise<string[]>;
}

主会话没有 subpath；每个子智能体 transcript 复用相同的 projectKey 与 session ID，只是 subpath 不同。

方法启用的能力
append、load镜像会话并按 ID 恢复 — 必需
listSessions / list_sessions恢复最近会话；列出已存会话
delete从存储中删除会话
listSubkeys / list_subkeys完整恢复与检视子智能体 transcript

实现清单（关键纪律）：

  • 按 key 保持 append 顺序，且 load 返回完整历史。重放依赖顺序。
  • 键之间必须隔离。绝不把一个 key 的条目返回给另一个 key。
  • append 必须幂等。SDK 可能用同一批条目重试失败的写入，重试不得重复历史。
  • 列举会话时 mtime 返回 Unix 毫秒时间戳，且只返回主会话（无 subpath 者）。
  • 级联删除。删除主会话必须同时删除其子智能体 transcript。
  • listSubkeys / list_subkeys 只返回相对标识符——绝不返回绝对路径，绝不包含 . 或 ..。这些会成为存储键，路径穿越段会让 transcript 逃出自己的命名空间（目录穿越风险）。
  • 同一会话的并发写入者在存储层串行化（若多进程可写）。

操作与调优：

项说明
失败处理外部写入失败永不中断进行中的对话。最终重试失败后，SDK 发出镜像错误消息（TS：system/mirror_error；Python：SDKMirrorErrorMessage）。若镜像完整性重要则需监控它——写入失败时对话仍可能完成
读超时外部读取默认等待 60 秒，用 loadTimeoutMs / load_timeout_ms 调整
刷写策略sessionStoreFlush / session_store_flush 默认 batched；设为 eager 会更早镜像，代价是更多存储请求

约束（硬性）：

  • 显式 resume 的会话在存储中缺失时，SDK 仍可回退到同 ID 的本地会话。
  • 存储不能与以下组合使用：文件检查点（见 14.8）、自定义 transport、实验性 Cloud Agent 运行时（TypeScript 中还不能与 persistSession: false 组合）。TypeScript 中存储支持内置 Process 与 Worker transport；Python 需内置 subprocess transport。
  • 存储只承载会话历史。它不承载认证状态、应用配置、文件检查点或留存策略。

官方提供的测试支持：TypeScript SDK 仓库内置 SessionStore 一致性测试；Python 在 qoder_agent_sdk.testing 提供 run_session_store_conformance。连接管理、权限、加密、备份、迁移与留存由应用自行负责。

对墨道的落地提示：本篇对第十三章 F5「云同步」有直接价值，并给出了一组必须在架构决策阶段确认的互斥关系：

  1. 本篇是「多设备会话同步」的官方解法，且无需账号体系即可先做——只要有一个共享存储（自建服务、对象存储、甚至用户网盘），就能实现「同一项目在多台机器继续对话」。这比 F5 原本设想的「账号体系驱动」路径成本低得多，建议作为 F5 的第一阶段（用户级/自选同步盘），账号体系驱动的自动同步作为第二阶段。
  2. 必须二选一：文件检查点 vs 外部会话存储——两者不可组合。这是硬约束，直接影响 F2/F3（checkpoint/rewind）与 F5（云同步）的排期。建议决策顺序：先做 F1–F3（本地文件回滚），待用户对「跨设备继续对话」有明确需求时，再评估是否放弃文件回滚能力换取同步。这个取舍必须写进架构决策记录。
  3. cwd 必须一致是同步的前提——每个宿主的 cwd 相同，SDK 才认作同一项目。这意味着跨设备同步要求项目路径一致，这对普通用户在 Windows/macOS 间同步是个真实障碍。建议在产品层面提供「项目标识」抽象，而非依赖物理路径。
  4. 镜像失败是静默的（仅一条 mirror_error 消息）——若同步是实现的功能，必须监控该消息，否则用户会遇到「明明同步了却丢历史」且无任何提示。这与本项目「无静默假成功」的原则一致，应作为硬性要求。
  5. 子智能体 transcript 的恢复需要 listSubkeys——若 E7 要做嵌套时间线的历史回看（不只是实时），存储必须实现该方法。这应作为 E7 的隐含前置条件提前登记。
  6. listSubkeys 的目录穿越风险需在实现时专项防护——官方明确警告不得返回含 . / .. 的路径。若自建存储，必须做白名单校验。这是一条安全红线。
  7. importSessionToStore 是平滑迁移路径——已用本地存储的用户升级到同步能力时，可批量导入历史会话，无需用户重新对话。

15.0 本章用途与使用方式

  本章是给「让智能体帮你改代码」这件事用的授权契约。

前面的章节回答的是「墨道的智能体系统怎么设计」；本章回答的是另一个问题：当你把本项目的代码交给一个智能体去改时，它被允许做到哪里、绝对不许碰什么、碰到什么必须先回来问你。

使用方式（三步）：

  1. 从 15.3 的语法表里挑出一条指令，把 {范围} 替换成你的实际目录/文件。
  2. 若本次任务需要越界（通常是 B 类），从 15.6 的授权模板里挑一条，一并附上。
  3. 把指令与授权一起发给智能体，然后只按 15.4 的验收方法检查，不靠「看起来没问题」。

三条使用纪律：

纪律说明
一次只授权一个模块不要一次给「02 前端 + 03 后端」两个范围。跨模块任务拆成两轮，各自验收
默认最小授权不确定时，从更严的档位开始（如先 改动 而非 完整）。授权是与任务绑定的，不是与项目绑定的
口头同意不算任何 B 类动作必须体现为明确的书面授权（对话里明确写出即可），不接受「你看着办」这类模糊表述

15.1 三层边界模型

每个模块的边界都拆成三层。「不能做什么」在这三层里含义不同：

层名称含义越界后能否恢复判定方式
L1改动范围哪些文件/目录可以写能（版本控制可还原）看 diff 的文件清单
L2行为约束不改动文件但违反设计契约的行为（解耦、边界、契约稳定性）能，但返工成本高且会连带污染其他模块看 diff 的代码内容与专项核查
L3运行约束影响真实数据、凭据、外部系统的动作可能不可恢复（已发请求、已删数据、已泄露密钥）看审计记录、看是否发生了外部副作用

L3 与 L1/L2 的本质区别：L1/L2 越界可以回滚重来，L3 越界可能已经造成外部影响。因此 L3 的默认档位是全面禁止，且需要独立白名单授权，不能靠「最小授权」类推。

  为什么 L2 要单独存在：最常见的失败不是「改了不该改的文件」，而是「改对了文件、但破坏了模块间的解耦契约」——例如在 UI 模块里直接写了一个 fetch、在对话框模块里直接调了 fs API。这类改动在单个模块内看是合理的，但会让后续重构成本陡增。L2 就是为拦这类问题而设。

15.2 档位定义

每个模块提供一个基准档位；基准档是「不额外说明时」的默认授权，不是上限。

档位L1 可写范围L2 约束L3 权限适用场景
只读无（禁止一切写入）不适用全禁方案设计、代码审查、问题定位
局部指定的单个文件或子目录完全遵守 L2全禁（除 读项目）修一个 bug、改一个函数、调一处样式
改动模块内完全遵守 L2全禁（除 读项目）模块内功能开发与重构
完整模块内 + 授权清单内的跨模块改动完全遵守 L2需逐条授权涉及模块接口变更的联调改造

跨档不在档位里表达——跨模块改动一律走 15.6 的独立授权清单，不通过提升档位来实现。这样「越界」永远是一个显式动作，不会被档位本身吞掉。

15.4 通用禁止项（L3 — 全模块适用，无例外）

以下动作任何模块、任何档位下均禁止，需要时必须在对话中逐条明确授权：

#禁止项避免什么
U1删除或移动项目根目录之外的任何文件误伤用户桌面/文档/下载目录

U3修改或导出凭据类信息：登录态、token、密钥、证书、本机账户配置凭据泄露、账号被登出
U4向外部服务发送请求（未获授权时）：上传代码/数据、调用第三方 API、提交表单数据外流、被外部系统记录
U5修改 .git/ 内部、强推（push --force）、reset --hard、clean -fdx丢失提交历史
U6修改 package.json 的 name/version/依赖版本，或改动构建配置与产物布局破坏构建链、锁文件失配
U7安装新的运行时依赖（含 pip install / npm install <新包>）依赖污染、体积膨胀、供应链风险

  U8 是本项目最特殊的一条。它不是通用安全常识，而是本项目实测出的具体陷阱：隔离三件套缺任一项，SDK 会继承本机 qoderclicn 的全部配置。任何智能体「顺手简化一下配置」的行为都必须被拦下。

需要跨模块或触及 L3 时，从下面挑模板，替换 {} 内的内容，与任务指令一并发出。

15.7 冲突裁决顺序

当两条规则给出不同答案时，按下列顺序裁决（先出现者优先）：

序规则说明
1用户本轮指令但不得覆盖 U1–U14——通用禁止项需要显式授权语句，不能靠「帮我改一下 X」这类泛指令推定
2L3 禁止项（15.4 + 各模块专项）涉及不可逆或外部影响，优先级高于功能需求
3L2 设计契约解耦、契约稳定性、语义一致性
4L1 范围只影响「改哪个文件」，是最外层
5既有代码风格与惯例在没有明确规则时，跟随最近邻实现
6智能体自身判断仅在以上均无规定时使用，且须在回复中说明依据

两个常用推论：

  • 「任务需要我改配置」不构成 U8/U6 的豁免理由。需要时应走模板 B。
  • 若任务与某条 L2 约束冲突（例如「就是要在 UI 里直接请求接口」），正确做法是先回来确认，而不是自行判断哪条更重要。

15.9 与能力边界声明的联动

本项目有一条不可违背的文档纪律（贯穿第九章与第十三章）：「已实现」的判定以源码与验证报告为唯一依据，不得凭文档或意图宣称。

因此智能体完成任务后：

情形要求
任务把某个「待实现」项真正做完并验证通过应同步更新 04 文档中的状态标记与速查总表；并说明改了哪几处
任务完成了部分保持「部分实现」标记，不得因为「主体已完成」就改标为「已实现」
任务只是重构，「行为不变」不得改任何状态标记
任务新增了官方文档提及但项目未验证的能力不得据此宣称已实现（14.20 纪律三）

  这一步为什么必须由人工复核：状态标记直接决定对外承诺。智能体（和写文档的人）都有一种自然的乐观偏差——把「跑通了」当成「已实现」、「已实现」当成「稳定」。本章要求智能体主动报告「有哪些措辞需要回写」，但最终是否回写由人决定。
