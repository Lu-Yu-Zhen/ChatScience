一、板块定位与现状说明

1.1 板块范围

本板块覆盖墨台的商业化计量与订阅体系：双计量模型（积分与 Token）、个人会员四档、团队会员三档、免费用户与每日签到、增值充值包与到期规则、核心功能权益对照，以及从零实现的技术落地方案。

1.2 现状：完全零实现【关键结论】

经对全代码库（排除 node_modules/dist）的系统检索（关键词：积分 / 签到 / 充值 / 会员 / 订阅 / 付费 / credits / points / pricing / billing / quota / tier / plan / membership / subscription / checkin），结论是：订阅付费体系实质上零实现，仅有 1 处孤立字符串残留。

Token 计量无ai.ts 的 chatStream() 只解析 choices[].delta，完全不读取上游 usage 字段；全库检索 prompt_tokens / completion_tokens / usage_metadata 零命中
用量落盘无/api/chat 流式代理只统计字符数与耗时（chars / ttftMs / totalMs），无累计用量

结论：本板块无历史包袱，可全新设计实现。同时也意味着工作量最大——策划案规划的全部权益体系需从零建设。

二、双计量模型：积分与 Token【策划确认】

2.1 核心设计

策划案的双计量设计是本套商业化体系的核心，逻辑清晰且与已实现架构契合度高：

┌──────────────────────────────────────────────────────────────┐
│  算力维度（能不能跑）         │  权限维度（能用哪些功能）      │
├───────────────────────────────┼───────────────────────────────┤
│  Chat 高阶 Token 账户          │  会员档位（个人四档/团队三档）  │
│  Work 积分账户                 │                               │
├───────────────────────────────┼───────────────────────────────┤
│  余额 > 0 即可运行             │  决定高级功能是否解锁          │
└───────────────────────────────┴───────────────────────────────┘

两条铁律：

  1. 算力与权限彻底解耦——积分/Token 余额决定"能不能跑"，会员档位决定"能用哪些高级功能"，二者互不占用。
  2. 免费用户有积分即可体验 Work 基础能力——这是获客设计的关键，绝不能做成"Work 必须付费才能用"。

2.2 计量规则明细

模式计量对象规则
Chat高阶模型 Token会员基础模型无限畅用；高阶模型按 Token 计量
Work积分运行墨道工作流消耗积分
积分计价任务复杂度阶梯单次基础工作流约消耗 1 积分；多智能体串联、仿真解析、批量文献等复杂任务按复杂度上浮
有效期套餐内额度按月发放、当月有效、月底清零不结转
签到所有用户每日签到 +100 积分；签到积分与套餐积分合并使用并遵循相同有效期

2.3 积分阶梯计价模型【待实现 — 需补充设计】

策划案仅给出"基础工作流约 1 积分、复杂任务上浮"的定性描述。需补充可实施的定量模型：

建议：按"任务复杂度因子"计量

单次任务积分消耗 = 基础分 × 复杂度系数
  基础分 = 1
  复杂度系数 = f(智能体数量, 工具调用次数, 迭代轮次, 沙箱执行时长, 仿真解析)
复杂度因子系数贡献说明
基础对话/单工具调用1.0基础工作流 = 1 积分
每增加 1 个智能体+0.5多智能体串联
每 10 次工具调用+0.3工具密集任务
每轮审辨迭代+1.0迭代循环（待实现后启用）
沙箱执行按时长分档：<30s +0.2 / 30—120s +0.5 / >120s +1.0计算密集
仿真解析+2.0 起复杂度最高的任务类型
批量文献按篇数：每 10 篇 +1.0批量任务

计量实现要点【待实现】：

  • 工作量核算的唯一权威源在后端（前端不可信）
  • 计量在任务结束时结算（非开始时预扣），但开始时校验余额（余额不足直接拒绝，不启动任务）
  • 中途中断按已完成步骤计量（避免用户为中断任务全额付费）
  • 每次消耗落审计日志（任务 ID、智能体、工具调用数、时长、积分、时间）

2.4 Token 计量实现方案【待实现 — 关键技术缺口】

这是当前最大的技术缺口：Chat 链路完全不读取上游 usage 字段。

改造方案：

步动作位置
1定义上游 usage 接口（prompt_tokens / completion_tokens / total_tokens）shared/domain.ts
2chatStream() 解析上游 SSE 的 usage 帧（OpenAI 兼容协议在最后一个 chunk 或独立 usage chunk 中返回）server/ai.ts
3若上游不返回 usage，用 本地估算兜底（字符数 / 1.5 ≈ token 数，中文按字符数 × 1.0、英文按字符数 / 4）server/ai.ts
4在完成帧中返回 usage（前端可展示本次消耗）/api/chat 完成帧扩展
5累计写入用户用量账户（按日分桶，参考 usage-daily.json 形态）新增 usage store 分区
6计价：按模型的 input_cost_per_mtok / output_cost_per_mtok 换算（计价表内置，可配置更新）新增 pricing 配置

模型计价表示例（结构参考 AgentsView，金额单位建议用"积分"或"Token 数"而非美元，避免汇率与合规问题）：

模型档输入（每百万 token）输出（每百万 token）
基础模型0（会员无限）0（会员无限）
高阶模型 A计价表配置计价表配置
高阶模型 B计价表配置计价表配置

免费用户 Chat 限额【待实现】：策划案要求"Chat 模式下基础模型按每日限额使用、不享无限、不赠送高阶 Token，对话仅本地保存"。需新增每日限额计数（按天重置），限额值配置化。

5.3 免费用户的"200 初始积分"设计要点【待实现】

这是获客的关键设计——200 积分足以让用户跑通相当数量的基础工作流（按 1 积分/次基础工作流计，约可跑 200 次；即使按复杂任务 5 积分/次，也可跑 40 次）。确保用户能完整体验 Work 的核心价值后才遇到额度墙。

六、增值充值包与到期规则【策划确认】

6.1 两类增值包

包类型作用特点
Work 积分充值包单独补充积分只补充算力，不附带任何会员功能权益
Chat 高阶 Token 充值包单独补充 Token同上

设计精髓：算力与会员权益严格分离——买积分不会解锁功能，买会员不会多给算力。这维护了清晰的心智模型。

6.2 会员到期规则

到期后行为规则
高级功能权限收回
知识库超额容量收回（超额部分只读或限制新增）
Chat 基础模型无限权益同步失效
账户内剩余积分仍然保留，可继续消耗
剩余高阶 Token仍然保留，可继续消耗
身份降级以免费用户身份运行 Work 基础能力

设计理由（策划案原文）：既保证用户已购算力不会因到期作废，又清晰维护了"算力归算力、会员归会员"的计费心智。

实现注意【待实现】：到期后"可继续消耗"意味着余额与权益是两个独立生命周期——数据结构上必须把余额账户与会员订阅分开存储，各自的过期逻辑独立。

十、关键设计要点总结

供实现时反复对照，避免偏离策划案的核心意图：

#要点说明
1算力与权限彻底解耦两条独立的判断链：余额决定"能不能跑"，档位决定"能用什么"。任何"买积分送功能"或"买会员送算力"的设计都违背此原则
2余额与权益分离生命周期到期后权益收回、余额保留可继续消耗。数据结构上必须分离
3免费用户必须有完整 Work 体验200 初始积分 + 1 积分/次的基础工作流 = 用户能完整体验价值后才遇到墙。这是获客设计的核心
4签到积分与套餐积分合并使用、同有效期不做两套有效期（避免用户困惑）
5充值包只补算力、不带权益维护"算力归算力、会员归会员"的心智
6阶梯计价对用户透明任务前给预估、任务后给实际与计算依据。黑箱计价会伤害信任
7门禁统一入口 + 服务端强制前端只展示，后端做判定；失败返回结构化升级引导
8权益分批上线严格执行 3.3 的批次划分，不得为凑齐权益表而宣称待实现能力
9账本 append-only + 启动对账可审计、可追溯、可对账
10视觉克制会员/充值界面必须遵循中性墨色基调，避免商业化页面常见的彩色渐变与大色块
11诚实定位本地计费本地单机计费是"自律性计量"，非安全计费；真实商业化需云端账本

12.2 A 组：前置决策（P0 — 非代码，阻塞项）

这三项不做完，代码写了也要改。

#决策项为什么阻塞需要谁决策
A1法务合规评估预付费、虚拟额度、退款、发票、用户协议——涉及资金与合规，未评估即上线存在法律风险法务 + 产品

12.3 B 组：计量底座（P0 — 最大技术缺口）

核心问题：Chat 链路完全不读上游 usage，因此当前无任何 Token 计量能力。这是整个计费体系的地基。

Token 计量改造 6 步：

#步骤说明
B1上游 usage 解析在 AI 代理层解析各厂商返回的 usage 字段（prompt/completion tokens），注意厂商字段命名差异，需归一化
B2流式场景计量流式响应中 usage 通常在最后一个 chunk 才给出，需在流结束事件中捕获并回传
B3计量落盘每次调用记录：时间、模型、输入/输出 Token、耗时、会话与智能体归属
B4积分换算建立 Token → 积分的换算系数（按模型档位差异化）
B5按日分桶汇总复用 agentsview-report/usage-daily.json 的数据形态（schema v6：按日分桶、按模型计价、双字段 input/output、累计汇总）——注意该文件是第三方工具产物，仅作数据形态参考，不采用其代码
B6扣减与校验调用前校验余额、调用后扣减；扣减失败需补偿（先扣后调 vs 先调后扣的取舍需明确）

积分阶梯计价定量模型（本策划案补充设计）：

要素说明
基础积分每次调用的基础消耗
复杂度因子按任务复杂度（上下文长度、工具调用次数、迭代轮次）加权
模型系数高档模型系数高，低档低
阶梯折减用量越高单价越低（鼓励持续使用）

验收方法：B1–B3 用真实调用核对计量值与厂商账单一致；B6 构造余额不足场景验证拦截与补偿。

12.12 施工顺序建议

A 组（前置决策，阻塞）→ B 组（计量底座）→ C 组（权益门禁）→ D/E/F 组（个人能力分批）→ I 组（前端）→ G 组（支付）
                                                                                        ↘ H 组（团队，依赖账号体系）

关键纪律：

  1. A 组不做完不开工 —— 尤其是法务评估，涉及资金合规不可侥幸。
  2. B 组是整个体系的地基 —— Token 计量不落地，积分、权益、看板、门禁全部无数据可依。
  3. 权益表声明式，不散落 if —— 8 档权益若写进业务代码，后续调整档位将牵动全库。
  4. 数据结构分离 —— 权益生命周期与余额生命周期必须独立，这是到期规则能正确工作的前提。
  5. 不得宣传未上线档位 —— 与 05 板块保持一致。
