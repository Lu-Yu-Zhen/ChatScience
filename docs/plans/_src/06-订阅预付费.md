# 墨台 · 订阅预付费板块实现策划案

## 一、板块定位与现状说明

### 1.1 板块范围

本板块覆盖墨台的**商业化计量与订阅体系**：双计量模型（积分与 Token）、个人会员四档、团队会员三档、免费用户与每日签到、增值充值包与到期规则、核心功能权益对照，以及**从零实现的技术落地方案**。

### 1.2 现状：完全零实现【关键结论】

经对全代码库（排除 `node_modules`/`dist`）的系统检索（关键词：积分 / 签到 / 充值 / 会员 / 订阅 / 付费 / credits / points / pricing / billing / quota / tier / plan / membership / subscription / checkin），**结论是：订阅付费体系实质上零实现，仅有 1 处孤立字符串残留。**

| 维度 | 现状 | 证据 |
|---|---|---|
| 计费 API | **无** | 后端约 40 个端点中**无任何** `/api/billing` / `/credits` / `/subscription` / `/checkin` / `/usage` 端点 |
| 计费数据字段 | **无** | `server/config.json` 仅 6 个字段：`providerId` / `model` / `apiKey` / `note`，**无配额、无 tier、无额度** |
| **Token 计量** | **无** | `ai.ts` 的 `chatStream()` **只解析 `choices[].delta`，完全不读取上游 `usage` 字段**；全库检索 `prompt_tokens` / `completion_tokens` / `usage_metadata` **零命中** |
| 用量落盘 | **无** | `/api/chat` 流式代理**只统计字符数与耗时**（`chars` / `ttftMs` / `totalMs`），无累计用量 |
| 用量看板 | **无** | 检索 `统计` / `用量` / `看板` / `dashboard` / `stats`，命中项均为文件系统 `fs.statSync`、沙箱内存占位、或技能描述文本 |
| 积分账户 | **无** | — |
| 会员档位 | **无** | — |
| 签到 | **无** | — |
| 充值包 | **无** | — |
| 功能门禁（Feature Flag） | **无** | — |
| 唯一残留 | `01/webapp.js:182` 与 `:276` 定义 i18n 键 `upgrade: '升级 Pro'` / `'Upgrade to Pro'` | 该键**仅定义、无任何 `t('upgrade')` 调用点**，即"升级 Pro"按钮**从未渲染**。同期 `app/src/webapp/work/80-i18n.ts` 中**已无此键** |

**结论**：本板块**无历史包袱**，可全新设计实现。同时也意味着**工作量最大**——策划案规划的全部权益体系需从零建设。

### 1.3 澄清两个易误判项

调研中易被误认为"已有计费痕迹"的两个点，经核实**与本板块无关**：

| 项 | 实际用途 | 结论 |
|---|---|---|
| `modelToolSupport`（store 分区） | 记录某模型走 **Function Calling（fc）还是 ReAct** 工具调用协议（注释：`'providerId/modelId' -> 'fc' \| 'react'`） | **与计费无关**。且该字段仅有类型声明与默认值 `{}` 两处，**无任何读写逻辑**，是一个**预留未使用的空字段** |
| `agentsview-report/` 目录 | **第三方工具**（AgentsView v0.42.0，`kenn-io/agentsview`）的导出报告，旁路读取 `~/.workbuddy/projects/` 会话文件统计历史用量 | **非本项目代码**，无任何 import 或读取关系 |

**但 `agentsview-report/` 具有参考价值**：其 `usage-daily.json`（schema v6）提供了成熟的 **Token/成本计量模型样例**：

| 内容 | 说明 |
|---|---|
| `pricing` 计价表 | microdollars 计价，含各模型的 `input_cost_per_mtok` / `output_cost_per_mtok`（如 deepseek-v4.1-flash：输入 $0.15/M tok，输出 $0.6/M tok） |
| `daily[]` | 逐日 `inputTokens` / `outputTokens` / `totalCost` |
| `totals` | 累计（示例：27.18M input / 139K output / $6.29） |
| `stats.json` | 28 天窗口会话统计、工具调用分布、时长与上下文 token 分桶 |
| `sessions.json` | 会话清单（含 health_score / tool_failure / quality_signals） |

**建议**：自建用量看板时**复用这一数据形态**（按日分桶、按模型计价、双字段 input/output、累计汇总），可显著降低设计成本。

### 1.4 状态标记约定

本板块**绝大多数内容为【待实现】**。为便于阅读，本板块采用不同标记方式：

- **【策划确认】** — 策划案原有设计，经审阅后可原样采用
- **【策划修正】** — 策划案设计与已实现架构冲突或不可落地，已调整
- **【待实现】** — 需从零建设

## 二、双计量模型：积分与 Token【策划确认】

### 2.1 核心设计

策划案的双计量设计是本套商业化体系的核心，逻辑清晰且与已实现架构契合度高：

```
┌──────────────────────────────────────────────────────────────┐
│  算力维度（能不能跑）         │  权限维度（能用哪些功能）      │
├───────────────────────────────┼───────────────────────────────┤
│  Chat 高阶 Token 账户          │  会员档位（个人四档/团队三档）  │
│  Work 积分账户                 │                               │
├───────────────────────────────┼───────────────────────────────┤
│  余额 > 0 即可运行             │  决定高级功能是否解锁          │
└───────────────────────────────┴───────────────────────────────┘
```

**两条铁律**：
1. **算力与权限彻底解耦**——积分/Token 余额决定"能不能跑"，会员档位决定"能用哪些高级功能"，**二者互不占用**。
2. **免费用户有积分即可体验 Work 基础能力**——这是获客设计的关键，绝不能做成"Work 必须付费才能用"。

### 2.2 计量规则明细

| 模式 | 计量对象 | 规则 |
|---|---|---|
| **Chat** | 高阶模型 Token | 会员基础模型**无限畅用**；**高阶模型按 Token 计量** |
| **Work** | 积分 | 运行墨道工作流**消耗积分** |
| 积分计价 | 任务复杂度阶梯 | **单次基础工作流约消耗 1 积分**；多智能体串联、仿真解析、批量文献等复杂任务**按复杂度上浮** |
| 有效期 | 套餐内额度 | 按月发放、**当月有效、月底清零不结转** |
| 签到 | 所有用户 | 每日签到 **+100 积分**；签到积分与套餐积分**合并使用并遵循相同有效期** |

### 2.3 积分阶梯计价模型【待实现 — 需补充设计】

策划案仅给出"基础工作流约 1 积分、复杂任务上浮"的定性描述。**需补充可实施的定量模型**：

**建议：按"任务复杂度因子"计量**

```
单次任务积分消耗 = 基础分 × 复杂度系数
  基础分 = 1
  复杂度系数 = f(智能体数量, 工具调用次数, 迭代轮次, 沙箱执行时长, 仿真解析)
```

| 复杂度因子 | 系数贡献 | 说明 |
|---|---|---|
| 基础对话/单工具调用 | 1.0 | 基础工作流 = 1 积分 |
| 每增加 1 个智能体 | +0.5 | 多智能体串联 |
| 每 10 次工具调用 | +0.3 | 工具密集任务 |
| 每轮审辨迭代 | +1.0 | 迭代循环（待实现后启用） |
| 沙箱执行 | 按时长分档：<30s +0.2 / 30—120s +0.5 / >120s +1.0 | 计算密集 |
| 仿真解析 | +2.0 起 | 复杂度最高的任务类型 |
| 批量文献 | 按篇数：每 10 篇 +1.0 | 批量任务 |

**计量实现要点【待实现】**：
- 工作量核算的**唯一权威源在后端**（前端不可信）
- 计量在任务**结束时结算**（非开始时预扣），但**开始时校验余额**（余额不足直接拒绝，不启动任务）
- 中途中断按**已完成步骤**计量（避免用户为中断任务全额付费）
- 每次消耗落审计日志（任务 ID、智能体、工具调用数、时长、积分、时间）

### 2.4 Token 计量实现方案【待实现 — 关键技术缺口】

**这是当前最大的技术缺口**：Chat 链路**完全不读取上游 `usage` 字段**。

**改造方案**：

| 步 | 动作 | 位置 |
|---|---|---|
| 1 | 定义上游 usage 接口（`prompt_tokens` / `completion_tokens` / `total_tokens`） | `shared/domain.ts` |
| 2 | `chatStream()` 解析上游 SSE 的 `usage` 帧（OpenAI 兼容协议在最后一个 chunk 或独立 usage chunk 中返回） | `server/ai.ts` |
| 3 | 若上游不返回 usage，用 **本地估算**兜底（字符数 / 1.5 ≈ token 数，中文按字符数 × 1.0、英文按字符数 / 4） | `server/ai.ts` |
| 4 | 在完成帧中返回 usage（前端可展示本次消耗） | `/api/chat` 完成帧扩展 |
| 5 | 累计写入用户用量账户（按日分桶，参考 `usage-daily.json` 形态） | 新增 usage store 分区 |
| 6 | 计价：按模型的 `input_cost_per_mtok` / `output_cost_per_mtok` 换算（**计价表内置**，可配置更新） | 新增 pricing 配置 |

**模型计价表示例**（结构参考 AgentsView，金额单位建议用"积分"或"Token 数"而非美元，避免汇率与合规问题）：

| 模型档 | 输入（每百万 token） | 输出（每百万 token） |
|---|---|---|
| 基础模型 | 0（会员无限） | 0（会员无限） |
| 高阶模型 A | 计价表配置 | 计价表配置 |
| 高阶模型 B | 计价表配置 | 计价表配置 |

**免费用户 Chat 限额【待实现】**：策划案要求"Chat 模式下基础模型按每日限额使用、不享无限、不赠送高阶 Token，对话仅本地保存"。需新增**每日限额计数**（按天重置），限额值配置化。

## 五、免费用户与每日签到【策划确认】

### 5.1 免费用户能力边界

策划案设计（原样保留）：

| 维度 | 免费用户规则 |
|---|---|
| **Chat 模式** | 基础模型**按每日限额**使用（**不享无限**）；**不赠送高阶 Token**；对话**仅本地保存** |
| **Work 模式** | 注册即赠送 **200 初始积分**；**只要积分余额 > 0 即可运行**墨道工作流 |
| **功能权限（锁定项）** | ① 不能单独设置子智能体模型，**强制跟随主模型**<br>② 仅开放**少量基础 Skill**<br>③ **不支持**手动编排<br>④ **不支持**快照与 fork<br>⑤ 高级 MCP **全部关闭**<br>⑥ 模板最多保存 **2 套**<br>⑦ 知识库仅支持**本地极简文档上传**，**不提供向量库与数据库** |
| **签到** | 所有用户（含免费、个人会员、团队成员）每日签到可领取 **100 积分** |
| **积分用完后** | 可**单独购买积分**继续运行 Work 基础任务；但**高级功能仍需会员**才解锁 |

### 5.2 签到机制设计【待实现 — 需补充防刷设计】

| 项 | 设计 |
|---|---|
| 奖励 | 100 积分/日 |
| 有效期 | 与套餐积分合并使用，遵循相同有效期（当月有效，月底清零） |
| **防刷机制【待补充】** | ① 服务端时间判定（不可信客户端时间）<br>② 按"自然日"边界判定（本地时区）<br>③ 账号绑定（团队版需账号体系）<br>④ 本地单机场景：可用设备指纹 + 本地记录双重校验，但需明确**本地场景防刷能力有限**（诚实声明） |

### 5.3 免费用户的"200 初始积分"设计要点【待实现】

这是获客的关键设计——**200 积分足以让用户跑通相当数量的基础工作流**（按 1 积分/次基础工作流计，约可跑 200 次；即使按复杂任务 5 积分/次，也可跑 40 次）。**确保用户能完整体验 Work 的核心价值后**才遇到额度墙。

## 六、增值充值包与到期规则【策划确认】

### 6.1 两类增值包

| 包类型 | 作用 | 特点 |
|---|---|---|
| **Work 积分充值包** | 单独补充积分 | **只补充算力，不附带任何会员功能权益** |
| **Chat 高阶 Token 充值包** | 单独补充 Token | 同上 |

**设计精髓**：算力与会员权益**严格分离**——买积分不会解锁功能，买会员不会多给算力。这维护了清晰的心智模型。

### 6.2 会员到期规则

| 到期后行为 | 规则 |
|---|---|
| 高级功能权限 | **收回** |
| 知识库超额容量 | **收回**（超额部分只读或限制新增） |
| Chat 基础模型无限权益 | **同步失效** |
| **账户内剩余积分** | **仍然保留，可继续消耗** |
| **剩余高阶 Token** | **仍然保留，可继续消耗** |
| 身份降级 | 以**免费用户身份**运行 Work 基础能力 |

**设计理由（策划案原文）**：既保证用户已购算力不会因到期作废，又清晰维护了"**算力归算力、会员归会员**"的计费心智。

**实现注意【待实现】**：到期后"可继续消耗"意味着余额与权益是**两个独立生命周期**——数据结构上必须把余额账户与会员订阅**分开存储**，各自的过期逻辑独立。

### 8.5 关键风险与应对

| # | 风险 | 说明 | 应对 |
|---|---|---|---|
| 1 | **Token 计数准确性** | 上游可能不返回 usage；不同厂商行为不一 | 上游 usage 优先，本地估算兜底；两路都记录，便于对账；计价以"平台侧为准"并在协议中说明 |
| 2 | **本地单机的计费可信度** | 纯本地应用，用户可改本地文件篡改余额 | **诚实定位**：本地版计费为"自律性计量"，非安全计费；如做真实商业化，**必须引入云端账号与账本**（同时解决团队版的账号缺失） |
| 3 | **账本一致性** | 余额与流水必须一致 | append-only 流水 + 余额由流水推导校验（启动时对账，不一致告警） |
| 4 | **额度与权益分离的生命周期** | 到期后余额保留但权益收回 | 数据结构分离（见 8.1）；到期处理只回收权益字段 |
| 5 | **月度清零的时区与边界** | 月底清零易出边界 bug | 服务端统一按本地自然月边界计算；清零操作写 expire 流水（可追溯） |
| 6 | **签到防刷** | 本地场景无法强防 | 见 5.2；诚实声明局限 |
| 7 | **支付集成** | 需要支付渠道（微信支付/支付宝） | 需评估；可选：
  · 桌面端跳转网页支付
  · 集成微信支付能力（项目内已有微信支付相关技能套件） |
| 8 | **合规** | 虚拟额度/预付卡类业务的合规要求 | ⚠️ **必须法务评估**：预付费、虚拟货币、退款政策、发票、用户协议 |
| 9 | **权益体系与实现不同步** | 策划案多项权益依赖待实现能力 | 严格执行 3.3 的分批上线策略 |
| 10 | **过度复杂的阶梯计价** | 复杂度因子过多会导致用户不理解、易被质疑 | 阶梯计价**对用户透明**：任务启动前显示预估消耗，结束后显示实际消耗与计算依据 |

### 8.6 支付渠道方案【待实现】

| 方案 | 说明 | 评估 |
|---|---|---|
| **A. 网页支付跳转** | 桌面端打开浏览器完成支付，回调桌面端 | 实现简单；需后端回调服务（**与"纯本地"架构冲突**，需引入轻量云端） |

## 十、关键设计要点总结

供实现时反复对照，避免偏离策划案的核心意图：

| # | 要点 | 说明 |
|---|---|---|
| 1 | **算力与权限彻底解耦** | 两条独立的判断链：余额决定"能不能跑"，档位决定"能用什么"。任何"买积分送功能"或"买会员送算力"的设计都违背此原则 |
| 2 | **余额与权益分离生命周期** | 到期后权益收回、**余额保留可继续消耗**。数据结构上必须分离 |
| 3 | **免费用户必须有完整 Work 体验** | 200 初始积分 + 1 积分/次的基础工作流 = 用户能完整体验价值后才遇到墙。这是获客设计的核心 |
| 4 | **签到积分与套餐积分合并使用、同有效期** | 不做两套有效期（避免用户困惑） |
| 5 | **充值包只补算力、不带权益** | 维护"算力归算力、会员归会员"的心智 |
| 6 | **阶梯计价对用户透明** | 任务前给预估、任务后给实际与计算依据。黑箱计价会伤害信任 |
| 7 | **门禁统一入口 + 服务端强制** | 前端只展示，后端做判定；失败返回结构化升级引导 |
| 8 | **权益分批上线** | 严格执行 3.3 的批次划分，**不得为凑齐权益表而宣称待实现能力** |
| 9 | **账本 append-only + 启动对账** | 可审计、可追溯、可对账 |
| 10 | **视觉克制** | 会员/充值界面必须遵循中性墨色基调，**避免商业化页面常见的彩色渐变与大色块** |
| 11 | **诚实定位本地计费** | 本地单机计费是"自律性计量"，非安全计费；真实商业化需云端账本 |

本章把前文的「待实现」项收拢为可施工清单。**本板块实质性零实现，工作量为六个板块中最大**，且存在三个必须在产品层面先行决策的前置项（法务评估、计费定位、账号体系）——**不做完前置决策就动手写代码，返工风险极高**。

### 12.1 修改方向总览

| 组 | 主题 | 性质 | 优先级 |
|---|---|---|---|
| A | 前置决策（非代码） | **产品/法务决策** | **P0（阻塞全部）** |
| B | 计量底座（Token + 积分） | **最大技术缺口** | P0 |
| C | 权益与门禁 | 声明式实现 | P1 |
| D | 个人四档权益 | 分批上线 | P1 |
| E | 免费用户与签到 | 含防刷 | P1 |
| F | 积分商城与充值包 | 含到期规则 | P1 |
| G | 支付渠道 | 建议兑换码冷启动 | P2 |
| H | 团队三档 | **架构级缺失** | P2（依赖账号体系） |

### 12.2 A 组：前置决策（P0 — 非代码，阻塞项）

**这三项不做完，代码写了也要改。**

| # | 决策项 | 为什么阻塞 | 需要谁决策 |
|---|---|---|---|
| A1 | **法务合规评估** | 预付费、虚拟额度、退款、发票、用户协议——涉及资金与合规，未评估即上线存在法律风险 | 法务 + 产品 |
| A2 | **计费定位** | 算力与权限解耦的力度决定积分与权益的边界；定位不清则权益表反复改 | 产品 |
| A3 | **账号体系方案** | 团队版与云端账本的前置条件；纯本地单机应用需先决定是否引入账号 | 产品 + 技术 |

**交付物**：A1 出具法务合规意见（明确可做/不可做及条件）；A2 明确计费定位一句话表述；A3 明确账号体系的技术选型与上线时点。

### 12.3 B 组：计量底座（P0 — 最大技术缺口）

**核心问题**：Chat 链路**完全不读上游 `usage`**，因此当前无任何 Token 计量能力。这是整个计费体系的地基。

**Token 计量改造 6 步**：

| # | 步骤 | 说明 |
|---|---|---|
| B1 | 上游 `usage` 解析 | 在 AI 代理层解析各厂商返回的 `usage` 字段（prompt/completion tokens），**注意厂商字段命名差异**，需归一化 |
| B2 | 流式场景计量 | 流式响应中 `usage` 通常在最后一个 chunk 才给出，需在流结束事件中捕获并回传 |
| B3 | 计量落盘 | 每次调用记录：时间、模型、输入/输出 Token、耗时、会话与智能体归属 |
| B4 | 积分换算 | 建立 Token → 积分的换算系数（按模型档位差异化） |
| B5 | 按日分桶汇总 | **复用 `agentsview-report/usage-daily.json` 的数据形态**（schema v6：按日分桶、按模型计价、双字段 input/output、累计汇总）——注意该文件是第三方工具产物，仅作数据形态参考，不采用其代码 |
| B6 | 扣减与校验 | 调用前校验余额、调用后扣减；扣减失败需补偿（先扣后调 vs 先调后扣的取舍需明确） |

**积分阶梯计价定量模型**（本策划案补充设计）：

| 要素 | 说明 |
|---|---|
| 基础积分 | 每次调用的基础消耗 |
| 复杂度因子 | 按任务复杂度（上下文长度、工具调用次数、迭代轮次）加权 |
| 模型系数 | 高档模型系数高，低档低 |
| 阶梯折减 | 用量越高单价越低（鼓励持续使用） |

**验收方法**：B1–B3 用真实调用核对计量值与厂商账单一致；B6 构造余额不足场景验证拦截与补偿。

### 12.4 C 组：权益与门禁（P1）

| # | 动作 | 说明 |

| C4 | 门禁降级 | 权益校验服务不可用时，按最小权限降级（拒绝访问受控功能），**不得放行** |
