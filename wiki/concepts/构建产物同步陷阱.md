# 构建产物同步陷阱

**一句话**：`01/` 目录和 `app/renderer/index.html` 都是编译产物——改 UI/前端代码的正确位置是 `app/src/webapp/`，改产物会被下次构建无声覆盖。

## 事实链

| 路径 | 性质 | 可否手改 |
|---|---|---|
| `app/src/webapp/`（webapp.ts + work/*.ts） | **源码，唯一正确修改位置** | ✅ |
| `01/`（主页面.html + webapp.js + work/*.js） | 源码的**同步工作副本**（tsc 编译产物） | ❌ 改源后自动同步 |
| `app/renderer/index.html`（≈500KB） | `build.js` 三段拼接**构建产物** | ❌ 勿直接改 |
| `app/dist/ChatScience-win32-x64/` | `pack.js` 打包产物 | ❌ |

- 构建链：tsc（`tsconfig.webapp.json`，`noEmitOnError` 保证类型不过不出产物）→ `node app/build.js`（`SRC=01/主页面.html` → `OUT=app/renderer/index.html`，三段注入，见 [前端架构](../entities/前端架构.md)）→ 仅改 CSS 时无需 tsc，直接 build.js。
- 07 策划案明确："改造范围仅 `app/src/webapp/`（`01/` 为同步副本，改源后走 build.ts 三段注入构建）"。

## 为什么容易踩

1. **搜索命中产物**：全局搜索代码时 `01/` 与 `renderer/index.html` 里的同名内容先跳出来，误以为那是源。识别法：`.ts` 是源，`.js`/拼接 HTML 是产物；`01/` 内容永远与 `app/src/webapp/` 编译结果一致。
2. **改了没生效 / 生效一次又消失**：直接改 `01/` 或 index.html，运行能看到效果，但任何一次 `build:ts`/`pack` 就全部冲掉。
3. **字符数 ≠ 字节数**：build.js 打印的是**字符数**，文件大小是 UTF-8 **字节数**，含中文产物字节数明显更大——曾据此误判"产物变小"。
4. **旧进程假象**：主进程有单实例锁 + 关窗驻托盘，重打包前必须先杀旧 `ChatScience.exe`，否则新实例静默退出、看到的仍是旧代码。杀进程只按名过滤，**绝不可全杀 electron.exe**（宿主工具自身也是 Electron）。
5. **并发编辑**：用户可能同步改源码并自行 build:ts——改动前先重读文件，绝不回退用户改动。
6. **样式在 JS 内联**：对话消息样式（`.ai-text` 等）全在 webapp.ts 内联 cssText，**改主页面.html 无效**，要改 `app/src/webapp/webapp.ts`。

## 正确工作流

改 `app/src/webapp/` 源码 → 重新打包并启动应用验证（用户硬约定：`PACK_SKIP_HEAVY=1 node app/pack.js` → explorer 代理启动打包版 exe → 轮询进程/端口/boot-marker 确认）。纯重构验收标准是"行为完全不变"，不得借机改功能。
