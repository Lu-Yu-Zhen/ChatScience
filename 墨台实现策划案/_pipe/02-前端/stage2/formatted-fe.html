墨台 · 前端板块实现策划案

一、板块定位与冲突处理原则

1.1 板块范围

本板块覆盖墨台桌面客户端的前端工程层：技术栈与架构、模块划分、构建链路、状态管理、前后端通信、事件驱动、i18n、性能优化、工程化与测试。

与 UI 板块的分界：UI 板块定义"长什么样"，本板块定义"怎么搭、怎么跑、怎么扩"。

1.2 冲突处理原则

凡策划案（第 4 章 前端设计规划）与已实现内容冲突，一律以已实现为准。据此裁定的主要冲突如下：

冲突项策划案原始表述已实现实际（以此为基准）裁定
前端框架React + TypeScript，构建工具 Vite原生 JavaScript 单文件前端，无框架、无构建器（除自研拼接脚本）以原生实现为准，React 迁移列为长期演进项
桌面外壳推荐 Tauri 为长期方向，首期可用 ElectronElectron 33（已完整落地，含打包链路）以 Electron 为准，Tauri 迁出本期范围

前端模块化组件按模式与功能域分模块懒加载13 个模块构建期拼接为单一 IIFE，共享同一闭包作用域；主脚本 38 万字符内联于 HTML以拼接模型为准，ESM 化列为二期

2.2 关键设计决策（已实现，需在文档中固化）

决策理由（源码/报告记载）
不迁移 React/Vue现有单文件前端是"经多轮验收打磨的成熟 UI 资产，重写风险远大于收益"。Electron 直接承载该前端 + Node/Express 后端即满足"独立前端界面与后端服务"的核心目标
无前端构建器（除自研拼接）作为纯本地桌面应用，前端资源不从网络分发，构建期拼接到单文件反而消除了资源加载与路径解析的复杂度
测试脚本用 JS 而非 TS验证脚本本身就是行为安全网，同步改写会削弱验证能力
状态同步 180ms 防抖 + 原子写交互类操作走 IPC 即时（<10ms）；持久化用 180ms 差量检测 + tmp+rename 原子写，兼顾实时性与磁盘写入成本

四、构建链路

4.1 三脚本拼接模型【已实现】

构建脚本 build.ts 按严格顺序执行三个内联步骤（顺序不可调换）：

步脚本作用
①主脚本（webapp.ts 编译产物 webapp.js）注入 Chat 模式 + 通用 UI
②Work bundle（13 个 work/*.js）拼接为单一 IIFE 注入
③桌面桥接脚本CS_BACKEND 注入 + 状态回灌 + 差量同步

4.2 拼接实现细节【已实现】

机制实现
文件收集listWorkFiles() 按正则 /^\d\d-[A-Za-z0-9_-]+\.js$/ 过滤后 .sort() 字典序（不依赖文件系统返回顺序）
顺序断言断言首个必须 00-core.js、末个必须 90-boot.js，违反即抛错
语法门禁逐文件起 node --check 子进程校验语法，任一失败立即中止构建
IIFE 包裹全部模块拼进 (function(){\n'use strict';\n + parts.join + \n})();
注入标记<!--CS_MAIN_SCRIPT-->、<!--CS_WORK_MODULES-->（含其后注释）、<!--CS_DESKTOP_BRIDGE-->
函数式替换（关键）注入必须用函数式 replace，否则源中 KaTeX 的 $$ 定界符会被当作特殊替换模式改写（$& / $1 语义）

4.3 产物断言【已实现】

构建完成后执行 5 项断言，任一失败 process.exit(1) 阻止启动：

  1. 产物中无残留 CS_WORK_MODULES / CS_MAIN_SCRIPT 字面量
  2. 恰含 1 个 CS_DESKTOP_BRIDGE
  3. 主脚本体量 < 桥接
  4. work bundle 体量 < 桥接，且 > 主脚本（以 id="modeSwitcher" 定位）
  5. <title>ChatScience</title> 未被改动

实测产物一致性：新旧 build.js 产物 SHA256 完全一致（510,972 bytes）——迁移未改变任何渲染层行为。

4.4 bridge 脚本职责【已实现】

职责实现
后端桥接注入暴露 CS_BACKEND（IPC 模式 / HTTP 模式双通道）
状态恢复启动时回灌 localStorage（双实例共享持久化状态）
默认模型bailian / qwen3.8-flash
差量快照同步180ms 防抖；SNAP_TRIM_BYTES = 6MB；剥离 data / argsRaw 大字段；result / reasoning 截断 2048 字符
桌面模式降级纯浏览器模式自动隐藏标题栏与占位、回退本地演示模式

五、状态管理与前后端通信

5.1 状态分区【部分实现】

策划案要求前端全局状态分为UI 状态区、会话状态区、运行态状态区，以避免运行态事件高频更新影响输入与对话流畅度。

分区现状
UI 状态区部分实现（分散于主脚本与 Work 模块的局部状态，未显式分区）
会话状态区已实现（conversations / projects / models，随快照落盘）
运行态状态区部分实现（_calls 轨迹数组、WorkState 管理页状态；未与 UI 状态隔离为独立区）

待实现方案：显式三区划分，运行态事件只写入运行态区并仅重绘受影响的消息卡片（已有 traceRefresh 的 rAF 节流实践为基础）。

5.2 通信双通道【已实现】

通道用途实现
IPC桌面交互类操作（通知、置顶、窗口控制、选工作区对话框）即时响应（<10ms），preload 暴露白名单方法：winMinimize / winMaximizeToggle / winClose / onMaxChanged 等
本地 HTTP数据类操（状态快照、聊天、全部 /api/work/*）127.0.0.1 + 随机 24 字节 token Bearer 鉴权；端口候选回退

鉴权与安全【已实现】：

  • 仅绑定回环地址（127.0.0.1）
  • 无 token 请求返回 401
  • contextIsolation 开启 + sandbox + IPC 白名单
  • 环回不启用 TLS（决策理由：环回 TLS 无实际威胁模型支撑，属过度设计；以纵深防御替代）

六、模块化与 TypeScript 化（二期）【待实现】

6.1 现状问题

问题证据
前端未模块化13 个 work 模块共享同一闭包作用域，主脚本 38 万字符内联于 HTML
逐行类型检查关闭13 个 .js 模块首行均为 // @ts-nocheck
单文件规模失控主脚本（webapp）30 万字符 / 5,717 行
无编译期 i18n 校验现由 build.js 运行时做键集合 diff，非编译期

官方记载的结论：转 TS 需要先把前端模块化（ESM + 打包器），"硬转只会引入行为风险"，已明确列为后续迭代。

6.2 模块化改造方案

目标：把 01/work/*.js 拆为真正的 ESM 模块，主脚本抽取为 TS 源，经打包器产出 bundle，替换现有"字符串内联"模型。

改造步骤：

步动作风险控制
1建立打包器（esbuild，零配置、极快、无运行时依赖）与原 build.js 产物做 SHA256 对比，确保逐字节一致后再切换
2把 13 个模块改为显式 import / export，消除跨模块的隐式闭包依赖逐个模块改造，每改一个跑一次回归
3主脚本切分为多文件（按域：chat / layout / settings / kb / reader / msgNav / state / i18n）以现有函数边界为切分线，不改逻辑
4移除全部 // @ts-nocheck，改为真类型（复用 shared/domain.ts 类型面）按域渐进，允许局部 any 收口
5i18n 词条改 TS 常量，获得编译期键校验（替代运行时 diff）中英键一一对应约束由类型强制
6保留双通道构建：ESM 开发模式（便于调试） + bundle 生产模式（保持单文件分发）—

收益：编译期类型与 i18n 校验、可控的文件规模、可测试性、可 tree-shaking、支持懒加载。

6.3 组件懒加载【待实现】

策划案要求"组件按模式与功能域分模块懒加载，首屏只加载当前模式所需代码"。

方案：以域为切分单元（Chat 域 / Work 管理域 / 阅读器域 / 笔记本域 / 沙箱域），非当前模式与非常用页面用动态 import() 按需加载。

注意：桌面应用资源本地读取，懒加载的收益主要在启动解析时间与内存占用，需实测确认（当前 bundle 536KB，解析成本可控）。建议优先级低于模块化本身。

13.8 施工顺序建议

A 组（脚本切分）→ B 组（状态三区）→ C 组（构建升级）→ D 组（动态清单）→ E 组（工程化）
      ↓                                                                         ↓
  每抽一域即跑全量验证脚本                                            纳入 CI 后转为自动门禁

关键纪律：A、C 两组属纯重构，验收标准是「行为完全不变」——不得借重构之机顺手改功能，否则问题无法归因。
