# 墨台 · Agent 系统设计实现策划案

## 一、板块定位与冲突处理原则

### 1.1 板块范围

本板块覆盖 Work 模式的智能体系统——即策划案所称的**「墨道」**：Agent 运行架构、底座接入、智能体定义体系、模型与权限策略、工具生态、技能系统、上下文隔离、调度与迭代循环、会话机制、工作区模式、可观测性、能力边界。

### 1.2 已实现 vs 策划案：核心差异总览

这是六个板块中**差异最大**的一个。策划案描绘的是"墨道七类科研子智能体 + 主智能体调度 + 审辨迭代循环 + fork/检查点"的完整蓝图，而已实现的是一个**基于 Qoder Agent SDK 的、以"单智能体 + 技能白名单"为核心的可用 Work 体系**，且已通过 69+ 项真实验证。

| 维度 | 策划案设计 | 已实现实际 | 判定 |
|---|---|---|---|
| 智能体数量 | 主智能体 + **七类子智能体** | **4 个内置智能体**（并列，无主从调度关系） | 已实现 4 个为准，七类列为待实现 |
| 调度架构 | 主智能体**动态调度**子智能体，子智能体不可互相调度 | **无调度层**；用户在界面上**手动选择**一个智能体执行任务；SDK 内部循环驱动 | 以已实现为准；动态调度列为待实现 |
| 上下文隔离 | 子智能体强边界隔离，上下文单向权限，工具经主智能体审核中转 | **无子智能体，故无隔离层**；隔离体现在 `settingSources: []` + `strictMcpConfig` + `tools` 白名单（隔离本机配置污染） | 已实现的隔离是"与宿主环境隔离"，非"智能体间隔离" |
| 审辨迭代循环 | 评审智能体打分 → 不达标回环重做 → 可配置迭代上限 | **无**；Agent 单次运行至 `maxTurns` 上限即结束 | 待实现 |
| 检查点 / fork | checkpoint / rewind / fork 分支 | **无**；仅有 SDK 原生 `resume`（会话恢复） | 待实现 |
| 模型选择 | 每个智能体独立选模型，`resolveModel` 回调路由 | **模型档位系统**：每个智能体可设 5 档（auto/ultimate/performance/efficient/lite），走 SDK 平台模型池 | 已实现档位为准；自定义模型池路由为待实现 |
| 工具生态 | Skill（提示框架）+ 自定义工具（本地函数）+ MCP（外部程序），共 4 组 MCP | **6 个 in-process 科研 MCP 工具** + **12 个科研技能** + 外部 MCP 服务器接入 | 已实现为准 |
| 会话机制 | session-control + external session-storage | SDK 原生 `resume`（`conv.sdkSessionId` 持久化） | 已实现 resume，其余待实现 |
| 记忆方式 | 主智能体全局上下文长期保留子智能体产出 | SDK `resume` 原生多轮记忆，**不手工拼历史** | 以 SDk 原生为准 |
| 鉴权 | — | `server/qoder.json` 中的 PAT（**等同账户身份**） | 已实现（需在文档中强调安全） |

**冲突裁定**：本板块全部以已实现为准。策划案的"墨道七类子智能体"作为**演进目标架构**保留（见第八章），但**不得**在对外文档中宣称已实现。

### 1.3 状态标记约定

**【已实现】** / **【部分实现】** / **【待实现】**

## 二、运行架构

### 2.1 已实现架构全景【已实现】

```
┌────────────────────────────────────────────────────────────────┐
│  Work 模式入口（前端）                                          │
│  · 用户选择：工作区 / 权限模式 / 执行智能体 / 模型档位            │
│  · 发消息 → POST /api/work/agent/run（SSE）                     │
└──────────────────────────┬─────────────────────────────────────┘
                           │
┌──────────────────────────▼─────────────────────────────────────┐
│  runWorkTurn（qoder.ts）— Work 运行时封装层                     │
│  ① 解析请求：agentId / permissionMode / workspaceRoot / skills   │
│  ② 计算工具可见集（白名单过滤，隔离本机配置）                     │
│  ③ 计算技能白名单（skills 数组）                                 │
│  ④ 权限模式覆盖链：请求 > 智能体定义 > 全局配置 > default        │
│  ⑤ 装配 SDK options → 调 query()                                │
│  ⑥ 桥接 SDK 消息 → 发射 SSE 事件                                │
└──────────────────────────┬─────────────────────────────────────┘
                           │
┌──────────────────────────▼─────────────────────────────────────┐
│  Qoder Agent SDK（@qodercn-ai/qodercn-agent-sdk@1.0.34）        │
│  内置 qoderclicn 1.1.44 运行时                                   │
│  Agent 循环 / 工具调用 / MCP / 模型路由 / 会话 resume / 事件流    │
│  ⚠ 纯 ESM 包 → 动态 import() 惰性加载（loadSdk，Function 间接层） │
└──────────────────────────┬─────────────────────────────────────┘
                           │
┌──────────────────────────▼─────────────────────────────────────┐
│  墨道扩展（本产品自研部分）                                       │
│  · 隔离三件套：settingSources:[] + strictMcpConfig + tools 白名单 │
│  · 沙箱边界层：cwd 隔离 + canUseTool 高危拦截 + run_code 隔离执行 │
│  · 科研扩展：buildScienceServer 注入 6 个 in-process MCP 工具     │
│  · 技能插件：local plugin 目录（12 个内建科研技能）               │
│  · 管理页：智能体 / 技能与插件 / 连接器 / 沙箱 / 笔记本 / 运行     │
└────────────────────────────────────────────────────────────────┘
```

**策划案对照**：策划案的"四层分层架构"（桌面前端层 → 墨道外挂层 → SDK 底座层 → 模型与资源层）**与已实现架构结构一致**。差异在于"墨道外挂层"的实际内容比策划案简化（无七子智能体、无审辨循环、无主智能体网关）。

### 2.2 关键设计决策【已实现】

| 决策 | 内容 | 理由（项目记载） |
|---|---|---|
| **不自研 Agent 循环** | Work 模式放弃自研 Agent 循环，改以 Qoder Agent SDK 为底座 | ① Agent 循环、工具调用、MCP、模型路由是通用能力，自研成本高收益低；② 聚焦科研领域价值（技能 + 沙箱 + 科研工具）|
| **隔离三件套（缺一不可）** | `settingSources: []` + `strictMcpConfig: true` + `tools` 白名单 | **实测：缺任一项，SDK 会继承本机 qoderclicn 全部配置，泄漏数百个 MCP 工具** |
| **cwd 指向沙箱** | `options.cwd` 指向 `app/data/sandbox/<scope>/work` | 文件操作天然被限制在沙箱内；`global` 共享 / `conv-<id>` 会话独立 |
| **多轮走 SDK 原生 resume** | 用 `conv.sdkSessionId`，**不手工拼历史** | 避免上下文重复、成本浪费与不一致 |
| **技能用 local plugin 目录** | `app/server/skills-plugin` 播种 → `app/data/skills-plugin` | 支持自定义技能与热更新 |
| **模型/权限两套独立体系** | SDK 五档模型档位（Work）与 Chat 的厂商模型体系**互相独立** | 两条链路各自正常 |
| **PAT 鉴权** | `server/qoder.json` 中的 PAT | **等同账户身份，需严格保管** |

## 三、底座接入

### 3.1 SDK 接入实现【已实现】

| 项 | 实现 |
|---|---|
| 包 | `@qodercn-ai/qodercn-agent-sdk@1.0.34` |
| 内置运行时 | qoderclicn **1.1.44** |
| 加载方式 | **动态 `import()` 惰性加载**（`loadSdk()`，进程内缓存一次） |
| 为什么要动态加载 | SDK 是**纯 ESM 包**，而 Electron 33 内置 Node 20 不支持 `require(esm)`；静态 require 会导致 **server 完全无法启动**（此故障已在打包版实际发生并修复，见后端板块 8.3） |
| tsc 陷阱与解法 | tsc 会把一切 `import()`（含变量指示符）改写为 `require()` 包装 → 用 **Function 间接层**构造真实 `import()`，编译器无法识别 |
| 类型策略 | SDK 类型以官方包为准（自带 `dist/index.d.ts`）；业务代码**不直接 import SDK**，统一经 `shared/qoder-sdk.ts` 重导出 |
| 值类型获取 | `type QoderSdkModule = typeof import('@qodercn-ai/qodercn-agent-sdk')`（纯类型引用，不触发加载） |

### 4.4 待实现：七类科研子智能体【待实现】

策划案设计的七类子智能体，需按以下方式落地（保持与已实现架构兼容）。

**关键设计约束**：已实现架构是"用户直接选一个智能体执行"。七类子智能体落地时，有两种可选路径：

| 路径 | 方案 | 评估 |
|---|---|---|
| **路径 A：技能化（推荐，渐进）** | 把七类子智能体实现为**专属技能包 + 专属工具集**，由主智能体按任务动态加载 | 与已实现的 skill 白名单机制天然兼容；成本低；可分阶段落地 |
| **路径 B：多智能体注册（完整）** | 用 `options.agents` 注册主智能体 + 七个子智能体，实现主智能体调度 | 需 SDK 支持智能体间调用与上下文隔离；需先做技术探针（见第十章风险） |

**路径 A 的七类映射（建议）**：

| 子智能体 | 复用已实现资产 | 需新增 |
|---|---|---|
| **文献调研** | 技能：`lit-review` / `paper-deep-read` / `paper-repro-plan`<br>工具：`arxiv_search` / `fetch_url` / `kb_search` | 布尔检索式生成技能、Zotero/EndNote MCP、本地 PDF 增强解析（公式/图表/参考文献块）、GB/T 7714 / APA 引用生成 |
| **实验设计** | 技能：`ablation-design` / `experiment-log` | 假设生成、因果变量梳理（混杂/中介/调节）、统计效能计算 MCP、伦理自检 |
| **实验仿真** | 技能：`mindspore-repro`（最接近） | 仿真假设校验、边界与网格推荐、不收敛诊断；COMSOL/LAMMPS/GROMACS MCP、仿真文件解析、集群提交 |
| **数据分析** | 技能：`data-analysis` / `loss-curve-analysis` / `figure-plot`<br>工具：`run_code`（沙箱） | 统计方法匹配、缺失异常处理、相关与因果边界标注；学术绘图 MCP |
| **文稿撰写** | 技能：`thesis-audit`（部分） | IMRaD 范式、中英学术改写、结构一致性；期刊模板 MCP、Word/Markdown 导出、文献插入 |
| **结果评审** | 技能：`thesis-audit`（核心） | 论点证据匹配、引用核验、逻辑与伦理审查、多维打分；文献溯源核对、文本查重（可选） |
| **资料归档** | 技能：`experiment-log`（部分）<br>工具：`note_write`（笔记本联动已实现） | 自动分类、知识片段提取、版本快照；本地目录读写、向量知识库、团队云盘 |

**已实现技能与七类的覆盖关系**：12 个内建技能已覆盖七类的大部分需求（详见第六章），这是"路径 A"成本低的根本原因。

## 五、模型与权限策略

### 5.1 模型档位（五档）【已实现】

| 项 | 实现 |
|---|---|
| 档位 | `MODEL_TIERS = ['auto', 'ultimate', 'performance', 'efficient', 'lite']` |
| 归属 | **SDK 平台模型池**（Work 线路） |
| 与 Chat 独立 | **是的**——Chat 走厂商模型体系（8 家 Provider + 用户可配置模型），Work 走 SDK 五档。**两套链路各自正常，互不影响**（已实测确认） |
| 校验与回落 | 档位不合法时回落至 `agentDef.model`（智能体定义中的档位） |
| UI | 无边框下拉（门户方案）；空列表时显示「正在加载智能体…」并 `Work.ready(true)` 强制重拉 |

### 5.2 与策划案的差异【待实现】

| 策划案要求 | 现状 |
|---|---|

| 未指定时继承主智能体模型 | **部分实现**：`auto` 档位承担继承语义 |
| 借助 `resolveModel` 回调按智能体标识返回对应模型 | **待实现** |
| 模型池由设置页统一维护，涵盖**云端 API 模型与本地模型**，所有智能体共享 | **部分实现**：Chat 链路已有模型配置 UI（8 家 Provider）；**本地模型未接入** |

| 工作流模板持久化模型选择（"跟随主智能体" / "固定模型"标记） | **待实现** |
| 多智能体选高性能模型时给出**成本与显存提示** | **待实现** |

### 5.3 权限模式（五档）【已实现】

| 档位 | SDK 名称 | 语义 |
|---|---|---|
| 1 | `default` | 默认确认（每个高危操作需确认） |

### 7.2 待实现：智能体间上下文隔离【待实现】

策划案第 6.4 条的隔离设计（**强边界隔离与单向上下文权限**），核心机制：

| 设计要点 | 内容 |
|---|---|
| 独立上下文 | 子智能体各自拥有独立会话与局部上下文 |
| 不可直连 | 子智能体之间不能直接通信，也不能直接读取主智能体完整上下文 |
| 按需下发 | 子智能体只收到主智能体裁剪后的当前任务与必要材料片段 |
| 全局视角 | 主智能体掌握用户消息、项目文件与全部子智能体产出 |
| **唯一网关** | 子智能体的工具/文件访问请求必须向主智能体申请，由主智能体权限校验 + 审计后代理调用 |
| 六步信息流转 | ① 用户输入 → 主智能体全局上下文；② 主智能体裁剪任务 → 目标子智能体；③ 子智能体推理，工具请求上报主智能体；④ 主智能体校验并代调 MCP，回传结果；⑤ 子智能体交回成果与局部日志；⑥ 局部上下文冻结/销毁，产出由主智能体长期保留 |
| 信息不足处理 | 子智能体只能向主智能体申请，由主智能体判断是否授权并转发片段 |

**四点收益（策划案论述）**：防无关信息污染；集中权限管控以拦截危险文件操作；按需裁剪降低 Token 开销；为审辨迭代留存完整可追溯记录。

**实施约束**：该设计依赖 SDK 的智能体间调用与上下文控制能力。**必须先做技术探针验证**（见第十章风险一），若受限则退化为"预设模板 + 局部动态"方案。

### 8.2 主智能体设计（待实现）

策划案的三类职责：

| 职责 | 内容 | 落地方式 |
|---|---|---|
| **意图识别与动态路由** | 判断任务属简单/中度/复杂，据此决定自行完成、调用少量子智能体还是启动完整墨道循环，"绝不机械地为每个任务都拉起全部子智能体" | 意图分类（可为轻量分类器或主模型 system prompt 约束）→ 路由表 |
| **通用能力池** | 内置 PPT 制作、通用报告、通用程序设计、跨文档整合摘要等科研之外的能力 | 新增通用技能包；PPT 生成可复用现有文档能力（或接 `tencent-pptx` 类能力） |
| **全局上下文管理与权限网关** | 唯一有权调度子智能体、调用全局 MCP、审核工具请求的角色 | 需 SDK 支持智能体调度 + 工具代理（技术探针前置） |

**三分支路由策略【待实现】**：

| 分支 | 判定 | 行为 |
|---|---|---|
| 简单任务 | 如解释一个概念 | 主智能体**直接回答**，不唤起任何子智能体 |
| 中度任务 | 如检索若干篇文献 | 只调用**一个或少数几个**子智能体 |
| 复杂任务 | 如设计实验、做仿真、分析数据、写稿并评审 | **串联多个子智能体**并进入审辨迭代 |
| 混合任务 | 如先仿真产出结果再生成汇报 PPT | **先科研、后通用**：仿真与数据智能体产出 → 交回主智能体 → 用自身 PPT 能力生成汇报 |

**子智能体之间不互相调度**，调度权唯一归属主智能体。

## 九、能力边界（如实声明）

**【已实现 — 建议在对外文档中完整保留】**

以下边界已在项目验证报告中明确声明，这是产品诚信的体现，**不应在宣传中隐去或模糊**：

| 边界 | 说明 | 影响 |
|---|---|---|
| **`canUseTool` 对 Bash 的拦截可被绕过** | 静态扫描命令文本，"防误操作不防有意绕过"；需要硬隔离的执行走 `run_code`（独立进程沙箱） | 安全定位需准确表述为"防误操作"，非"沙箱隔离" |
| **沙箱进程级无资源上限** | 无 Job Object，`usage.peakRssKb` 恒为 null（**字段留位但不谎报**）；只有超时 / 并发 / 输出 / 文件大小上限 | 恶意代码可耗尽 CPU/内存 |
| **声明式断网不可强制** | 代理黑洞 + socket/net 阻断 + 可选静态导入拦截；**ctypes 与原生扩展仍可联网** | 不能作为网络隔离保证 |
| **`kb_search` 是词法检索（BM25）** | 非语义检索，同义改述会漏召回；返回 score 供模型判断 | 检索召回率受限 |
| **MCP 经元工具调用** | 经 `mcp_get` / `mcp_call` 元工具间接调用（先发现后调用）；直接 `mcp__server__tool` 命名同时声明在工具清单中 | 多一跳开销 |
| **`init.skills` 是发现报告** | 含本机用户级技能（实测 54 项），**仅发现不注入上下文**；上下文与调用由 `skills` 白名单限制 | 需正确理解"发现"≠"启用" |
| **简单算术可能不调工具** | 模型对平凡问题可能直接回答（**预期行为，非缺陷**） | — |
| SDK 暂停中途抛内部错误 | SDK worker 在工具调用中途被用户暂停时抛内部 `state is not defined` | 前端已按「已中断」呈现；不影响后续会话 |
| **模型侧重复循环** | 实测模型（qwen3.8-max-0902）在写文件任务中出现 Write/Read 重复循环，触发 `maxTurns=16` 上限 | 前端如实显示【AI 回复失败】，**无静默假成功** |
| 两套模型链路 | Work 走 Qoder 平台模型（`MODEL_TIERS`）；Chat 走厂商模型 | 需在文档与 UI 中讲清，避免用户困惑 |

### 14.1 Quick Start（快速开始）

**官方地址**：`https://docs.qoder.com/en/cli/sdk/quick-start`

**环境要求**：TypeScript 需 Node.js 18+；Python 需 Python 3.10+。

**安装**：

```
npm install @qoder-ai/qoder-agent-sdk
```

**认证**：SDK 通过 PAT（个人访问令牌）认证，适用于脚本、CI 管线、第三方集成。PAT 在 `qoder.com/account/integrations` 生成——**页面关闭后无法再次查看，必须立即复制**。

```
export QODER_PERSONAL_ACCESS_TOKEN="<your-qoder-personal-access-token>"
node agent.mjs
```

配置认证：TypeScript 用 `accessTokenFromEnv()`，Python 用 `access_token_from_env()`。

```
import { accessTokenFromEnv, query } from '@qoder-ai/qoder-agent-sdk';

const stream = query({
  prompt: 'Hello',
  options: {
    auth: accessTokenFromEnv(),
  },
});
```

SDK 在启动 qodercli 之前读取该环境变量，并把解析出的访问令牌写入一次性认证载荷。通常不需要通过 `env` 选项传 PAT；若显式提供了 `options.env`，SDK 会**优先从它读取**同名变量。

> **安全提示**：不得在代码仓库中硬编码 PAT，只能通过环境变量或密钥管理服务注入。

**两种输入模式**：两个 SDK 均以 `query()` 为核心入口。当 `prompt` 为字符串时，一次调用提交一条用户消息，turn 结束后 SDK 关闭会话——适合一次性、无状态任务。若要在同一会话内发送多条消息、并根据响应决定下一步，则向 TypeScript 的 `query()` 传异步消息流，或用 Python 的 `QoderSDKClient` 维持长连接。

**完整示例**：

```
import { accessTokenFromEnv, query } from '@qoder-ai/qoder-agent-sdk';

for await (const message of query({
  prompt: 'Analyze the codebase, find functions without test coverage, and write unit tests for them.',
  options: {
    auth: accessTokenFromEnv(),
    allowedTools: ['Read', 'Write', 'Edit', 'Glob', 'Grep', 'Bash'],
    permissionMode: 'acceptEdits',  // Auto-approve file edits
  },
})) {
  if (message.type === 'assistant') {
    for (const block of message.message.content) {
      if (block.type === 'text') {
        console.log(block.text);              // AI text response
      } else if (block.type === 'tool_use') {
        console.log(`Tool: ${block.name}`);   // Tool being called
      }
    }
  } else if (message.type === 'result') {
    console.log(`Done: ${message.subtype}`);  // Final result
  }
}
```

**对墨道的落地提示**：本项目已按此模式封装 `runWorkTurn`。示例中的 `message.type` 分支处理（`assistant` → 遍历 `content` 区分 `text` / `tool_use`；`result` → 取 `subtype`）正是 SSE 桥接层需要复刻的最小集合。`permissionMode: 'acceptEdits'` 对应本项目权限档位中的相应档位——**注意 `acceptEdits` 只自动接受文件编辑，其他敏感操作仍走权限流程**，这与本项目「五档权限 + 四层覆盖链」的设计兼容。

### 14.2 Agents / Subagents（子智能体注册 — 墨道核心）

**官方地址**：`https://docs.qoder.com/en/cli/sdk/agents`

> **这是墨道最核心的一篇。** 第十三章 E 组「七类科研子智能体 + 主智能体调度」的落地，几乎全部依赖本篇的 `options.agents` 机制。

**内置子智能体**：SDK 自带三个 —— `general-purpose`（通用）、`Explore`（探索）、`Plan`（规划）。用 `q.supportedAgents()` 读取当前可用列表（含插件贡献的 Agent）。

**两种注册位置**：

| 字段 | 作用 |
|---|---|
| `options.agent` | 指定**主会话**以哪个 Agent 角色运行（把定义好的 Agent 提升为会话主体） |
| `options.agents` | 注册**自定义子智能体**供主会话委派（`Record<string, AgentDefinition>`） |

**AgentDefinition 全字段**：

| 字段 | 类型 | 必需 | 说明 |
|---|---|---|---|
| `description` | string | 是 | **用途描述；模型据此判断何时调起该子智能体**——写成「什么时候用我」而非「我是什么」 |
| `prompt` | string | 是 | 该子智能体的系统提示 |
| `tools` | string[] | 否 | 该子智能体的工具白名单 |
| `disallowedTools` | string[] | 否 | 从该子智能体工具集排除的工具 |
| `model` | string | 否 | 模型覆盖；`'inherit'` 表示继承主会话模型 |
| `maxTurns` | number | 否 | 该子智能体的最大 API 轮数（防失控） |
| `effort` | `'low' \| 'medium' \| 'high' \| 'max'` | 否 | 推理努力级别 |
| `permissionMode` | PermissionMode | 否 | 该子智能体内部工具执行的权限模式 |
| `skills` | string[] | 否 | **预加载**到该子智能体上下文的技能名称 |
| `mcpServers` | AgentMcpServerSpec[] | 否 | 该子智能体可用的 MCP 服务器规格 |
| `initialPrompt` | string | 否 | 当该子智能体**作为主会话 Agent**（即 `options.agent`）时自动提交的首个用户输入 |

**委派机制的关键约束**：

| 约束 | 说明 |
|---|---|
| 必须有 `Agent` 工具 | 主会话要想委派子智能体，其 `tools` 中**必须包含 `Agent` 工具**，否则委派能力不存在 |
| 上下文独立 | 子智能体使用独立上下文，**不接收父会话的完整历史**；父会话传给它的核心信息是 `Agent` 工具调用的任务提示 |
| 工具结果不回灌 | 子智能体的中间工具结果**不会直接进入父会话**，只有它返回的最终结果进入 |
| 不可嵌套 | **子智能体不能衍生自己的子智能体**——因此不要在任何子智能体的 `tools` 中放 `Agent` |
| `initialPrompt` 范围 | 仅对 `options.agent` 指定的**主会话 Agent** 生效，普通子智能体不适用 |

**对墨道的落地提示**：这是第十三章 D 组（上下文隔离与信息流转）与 E 组（主智能体调度）**唯一的实现基础**。三点必须写进设计：

1. **硬性约束**——子智能体的 `tools` 一律不得含 `Agent`（不可嵌套）；主会话的 `tools` 必须含 `Agent`（否则无法委派）。这是 D3「主智能体唯一网关」在 SDK 层面的天然支撑：子智能体直连其他子智能体在能力上就不成立。
2. **`description` 即路由依据**——E 组「七类子智能体」能否被正确分派，取决于每类的 `description` 是否清晰描写了「何时用我」。建议把它当作路由质量的**第一等验收指标**，而非文档装饰。
3. **`maxTurns` 必设**——E4「审辨循环」的最大迭代次数、E6「失败兜底」都需要防失控，`maxTurns` 是第一道闸。
4. `skills` 字段（预加载技能）与第十四章「十二个内建科研技能」直接衔接——可用它为每类子智能体预设专属技能集，替代全局技能白名单。详见 14.4。

### 14.3 MCP Integration（MCP 集成）

**官方地址**：`https://docs.qoder.com/en/cli/sdk/mcp`

**三种传输方式**：

| 传输 | 配置形态 | 适用场景 |
|---|---|---|
| `'sdk'` | in-process，`createSdkMcpServer()` + `tool()`（Python 用 `@tool()` + `create_sdk_mcp_server()`） | **本项目六个科研 MCP 工具走的就是这条路** |
| `'stdio'` | 本地子进程，含 `command` / `args` / `env` | 外部本地 MCP 服务器 |
| `'sse'` / `'http'` | 远端 URL + `headers` | 远端 MCP 服务器 |

**工具命名规则**（贯穿全 SDK）：

```
mcp__{serverName}__{toolName}
```

例：服务器名 `orders` + 工具名 `lookup_order` → `mcp__orders__lookup_order`。**该全名用于工具白/黑名单、权限回调、hooks 匹配器、子智能体 `tools` 配置**——凡是配置工具名的地方都用全名。

**三层工具控制的语义区别**（极易混淆，必须分清）：

| 手段 | 语义 | 后果 |
|---|---|---|
| `tools` | **可见性允许列表** | 不在列表中的工具**根本不会提供给模型**（模型看不到） |
| `allowedTools` | **预批准** | 工具可见，但匹配即跳过授权提示 |
| `disallowedTools` | **拒绝** | 匹配即拒绝；**优先级高于 allow** |

三者可组合。MCP 服务器级还有 `allowedMcpServerNames`（服务器白名单）与 `strictMcpConfig`（严格配置校验）。

**MCP 工具注解（annotations）**：`readOnlyHint`（只读）、`destructiveHint`（破坏性）、`openWorldHint`（开放世界）。这些提示可被上层用于权限决策与 UI 展示。

**错误约定**：MCP 工具**应当返回 `isError: true` 而不是抛异常**——抛异常会破坏协议链路。

**OAuth 双路径**：

| 路径 | 机制 | 适用 |
|---|---|---|
| CLI 驱动 | `mcpAuthenticate` 运行时方法 | TypeScript 侧主动发起 |
| 服务器驱动 | elicit URL + `onElicitation` 回调 | Python 侧 `on_mcp_oauth_required` 入站回调 |

Elicitation 支持 **form 模式**（表单填写）与 **url 模式**（跳转授权）。

**运行时方法与缓存破坏原则**：MCP 状态、工具列表等在会话内有缓存；**增删 MCP 服务器后必须走破坏缓存的路径（如 `reloadPlugins` 或 MCP 状态刷新），否则模型侧看到的仍是旧的工具集**。

**对墨道的落地提示**：本项目「6 个 in-process 科研 MCP + 外部 MCP + 白名单过滤 + `mcp_get`/`mcp_call` 元工具」的结构与官方一致。三点改进建议：

1. **回归 `isError` 语义**——MCP 元工具调用机制与第十三章 A3「工具错误回传完善」应对齐 `isError: true` 约定，避免异常穿透。
2. **补齐工具注解**——为 6 个科研 MCP 工具补 `readOnlyHint` / `destructiveHint`，使权限层与 UI 能区分「读文献」与「写产物」。
3. **注意工具名全名规则**——白名单与权限规则一律写全名 `mcp__<server>__<tool>`，这是 A3/A4 审计记录里应落库的键。

### 14.4 Skills（技能）

**官方地址**：`https://docs.qoder.com/en/cli/sdk/skills`

> **最容易踩坑的一篇。** 官方文档此处存在多处反直觉设计。

**第一硬约束 —— SDK 永远加 `--disable-builtin-skills`**：

> **SDK 模式下内置技能永不加载，且没有任何 opt-in 开关。**

这与 CLI 交互式使用完全不同。含义：**如果你希望某些能力通过技能暴露，就必须由你自己通过 `options.skills` 显式提供**——不能依赖内置技能兜底。

**`options.skills` 的三种形态**：

| 取值 | 行为 |
|---|---|
| `'all'` | 启用**全部已发现**的技能 |
| `string[]` | 启用指定技能（**限定名规则见下**） |
| `[]` | **禁用全部技能** |

**插件技能的限定名**：插件贡献的技能注册为 `plugin:skill` 形式，配置时必须用限定名，否则匹配不上。

**`skillOverrides` 的四个档位**：

| 值 | 含义 |
|---|---|
| `'on'` | 完整启用 |
| `'name-only'` | 仅暴露名称（不注入完整技能内容） |
| `'user-invocable-only'` | 仅允许用户显式调用（模型不可自主调用） |
| `'off'` | 关闭 |

**极易误用的两点**：

1. `initializationResult().skills` 返回的是**发现列表，不是可调用列表**。发现 ≠ 可用。UI 要展示「当前会话实际可调用的技能」时，**不能直接用这个字段**。
2. **string-list 不是安全边界**。用 `options.skills` 传字符串列表**不等于**限制了技能的权限范围——它只影响加载与否，不构成沙箱。

**Agent 级 `skills`**：`AgentDefinition.skills` 为**预加载**语义——把指定技能的内容直接注入该子智能体的上下文，而非按需加载。

**对墨道的落地提示**：本项目「12 内建科研技能 + 自定义技能 CRUD + 启用白名单端到端 + builtin 标记」的设计需要按本篇校正：

1. **`--disable-builtin-skills` 的后果要写进架构文档**——本项目的 12 个技能必须是「自备技能」，且必须在 `options.skills` 中被显式列出。**任何「依赖 SDK 内置技能」的隐含假设都不成立**。
2. **`builtin` 标记的语义需要重新定义**——官方语境下「built-in」指永远不加载的那些；本项目的「builtin 标记」实为「随产品分发的自备技能」，建议改称 `bundled` 以免混淆。
3. **UI 技能列表的数据来源要改**——前端若用 `initializationResult().skills` 渲染「可用技能」，会显示未启用项。应改为：以 `options.skills` 白名单为源，与发现列表求交集。
4. **不要把技能白名单当权限边界**——第十三章 B 组的权限设计不得依赖 `options.skills`；真正的边界是 `tools` / `allowedTools` / `disallowedTools` / `permissionMode`（见 14.3、14.10）。

### 14.5 Plugins（插件）

**官方地址**：`https://docs.qoder.com/en/cli/sdk/plugins`

**加载方式**：`options.plugins` 载入本地插件目录；SDK 将其转为 `--plugin-dir <path>` 启动参数，插件内的 commands、agents、skills、MCP 服务器**全部参与本会话的能力发现**。

```
import { query } from '@qoder-ai/qoder-agent-sdk';

const q = query({
  prompt: 'List the commands and agents contributed by the current plugins',
  options: {
    plugins: [
      { type: 'local', path: '/path/to/my-plugin' },
    ],
  },
});

const init = await q.initializationResult();
console.log(init.commands);
console.log(init.agents);
console.log(init.skills);

const plugins = await q.listPlugins();
console.log(plugins);
```

传多个插件时，`--plugin-dir` 参数**按顺序写入**。

**插件目录布局**：

```
my-plugin/
  .qoder-plugin/plugin.json    # 声明 name / version / description
  commands/                    # 斜杠命令 → 命名为 <plugin>:<cmd>
  agents/                      # 子智能体 → 命名为 <plugin>:<agent>
  skills/<name>/SKILL.md       # 技能 → 命名为 <plugin>:<skill>
  .mcp.json                    # MCP 服务器
```

**容错行为（重要）**：

| 情况 | 行为 |
|---|---|
| `--plugin-dir` 路径不存在 | **SDK 模式下静默忽略**，会话仍正常初始化 |
| frontmatter 或 `.mcp.json` 损坏 | **不阻塞 init**，只是损坏的命令不出现在 init 响应里 |

> 含义：**插件加载失败是静默的**。唯一显式诊断手段是 reload 后的 `error_count`。

**会话级覆盖**：`options.plugins` 加载的插件是**会话作用域**。若本地插件与已安装插件同名，**本次会话内本地插件优先**——适合插件开发、调试、灰度验证。**不触碰用户的全局安装状态**。

**运行时重载**：

```
const refreshed = await q.reloadPlugins();

console.log(refreshed.commands);
console.log(refreshed.agents);
console.log(refreshed.plugins);
console.log(refreshed.mcpServers);
console.log(refreshed.error_count);   // 本次重载加载失败的插件数
```

典型场景：插件开发中增删 `commands/*.md` 后刷新；安装/更新插件后不重启宿主；宿主 UI 需在重载后同步展示资源。

> **Python 差异**：`reload_plugins()` 仅在 `QoderSDKClient`（流式）模式下有意义；一次性 `query()` 流没有运行时控制通道。

**返回结构**：

- `listPlugins()` 返回 `PluginDetails[]`，每项含 `id` / `name` / `source` / `path` / `version` / `scope` / `enabled` / `canDisable`，以及 `resources` 汇总（`skills` / `agents` / `mcpServers` / `commands` / `hooks`）。
- `reloadPlugins()` 返回 `commands` / `agents` / `plugins` / `mcpServers` / `error_count`。
- **`initializationResult()` 没有稳定的插件清单字段**——宿主展示插件清单**应当用 `listPlugins()`**，不要用 init 结果的 `plugins`。

**`options.settings` 的插件相关字段**：`settings.enabledPlugins` 控制启用，`settings.pluginConfigs` 提供插件配置（如 MCP 服务器替换）。

**已知限制**：

- 某些 qodercli 版本下，本地插件的 commands/agents/MCP 出现在 init 结果中，但其 **skills 可能缺失于发现列表**（CLI 侧发现缺陷）。
- SDK 模式下不存在的 `--plugin-dir` 被静默忽略，只有 reload 后的 `error_count` 能诊断。
- 若 CLI 版本在 reload 时抛出内部 `this._plugins` 错误，需升级到修复版 qodercli。

**对墨道的落地提示**：插件是「技能/子智能体/命令」的**打包分发单元**，与 13.8 的落地路线相关。三点：

1. **静默失败是主要风险**——若未来把七类子智能体做成插件分发，必须自建「加载后校验」步骤（读 `listPlugins()` 比对期望清单 + 检查 `error_count`），不能假定加载成功。
2. **`<plugin>:<name>` 限定名会影响 Skills 白名单**——见 14.4，`options.skills` 中必须写限定名。
3. **init 结果与插件清单要分开取**——前端若做「已加载资源」面板，commands/agents/skills 取 init，插件清单取 `listPlugins()`。

### 14.6 Authentication（认证）

**官方地址**：`https://docs.qoder.com/en/cli/sdk/authentication`

**一个会话只能使用一种认证方式**：

| 方式 | 身份 | 适用场景 |
|---|---|---|
| PAT（个人访问令牌） | 某个 Qoder 用户 | 脚本、CI、需要该用户权限与数据的宿主应用 |
| Service Account（服务账号） | 组织级工作负载 | 后端服务、CI、定时任务——**不应依赖个人账号** |
| 本地 qodercli 登录态 | 当前已登录用户 | 开发者工作站（已登录 Qoder） |

**PAT 用法**：

```
export QODER_PERSONAL_ACCESS_TOKEN="<your-qoder-personal-access-token>"
```

```
import { accessTokenFromEnv, query } from '@qoder-ai/qoder-agent-sdk';

const q = query({
  prompt: 'Summarize the current workspace.',
  options: {
    auth: accessTokenFromEnv(),
  },
});
```

- 默认读 `QODER_PERSONAL_ACCESS_TOKEN`；自定义变量名用 `accessTokenFromEnv('MY_QODER_PAT')`。
- **`options.env` 与进程环境同名时，SDK 优先用 `options.env` 的值。**
- 直接传令牌：`accessToken(token)`，用于已从密钥管理取到 PAT 的可信后端。

> **SDK 不会刷新 PAT。** PAT 失效后必须获取新 PAT 并**创建新的 SDK 会话**。

**服务账号**：由 Qoder 组织管理员创建并授权、生成 key。调用方通过 `serviceAccount({ serviceAccountKey })` 传入；SDK 与 qodercli 负责获取并刷新**短期 Service Account Token（SAT）**。

链路：

```
secret manager
     |
     | Service Account Key
     v
caller reads the key
     |
     | serviceAccount({ serviceAccountKey })
     v
SDK starts qodercli and obtains a short-lived SAT
     |
     `----> authenticate session requests with the SAT
```

**宿主自行换取 SAT**（`serviceAccount({ fetchServiceAccountToken })`）：Service Account Key 留在宿主进程，qodercli 每次需要 SAT 时回调宿主，宿主调用 Token 交换 API 返回新 SAT。

```
qodercli
     |
     | request a SAT
     v
fetchServiceAccountToken callback in the SDK host
     |
     | call Token exchange with the host-managed Service Account key
     v
Qoder Token exchange
     |
     `----> return the short-lived SAT to qodercli
```

交换端点：`https://openapi.qoder.sh/api/v1/serviceToken/exchange`，`grant_type: client_credentials`，`audience: qoder`，`scope` 按需（如 `models.read chat.completions`），`ttl_seconds: 3600`。回调需返回 `{ token, expiresAt? }`；**取不到有效 SAT 时返回 `null` 或抛异常**，让当前会话显式失败。

**认证失败回调**：`onAuthExpired`（TS）/ `on_auth_expired`（Python），在远端拒绝令牌、令牌过期或 CLI 以认证错误退出时触发，**每个 SDK 会话最多触发一次**。

**Python 认证错误码**：

| 异常 | code |
|---|---|
| `AuthNotConfiguredError` | `auth_not_configured` |
| `AuthAccessTokenEnvVarError` | `auth_access_token_env_var_not_configured` |
| `AuthServiceAccountEnvVarError` | `auth_service_account_env_var_not_configured` |

**最佳实践**：生产与 CI 用密钥管理提供凭据；不把 PAT / SA key / SAT 写入日志或错误对象；自动化环境显式配置 PAT 或服务账号，不依赖本地登录态；面向用户的应用注册认证过期回调，把失败转成清晰的重新登录提示；凭据更新或轮换后**新建会话**，不复用已认证失败的会话。

**对墨道的落地提示**：本项目为桌面应用（单机），当前使用本地登录态最自然。但**若规划云端/团队能力（第十三章 F5 云同步、06 板块团队权益），Service Account 路径必须提前设计**：

1. **账号体系缺失是架构级前置**——服务账号需要组织管理员创建，这意味着团队能力落地前须先有组织概念（与 06 板块账号体系互为依赖）。
2. **不要把凭据写进日志**——本项目已有审计日志规划（A4），审计记录中**禁止包含 PAT / SAT / SA key 原文**，只记 `tokenSource` 一类元信息。
3. **认证失败要可诊断**——注册 `onAuthExpired` 并把失败转为前端可见的重新登录引导，避免「静默假成功」。

### 14.7 Model Policy / Model Selection（模型策略）

**官方地址**：`https://docs.qoder.com/en/cli/sdk/model-policy`

**两种模式，互斥**：

| 模式 | 机制 |
|---|---|
| 固定模型（默认） | 整个会话用一个模型，通过 `model` 选项指定；省略则用账号默认 |
| 动态选择 | 每次 LLM 请求前调用回调返回模型 —— 传 `resolveModel` 即切换，**固定模型设置被忽略** |

**固定模型**：

```
const q = query({
  prompt: 'Analyze this code',
  options: {
    auth: qodercliAuth(),
    model: 'performance',
  },
});
```

**动态选择**：

```
import { qodercliAuth, query, type ModelPolicyProvider } from '@qoder-ai/qoder-agent-sdk';

const resolveModel: ModelPolicyProvider = (context) => {
  return { model: 'performance' };
};

const q = query({
  prompt: 'Analyze this code',
  options: {
    auth: qodercliAuth(),
    resolveModel,
  },
});
```

**按用途路由**（官方示例）：

```
const resolveModel: ModelPolicyProvider = (context) => {
  switch (context.purpose) {
    case 'main':       return { model: 'performance' };
    case 'subagent':   return { model: 'efficient' };
    case 'compact':    return { model: 'lite' };
    default:           return { model: 'auto' };
  }
};
```

`purpose` 覆盖：主对话（`main`）、子智能体（`subagent`）、上下文压缩（`compact`）、WebFetch（`web_fetch`）、图像生成（`image_gen`）等。

**模型参数覆盖**：回调可返回 `parameters`：

```
const resolveModel: ModelPolicyProvider = (context) => {
  return {
    model: 'ultimate',
    parameters: {
      contextWindow: 200000,
      reasoningEffort: 'high',
    },
  };
};
```

这些值**必须匹配当前模型支持的配置**；上下文窗口与思考元数据通过回调入参的 `availableModels` 暴露（`ModelInfo.context_config` / `ModelInfo.thinking_config`）。

**超时**：回调有默认超时（毫秒），做远程 I/O 时应加大：`{ resolveModel, resolveModelTimeoutMs: 800 }`。

**BYOK（自带 API Key）**：回调可返回 BYOK 凭据对象，该请求将被路由到第三方提供方。**使用前需确认账号具备 BYOK 权限**。

```
const resolveModel: ModelPolicyProvider = () => ({
  model: {
    provider: 'bailian',
    model: 'qwen3.5-plus-cp',
    api_key: process.env.MY_API_KEY!,
  },
});
```

可用 provider/model 目录可在运行时获取，供前端渲染选择器与 API Key 输入框。

**运行时操作**：`getAvailableModels()` 取当前账号可用模型列表（`value` / `displayName` / `isEnabled`）；固定模型模式下可切换当前模型；可获取 BYOK provider 目录。

**错误处理（重要）**：

> **动态选择模式没有自动回退。** 回调超时、抛错、或返回空模型，都会导致本次查询**失败**。

正确做法是在回调内部兜底：

```
const resolveModel: ModelPolicyProvider = async (context) => {
  try {
    const policy = await fetchRemotePolicy(context);
    return { model: policy.model };
  } catch {
    return { model: 'auto' };   // fallback, must be non-empty
  }
};
```

**模型档位对照（官方）**：

| 值 | 层级 | 适用场景 | Credit 成本 |
|---|---|---|---|
| `auto` | 智能路由 | 大多数日常开发；推荐默认 | ~1.0x |
| `ultimate` | 终极 | 复杂系统设计、困难分析 | ~1.6x |
| `performance` | 性能 | 核心实现、架构设计、重构 | ~1.1x |
| `efficient` | 高效 | 基础代码生成、单元测试 | ~0.3x |
| `lite` | 轻量 | 快速验证、简单逻辑 | 0x |

特殊形式：`inherit`（继承主会话模型）、完整模型 ID。此外 `fallbackModel` 选项可指定主模型失败时的回退模型。

**对墨道的落地提示**：本篇与第十三章 A7、B1、B2、B3、B4 高度相关，且有**一处必须纠正的认知**：

1. **本项目的 `MODEL_TIERS` 五档是自建档位，不是官方档位**。官方档位为 `auto` / `ultimate` / `performance` / `efficient` / `lite`。A7 提出的「引入 `resolveModel` 映射层，档位到具体模型可由配置决定」正是为此——**必须在映射层内显式处理官方档位名与本项目档位名的对应关系**，否则配置会在两套命名间错位。
2. **动态选择无自动回退，必须自建兜底**——B1 的 `resolveModel` 路由实现中，回调内部**必须** try/catch 并返回非空模型（建议回退到 `'auto'`）。这一条若不落实，会出现「网络抖动导致整个对话失败」的严重体验问题。
3. **`purpose` 天然支持 B2「节点级/类型级预设」**——`main` / `subagent` / `compact` 三类用途已由 SDK 区分，B2 所需的「规划用高档、执行用中档」可在 `subagent` 分支上按 `context.availableModels` 与自定义元数据进一步细分。
4. **B3 成本提示可用 `availableModels` 的 `priceFactor`**——官方 `ModelInfo` 含价格因子与促销信息，可直接支撑发起前成本预估。
5. **B4 本地模型可走 BYOK**——`resolveModel` 返回 BYOK 凭据即可路由到自建端点，无需自研路由层。

### 14.8 Checkpoint（文件检查点与回滚）

**官方地址**：`https://docs.qoder.com/en/cli/sdk/checkpoint`

> **注意**：这是**文件检查点**，不是「对话检查点」。它记录的是 **session 内被工具修改过的本地文件状态**。

**开启**：

```
import { query } from '@qoder-ai/qoder-agent-sdk';

const q = query({
  prompt: 'Refactor src/foo.ts into a cleaner implementation',
  options: {
    cwd: '/path/to/project',
    enableFileCheckpointing: true,
    allowedTools: ['Read', 'Edit', 'Write'],
    permissionMode: 'acceptEdits',
  },
});
```

**两个能力必须配合**：检查点提供快照，`rewindFiles` 消费快照。**未开启检查点则 rewind 无快照可用。**

**回滚锚点 = 用户消息的 `uuid`**：

- **不是** `session_id`，**不是** result 消息的 ID。
- 仅在产生该检查点的会话上下文内有效；**其他会话不能直接用这个 ID 回滚**。
- TypeScript 建议**自行生成 `uuid`**（`randomUUID()`）并通过结构化输入传入，便于 UI 精确映射「回到这条消息之前」。
- Python 常用做法：从响应流的 `UserMessage.uuid` 捕获，并配合 `extra_args={"replay-user-messages": None}`（该参数**不是检查点开关**，作用是让响应流重放携带 `uuid` 的 `UserMessage`，使其可作为回滚锚点）。

```
import { randomUUID } from 'node:crypto';
import { query } from '@qoder-ai/qoder-agent-sdk';

const userMessageId = randomUUID();

async function* input() {
  yield {
    type: 'user' as const,
    uuid: userMessageId,
    parent_tool_use_id: null,
    message: {
      role: 'user' as const,
      content: [
        {
          type: 'text' as const,
          text: 'Rewrite notes.txt as a two-line summary.',
        },
      ],
    },
  };

  // If your application needs to call rewind later within the same session,
  // keep yielding subsequent user inputs here instead of closing the stream.
}

const q = query({
  prompt: input(),
  options: {
    cwd: '/path/to/project',
    enableFileCheckpointing: true,
    allowedTools: ['Read', 'Write'],
    permissionMode: 'acceptEdits',
  },
});
```

> **Python 提示**：需要后续回滚时，必须用 `QoderSDKClient` 保持同一活跃会话。

**Dry Run 预演**：执行前先预演，查看**是否可回滚、影响哪些文件、增删行数统计**。**dry run 不修改任何文件**，适合确认弹窗与审计日志。

`RewindFilesResult` 字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `canRewind` | boolean | 是否可回滚。dry run 模式下失败**不抛异常**，用该字段表示状态 |
| `error` | string? | `canRewind` 为 false 时的诊断文本，**可直接展示给用户** |
| `filesChanged` | string[]? | 受影响文件的**绝对路径**列表 |
| `insertions` | number? | 将被撤销的**新增行总数**（聚合） |
| `deletions` | number? | 将被撤销的**删除行总数**（聚合） |

```
const preview = await q.rewindFiles(userMessageId, { dryRun: true });

if (!preview.canRewind) {
  // Show the diagnostic message in the UI.
  console.error(preview.error);
  return;
}

// Overall stats across all affected files.
console.log({
  files: preview.filesChanged?.length ?? 0,
  insertions: preview.insertions ?? 0,
  deletions: preview.deletions ?? 0,
});

// Per-file listing — useful for a confirmation dialog.
for (const file of preview.filesChanged ?? []) {
  console.log(`will be reverted: ${file}`);
}
```

> **限制**：当前 `RewindFilesResult` **只返回受影响文件列表与聚合行级统计，不返回逐文件 diff**。若需逐文件差异，可在 dry run 后按 `filesChanged` 读盘与检查点比对，或在执行回滚后用 git/工作区 diff 工具。

**执行回滚**：省略 dry-run 参数即可。

```
const result = await q.rewindFiles(userMessageId);
console.log(result.filesChanged);
```

> **回滚只恢复本地文件状态，不回滚对话历史。** 模型仍保有前序轮次的上下文；UI 必须自行按 `filesChanged` 刷新编辑器、文件树或 diff 视图。

**失败语义**：

| 调用形式 | 不可回滚时的行为 |
|---|---|
| Dry run（`rewindFiles(id, { dryRun: true })`） | 返回 `{ canRewind: false, error }`，便于 UI 展示诊断 |
| 执行模式（`rewindFiles(id)`） | **TypeScript 中 Promise reject；Python 抛异常**。调用方必须捕获并暴露失败 |

**常见失败原因**：未开启文件检查点；ID 不是合法的用户消息 UUID；ID 属于其他会话；目标消息没有可回滚的文件快照。

**与 settings 的关系**：`settings` 接受 `Settings` 对象或设置文件路径字符串。

- 传**对象**时，SDK 会自动合并 `general.fileCheckpointing.enabled = true`——无需手写；已有字段保留，已有的 `fileCheckpointing` 配置其 `enabled` 会被 SDK 选项覆盖。
- 传**文件路径字符串**时，SDK **不重写文件**，需自行配置：

```
{
  "general": {
    "fileCheckpointing": {
      "enabled": true
    }
  }
}
```

纯回滚场景**只设检查点开关、不传 `settings` 即可**。

**边界（务必如实声明）**：

| 边界 | 说明 |
|---|---|
| 仅本地文件 | MCP 工具、远端服务、数据库的**外部副作用不会被撤销** |
| Bash 写入不算 | 通过 `Bash` 直接写文件**不被视为可回滚的文件快照** |
| 目录副作用可能不撤销 | 文件内容可恢复，但目录创建等目录级副作用可能不撤销 |
| 绑定会话 | 检查点 ID 绑定会话；恢复同一会话后仍可用，**不能跨会话混用** |

**最佳实践**：消息发送时**保存 user message ID**（Python 绑定 `UserMessage.uuid` 到 UI 消息记录），不要靠反查 UI 文本；回滚前先 dry run 展示影响范围再让用户确认；回滚后按 `filesChanged` 刷新 UI；失败时把 `error` 文案直接展示给用户。

**对墨道的落地提示**：本篇直接支撑第十三章 F2「checkpoint」与 F3「rewind」，且**纠正了一个常见预期**：

1. **这是文件回滚，不是对话回滚**。F2/F3 在需求描述上若写的是「会话回退到任意历史节点」，与官方能力**不一致**——官方只回滚文件，对话历史仍保留在前序上下文中。**建议把 F2/F3 的措辞改为「文件检查点与文件回滚」，对话回退另作规划（可用 `resumeSessionAt` + `resumeDropsTurn`，见 14.15、14.17）**。
2. **用户消息 UUID 必须落库**。F2/F3 落地时，前端消息记录必须保存 user message ID。这需要**前端配合**（与 02 板块联动），不是后端单方面可实现。
3. **UI 需新增 dry run 确认弹窗**。`canRewind` / `filesChanged` / `insertions` / `deletions` 四个字段足以支撑一个清晰的确认对话框，且 dry run 不改文件，风险为零。
4. **能力边界必须写清楚**——Bash 写入不可回滚、MCP 副作用不可回滚。这两条若不声明，用户会误以为「回滚 = 时光倒流」。这应作为第九节「能力边界」的新增条目。
5. **检查点与外部会话存储互斥**（见 14.16）：若未来启用 `sessionStore`，**不得同时开启文件检查点**——这是硬性约束，必须在架构决策时二选一。

1. **盘一遍内置工具清单**——本项目声明的 9 个与官方清单（至少 24 个工具名）存在差异。第十四章前的工具生态描述中「9 个」应核对是否为**本产品实际暴露**的子集；若是，应明确「另有 N 个官方工具未向模型暴露」，避免读者误以为 SDK 只有 9 个工具。

### 14.10 Permission Control（权限控制）

**官方地址**：`https://docs.qoder.com/en/cli/sdk/permissions`

> 官方文档中 `security` 路径不存在；权限相关内容位于 `permissions`。本篇即「Security 权限安全」的正式对应文档。

**四组权限手段**：① 默认策略（`permissionMode`）；② 工具范围与规则（`tools` / `allowedTools` / `disallowedTools`）；③ 运行时审批（`canUseTool`）；④ 高级设置（`additionalDirectories` / `settings` / `hooks` / MCP 工具策略）。

**总览表**：

| 要解决的问题 | 入口（TS / Python） | 说明 |
|---|---|---|
| 设会话默认权限行为 | `permissionMode` / `permission_mode` | 无显式规则匹配时如何处置工具调用 |
| 显式确认跳过权限检查 | `allowDangerouslySkipPermissions` | **仅配合** `bypassPermissions` 或 `yolo` |
| 限制本会话可见工具 | `tools` | 不在列表中的工具不提供给模型 |
| 预批准工具 | `allowedTools` | 匹配通常跳过授权提示 |
| 拒绝工具 | `disallowedTools` | 匹配即拒绝；**优先于 allow** |
| 让宿主批准工具调用 | `canUseTool` | SDK 宿主在运行时返回 allow 或 deny |
| 把审批交给外部提示工具 | `permissionPromptToolName` | 适用于已提供权限提示工具的运行时 |
| 审批后更新会话规则 | `PermissionUpdate` | 常见「允许一次」「本会话始终允许」 |
| 允许 cwd 之外的访问 | `additionalDirectories` | 扩展会话可访问目录 |
| 从 settings 提供权限规则 | `settings` | 适合会话启动时的静态权限配置 |
| 生命周期拦截或审计 | `hooks` | 高级拦截、审计、告警 |
| 在 MCP 服务器上声明工具策略 | MCP 工具策略 | 在 MCP 服务器配置里按工具声明 allow / ask / deny |

**权限模式全表**：

| 模式 | 行为 |
|---|---|
| `default` | 标准权限行为。工具调用按 `tools`、允许/拒绝规则、动态审批或运行时策略处理 |
| `acceptEdits` | 自动接受文件编辑操作；用于已确认可修改工作区的场景 |
| `bypassPermissions` | 跳过权限检查；**需同时显式确认** |
| `yolo` | `bypassPermissions` 的兼容别名；同样需显式确认 |
| `plan` | 计划模式；面向先产出执行计划，默认不产生真实改动 |
| `dontAsk` | 不交互询问。未预先授权或规则不允许的操作**被拒绝** |
| `auto` | 运行时能力自动判定允许或拒绝；安全的**工作区内**文件编辑可能被自动批准 |

> `bypassPermissions` 与 `yolo` 是**高危模式**。SDK 要求显式传 `allowDangerouslySkipPermissions: true`（Python：`allow_dangerously_skip_permissions=True`），以免普通会话意外跳过权限检查。

**会话内切换模式**：`await q.setPermissionMode('default')`。

**运行时审批 `canUseTool`**：

```
query({
  prompt: 'Create a changelog file for this release.',
  options: {
    auth: accessTokenFromEnv(),
    cwd: '/path/to/project',
    permissionMode: 'default',
    async canUseTool(toolName, input, options) {
      showApprovalDialog({
        title: options.title ?? toolName,
        description: options.description,
        input,
      });

      const approved = await waitForUserApproval(options.signal);

      if (!approved) {
        return {
          behavior: 'deny',
          message: 'Rejected by user.',
          toolUseID: options.toolUseID,
        };
      }

      return {
        behavior: 'allow',
        updatedInput: input,
        toolUseID: options.toolUseID,
      };
    },
  },
});
```

**回调签名**：

```
type CanUseTool = (
  toolName: string,
  input: Record<string, unknown>,
  options: {
    signal: AbortSignal;
    suggestions?: PermissionUpdate[];
    blockedPath?: string;
    decisionReason?: string;
    title?: string;
    displayName?: string;
    description?: string;
    toolUseID: string;
    agentID?: string;
  },
) => Promise<PermissionResult>;
```

**options 关键字段**：

| 字段 | 说明 |
|---|---|
| 工具名 | 全名，如 `Read` / `Bash` / `mcp__orders__read_order` |
| input | 工具调用的原始参数 |
| `toolUseID` | 本次工具调用 ID；TypeScript 中需在返回值里带上以精确匹配 |
| `signal` | 授权请求被取消时触发；UI 或远程审批应监听 |
| `title` / `displayName` / `description` | 运行时生成的人类可读文案，**可直接用于审批 UI** |
| `suggestions` | 运行时建议的权限更新，可用于「本会话始终允许」 |
| `blockedPath` | 路径类授权场景中被限制的路径 |
| `decisionReason` | 运行时给出的原因，用于展示或审计 |
| `agentID` | **子智能体发起工具调用时的 Agent ID** |

**返回结构**：

- 允许：`{ behavior: 'allow', updatedInput, toolUseID }`。**`updatedInput` 是工具最终收到的参数**——可原样返回，也可在批准后改写（加租户 ID、把路径重写进安全目录、剥离不允许字段）。
- 拒绝：`{ behavior: 'deny', message, toolUseID }`。**`message` 必填**，会成为模型/日志/宿主看到的拒绝原因。`interrupt: true` 表示拒绝并中断当前 Agent 流程。

> **默认拒绝**：若 SDK 收到 CLI 授权请求但**未配置权限回调，则返回错误——默认不允许任何操作**。

**权限拒绝消息**（出现在消息流中）：

```
type SDKPermissionDeniedMessage = {
  type: 'system';
  subtype: 'permission_denied';
  tool_name: string;
  tool_use_id?: string;
  message?: string;
  decision_reason?: string;
  decision_reason_type?: string;
};
```

通常出现在 `dontAsk` 模式、自动拒绝或规则拒绝时。宿主可用它更新 UI 状态或写审计日志。

**外部授权工具 `permissionPromptToolName`**：把权限请求交给运行时环境中的权限提示工具（而非在 SDK 宿主实现回调），适合已有外部审批工具、远程运行时或统一权限网关。三点注意：必须是当前运行时识别的提示工具名；**与 `canUseTool` 互斥**；若由 SDK 宿主自行决定审批，优先用 `canUseTool`。

其输入 / 输出结构：

```
type PermissionPromptToolInput = {
  tool_name: string;
  input: Record<string, unknown>;
  tool_use_id?: string;
};

type PermissionPromptToolOutput =
  | {
      behavior: 'allow';
      updatedInput: Record<string, unknown>;
      updatedPermissions?: PermissionUpdate[];
      toolUseID?: string;
    }
  | {
      behavior: 'deny';
      message: string;
      interrupt?: boolean;
      toolUseID?: string;
    };
```

**用 `settings` 提供静态权限规则**：

```
query({
  prompt: 'Inspect the project.',
  options: {
    auth: accessTokenFromEnv(),
    cwd: '/path/to/project',
    settings: {
      permissions: {
        allow: ['Read', 'Grep'],
        deny: ['Bash'],
        ask: ['Write'],
        defaultMode: 'default',
        additionalDirectories: ['/path/to/shared-lib'],
      },
    },
  },
});
```

| 字段 | 说明 |
|---|---|
| `permissions.allow` | 允许规则 |
| `permissions.deny` | 拒绝规则 |
| `permissions.ask` | 始终询问规则 |
| `permissions.defaultMode` | 默认权限模式 |
| `permissions.disableBypassPermissionsMode` | 设为 `'disable'` 可禁用绕过权限模式 |
| `permissions.additionalDirectories` | 额外可访问目录 |

> 若应用会从 settings 读取并应用默认权限模式，**建议在执行高危模式前自行做产品级确认**。`bypassPermissions` / `yolo` 只应出现在明确可信的环境。

**MCP 工具策略**：把工具级权限策略直接声明在 MCP 服务器配置里，策略随服务器配置走，而非散落在全局工具列表。

```
mcpServers: {
  repo_tools: {
    type: 'http',
    url: process.env.REPO_TOOLS_MCP_URL!,
    tools: [
      { name: 'search', permission_policy: 'always_allow' },
      { name: 'write_file', permission_policy: 'always_ask' },
      { name: 'delete_file', permission_policy: 'always_deny' },
    ],
  },
}
```

| 策略 | 行为 |
|---|---|
| `always_allow` | 匹配工具直接允许 |
| `always_ask` | 匹配工具进入授权流程 |
| `always_deny` | 匹配工具直接拒绝 |

`name` 可用 MCP 工具原始名或全名（如 `mcp__repo_tools__search`）。

**对墨道的落地提示**：本篇是第十三章 B5「权限授权弹窗通道」与 B6「权限审计」的**权威实现依据**，直接推翻了一条此前的实现假设：

1. **B5 有了官方通道，但代价是架构变化**——官方 `canUseTool` **本身就是「阻塞式交互通道」**：它在服务端暂停并等待宿主返回结果，`options.signal` 提供取消。但它的运行位置是 **SDK 宿主进程**，而本项目是「服务端跑 SDK + 前端 UI」的分离结构。因此 B5 的正确落地方式不是自建暂停协议，而是：**在 SDK 宿主侧实现 `canUseTool`，通过既有 SSE 桥接把审批请求推给前端，前端回传结果后再 resolve**。这比自研协议更可靠。
2. **`options.title` / `description` 可直接做审批 UI 文案**——无需自建文案生成。
3. **`options.agentID` 是 D 组的关键字段**——它标识「本次工具调用由哪个子智能体发起」。**这正是 D3「主智能体唯一网关」的落地点**：在 `canUseTool` 中按 `agentID` 应用不同策略，即可在权限层实现网关语义，无需另建调用层。
4. **B6 审计有了标准数据源**——除 `canUseTool` 入参外，还应订阅 `SDKPermissionDeniedMessage`（`type: 'system'`, `subtype: 'permission_denied'`），把 `decision_reason` / `decision_reason_type` 落库。**这补上了 A4 审计中「权限判定依据」这一缺口**，且是官方结构而非自造。
5. **「默认拒绝」是官方行为**——未配置回调即不允许任何操作。本项目权限设计应与此对齐，避免出现「未配置即放行」的相反假设。
6. **`settings.permissions` 可承载本项目的四层覆盖链**——`allow` / `deny` / `ask` / `defaultMode` 与「四层覆盖链」语义相容，建议评估用它替代自建配置结构，降低维护成本。
7. **MCP 工具策略可下沉权限声明**——`permission_policy` 让「写产物」类工具默认 `always_ask`、「读文献」类默认 `always_allow`，策略随 MCP 走，比全局列表更内聚。这对 C 组新增的 4 组 MCP 尤其有价值。

### 14.11 Hooks（生命周期钩子）

**官方地址**：`https://docs.qoder.com/en/cli/sdk/hooks`

**全部事件与可控行为**：

| 事件 | 触发时机 | 可控行为 |
|---|---|---|
| `PreToolUse` | 工具调用前 | **拦截 / 允许 / 修改输入** |
| `PostToolUse` | 工具成功后 | **审计 / 注入上下文 / 覆盖输出** |
| `PostToolUseFailure` | 工具失败后 | 错误处理 / 日志 |
| `UserPromptSubmit` | 用户提示发送前 | **注入上下文 / 拦截** |
| `SessionStart` | 会话开始 | 初始化 / 注入上下文 |
| `SessionEnd` | 会话结束 | 清理 / 日志 |
| `Stop` | AI 停止生成 | **阻止停止、强制继续** |
| `SubagentStart` | 子智能体开始 | 观察 / 日志 |
| `SubagentStop` | 子智能体停止 | 观察 / 日志 |
| `PreCompact` | 上下文压缩前 | 观察 / 日志 |
| `PostCompact` | 上下文压缩后 | 观察 / 日志 |
| `CwdChanged` | 工作目录变化 | 观察 / 日志 |
| `InstructionsLoaded` | 指令文件加载 | 观察 / 日志 |
| `FileChanged` | 文件创建/修改/删除 | 观察 / 日志 |
| `PermissionRequest` | 请求权限 | **自动批准 / 拒绝权限请求** |
| `PermissionDenied` | 权限请求被拒 | 观察 / 审计拒绝 |
| `WorktreeCreate`（TS） | 请求托管工作树 | **替换内置的物理创建** |
| `WorktreeRemove`（TS） | Hook 创建的工作树被移除 | **替换内置的物理删除** |

**Worktree 替换钩子（TypeScript）**：`WorktreeCreate` / `WorktreeRemove` 是**资源替换钩子，不是只读通知**。注册 `WorktreeCreate` 后，回调**必须物理创建 worktree 并返回其路径**；配对的 `WorktreeRemove` 回调必须物理删除该 Hook 创建的资源。Qoder CLI 仍负责 session cwd 切换、transcript 迁移、Resume 状态与 Exit 生命周期。

```
const hooks = {
  WorktreeCreate: [{
    hooks: [async (input) => {
      const worktreePath = await createWorktree(input.name);
      return {
        hookSpecificOutput: {
          hookEventName: 'WorktreeCreate',
          worktreePath,
        },
      };
    }],
  }],
  WorktreeRemove: [{
    hooks: [async (input) => {
      await removeWorktree(input.worktree_path);
      return {};
    }],
  }],
};
```

`createWorktree` / `removeWorktree` 需**应用自行实现**（执行 Git 或宿主特定的操作），SDK 不提供。

**配置**：在 `options.hooks` 中配置。

```
const result = query({
  prompt: 'perform task',
  options: {
    hooks: {
      PreToolUse: [{ matcher: 'Bash', hooks: [myHook] }],
      PostToolUse: [{ hooks: [auditHook] }],
      SessionEnd: [{ hooks: [logHook] }],
    },
  },
});
```

**matcher 是正则**，匹配工具名；**省略 matcher 则对所有工具生效**：

```
hooks: {
  PreToolUse: [
    { matcher: 'Bash', hooks: [bashAuditHook] },               // Bash only
    { matcher: 'File.*|Write|Edit', hooks: [fileAuditHook] },  // File operations
    { hooks: [generalLogHook] },                               // All tools (no matcher)
  ],
},
```

**回调签名**：

```
type HookCallback = (
  input: HookInput,
  toolUseID: string | undefined,
  options: { signal: AbortSignal },
) => Promise<HookJSONOutput>;
```

**输入**：所有事件共享 `hook_event_name`、`session_id`、`transcript_path`、`cwd`；各事件另有专属字段（如 `PreToolUse` 的 `tool_name` / `tool_input`）。

**输出（关键）**：

```
interface HookJSONOutput {
  continue?: boolean;
  stopReason?: string;
  decision?: string;
  reason?: string;
  hookSpecificOutput?: object;
}
```

| 字段 | 说明 |
|---|---|
| `continue: false` | 结束会话（Python 字段名 `continue_`，序列化时转为 `"continue"`） |
| `decision: "block"` + `reason` | 阻止工具执行；对 `Stop` 事件则阻止停止、强制继续 |
| `hookSpecificOutput` | 事件特定输出：修改工具输入（`updatedInput`）、覆盖工具输出（`updatedToolOutput`）、注入上下文（`additionalContext`） |

**五类典型用法**（官方示例）：

① **安全拦截（PreToolUse）** —— 拦危险 shell 命令：

```
const securityHook: HookCallback = async (input) => {
  if (input.hook_event_name !== 'PreToolUse') return {};

  if (input.tool_name === 'Bash') {
    const cmd = String((input.tool_input as any)?.command ?? '');
    if (cmd.includes('rm -rf')) {
      return {
        hookSpecificOutput: {
          hookEventName: 'PreToolUse',
          permissionDecision: 'deny',
          permissionDecisionReason: 'Destructive delete operations are not allowed',
        },
      };
    }
  }

  return {};
};
```

② **脱敏（PostToolUse）** —— 覆盖工具输出，替换 AK / Token 等敏感信息：

```
const secretRedactHook: HookCallback = async (input) => {
  if (input.hook_event_name !== 'PostToolUse') return {};

  const content = typeof input.tool_response === 'string'
    ? input.tool_response
    : JSON.stringify(input.tool_response);

  const redacted = content
    .replace(/(?:LTAI|AKID)[A-Za-z0-9]{16,}/g, '<REDACTED_AK>')
    .replace(/Bearer\s+[A-Za-z0-9\-._~+/]+=*/g, 'Bearer <REDACTED>');

  if (redacted === content) return {};

  return {
    hookSpecificOutput: {
      hookEventName: 'PostToolUse',
      updatedToolOutput: redacted,
    },
  };
};
```

③ **截断超长输出（PostToolUse）** —— 保留首尾、掐掉中段：

```
const bashSummarizeHook: HookCallback = async (input) => {
  if (input.hook_event_name !== 'PostToolUse') return {};
  if (input.tool_name !== 'Bash') return {};

  const content = String(input.tool_response ?? '');
  const THRESHOLD = 50 * 1024;
  if (content.length <= THRESHOLD) return {};

  const head = content.slice(0, 8 * 1024);
  const tail = content.slice(-4 * 1024);
  const omitted = content.length - head.length - tail.length;
  return {
    hookSpecificOutput: {
      hookEventName: 'PostToolUse',
      updatedToolOutput: `${head}\n\n[... OMITTED ${omitted} chars ...]\n\n${tail}`,
    },
  };
};
```

④ **强制继续（Stop）** —— 任务未完成时阻止 AI 停止：

```
const keepGoingHook: HookCallback = async (input) => {
  if (input.hook_event_name !== 'Stop') return {};

  if (!isTaskComplete()) {
    return {
      decision: 'block',
      reason: 'Please continue completing the remaining tasks',
    };
  }
  return {};
};
```

⑤ **自动批准权限（PermissionRequest）**：

```
const autoApproveRead: HookCallback = async (input) => {
  if (input.hook_event_name !== 'PermissionRequest') return {};

  if (input.tool_name === 'Read') {
    return {
      hookSpecificOutput: {
        hookEventName: 'PermissionRequest',
        decision: { behavior: 'allow' },
      },
    };
  }
  return {};
};
```

**注意事项（重要）**：

- Hook 回调**应快速返回**，避免阻塞 AI 执行。
- `matcher` 匹配 `tool_name` 字段；正则语法随语言（TS 用 JS 正则，Python 用 `re`）。
- `continue: false` 仅对 `PreToolUse`、`PostToolUse`、`PostToolUseFailure`、`UserPromptSubmit`、`Stop`、`SubagentStop` 生效；**观察类事件（如 `SessionEnd`、`CwdChanged`）忽略它**。
- **多个 Hook 返回冲突 `decision` 时，`"deny"` / `"block"` 优先（最严格规则胜出）。**
- **多个 Hook 设置 `updatedToolOutput` 时，最后一个非空值生效。** 若需链式变换（先脱敏再截断），**应在单个回调内顺序执行**。
- Python SDK 用下划线后缀字段名（`continue_`）避免与关键字冲突，序列化时自动转换。

**对墨道的落地提示**：Hooks 是本轮全部 16 篇中**对第十三章落地最有直接价值、且成本最低**的一篇。它能在**不改架构**的前提下补上多个此前被列为「待建」的能力：

1. **A4 工具审计 → `PreToolUse` + `PostToolUse`**。官方示例（审计日志 + 安全拦截合并）可直接复用。这比自建审计层更内聚，且拿到的是**官方标准 Hook 输入结构**而非自定义事件。
2. **A3 工具错误回传完善 → `PostToolUseFailure`**。该事件提供 `error` 与 `is_interrupt`，正是 A3 所需的结构化错误字段。
3. **A2 熔断 / A1 超时 → `PreToolUse` 拦截 + 计数**。在 Hook 内维护失败计数，达到阈值即返回 `permissionDecision: 'deny'`，即可实现熔断语义，无需改动 MCP 层。
4. **E4 审辨迭代循环 → `SubagentStop` + `Stop`**。`SubagentStop` 提供 `agent_id` / `stop_hook_active`，`Stop` 支持 `decision: 'block'` 强制继续——**这是实现「审辨不通过则带反馈重试」的官方机制**，比在应用层重建循环更稳。`SubagentStart` 的 `agent_id` / `agent_type` 还可用于 E7「嵌套时间线展示」。
5. **E7 可观测性扩展 → 全套观察类 Hook**。`SubagentStart` / `SubagentStop` / `PreCompact` / `PostCompact` / `FileChanged` / `CwdChanged` 提供的正是「多智能体并行嵌套时间线」所需的原始事件，**且比现有 SSE 7 类事件更细**。建议评估以 Hook 事件为时间线的第二数据源。
6. **权限审计（B6）→ `PermissionDenied`**。与 14.10 的 `SDKPermissionDeniedMessage` 互为补充（一个在 Hook 侧、一个在消息流侧）。
7. **上下文注入 → `UserPromptSubmit` / `SessionStart` 的 `additionalContext`**。D4「六步信息流转」中的「取用」环节可借此注入受控上下文，而非全量透传。
8. **敏感信息脱敏可直接落地**——脱敏 Hook 官方示例与本项目「审计日志不得含凭据」（见 14.6）要求完全吻合，建议优先实现。
9. **`WorktreeCreate` 为并发隔离提供路径**——若 E6 需要多个子智能体并行操作同一仓库，可用 worktree 隔离，避免写冲突。注意该 Hook **需自行实现物理创建/删除**。

### 14.12 Cost and Usage（成本与用量）

**官方地址**：`https://docs.qoder.com/en/cli/sdk/cost-usage`

**用量查询**：`q.getUsageInfo()`（TS）/ `client.get_usage_info()`（Python）返回 `UsageInfo`，含账号级与配额级信息：

| 字段 | 说明 |
|---|---|
| `userId` / `userType` | 用户标识与类型 |
| `totalUsagePercentage` | 总用量百分比 |
| `isHighestTier` | 是否最高档 |
| `expiresAt` | 到期时间 |
| `upgradeUrl` | 升级入口 |
| `userQuota` | 用户配额桶：`total` / `used` / `remaining` / `percentage` / `unit` |

**对墨道的落地提示**：本篇直接解决第十三章 A6「用量/成本统计」，且**顺带解决了一个未列出的问题**：

1. **A6 不该自建计量**——官方已提供 `getUsageInfo()`（账号/配额/会话级 credits）与 `message.usage.credits`（单次请求级），比自建 Token 计数器更准确。**建议 A6 改为「接入官方用量接口 + 落库」，而非自研统计**。
2. **发现了一个额外收益：上下文占用可视化**——`getContextUsage()` 的 `categories`（含 `skills` 占比）与 `duplicateFileReads`（重复读文件）是**现成的优化诊断数据**，可直接用于：展示「技能占用了多少上下文」（为 14.4 的 `skillOverrides` 调优提供量化依据）；发现重复读取的文件以优化上下文效率。**这两项此前不在第十三章任何分组中，建议新增为 A 组补充项。**
3. **`session.toolCalls` 的成败计数可作 A2 熔断的数据源**。
4. **与 06 板块的衔接**：`userQuota` / `addOnQuota` / `orgResourcePackage` / `isQuotaExceeded` 正是 06 板块「权益门禁」与「团队资源包」所需的官方字段。**建议 06 板块的计量底座优先复用这些结构**，而非自定义配额模型——这能显著降低前后端与官方配额语义不一致的风险。

2. **`SDKAPIRetryMessage` 可消除一类「静默假成功」风险**——本项目已强调「无静默假成功」。API 重试期间若无提示，用户会看到长时间的静止画面。建议把该消息映射为前端状态行提示。
3. **`thinking_delta` 支撑思考过程实时展示**——本项目已有「思考折叠」功能，`thinking_delta` 使其从「事后展示」升级为「实时流式」，体验提升明显。
4. **`input_json_delta` 可用于产物实时预览**——模型写文件时可实时渲染正在写入的内容，与「笔记联动」「产物 diff」功能天然契合。
5. **`message.usage` 是 A6 的最细粒度数据源**（单次请求级 credits），与 `getUsageInfo()` 的会话级聚合互补。
6. **`SDKCompactBoundaryMessage` 提示了自动压缩的存在**——长会话中上下文会被自动压缩（`autoCompact.thresholdPercentage`）。**这会丢失细节**，本项目若处理长科研对话，应评估在压缩边界处落一份摘要备份。

### 14.14 Cloud Agent（云端智能体，实验性）

**官方地址**：`https://docs.qoder.com/en/cli/sdk/cloud-agent`

> **状态：实验性 / 不稳定。API 形态可能在次版本间变化，生产路径不得依赖未发布字段。**

**何时使用**：不想管理 qodercli / 捆绑二进制 / 本地运行时；需要跨机器复用的长生命周期 agent（agent 持久化在云端）；希望会话上下文存在云端，使多个进程/主机可恢复。

**关键限制（先行声明）**：

> **本地 CLI 独有能力——MCP 服务器 / `settings` / `hooks` / `plugins` / 本地权限 / 检查点——在 Cloud 运行时全部不支持；传入这些参数会同步抛错。**

**前置条件**：

- **PAT**：Cloud 运行时**只接受 access-token 认证**（`accessToken()` / `accessTokenFromEnv()`）；本地登录态或 job token **同步失败**。
- **Cloud `environment_id`**：创建会话时必需。

```
export QODER_PERSONAL_ACCESS_TOKEN="<your-pat>"
export QODER_CLOUD_AGENT_ENVIRONMENT_ID="<your-env-id>"
```

**首次调用：创建 agent + 创建 session**：

```
import { accessTokenFromEnv, query } from '@qoder-ai/qoder-agent-sdk';

const q = query({
  prompt: 'Summarize this repository in one short paragraph.',
  options: {
    auth: accessTokenFromEnv(),
    experimentalCloudAgent: {
      agent: {
        create: {
          name: 'my-cloud-agent',
          model: 'ultimate',
          system: 'You are a concise code assistant.',
          tools: [
            {
              type: 'agent_toolset_20260401',
              enabled_tools: ['read', 'glob', 'grep'],
            },
          ],
        },
      },
      session: {
        create: {
          environment_id: process.env.QODER_CLOUD_AGENT_ENVIRONMENT_ID!,
          title: 'first-cloud-session',
        },
      },
    },
  },
});
```

运行后从最终 result 消息取 `session_id`，后续轮次可继续该会话。

**内置工具允许列表**：`tools[].enabled_tools` 支持 `bash` / `write` / `glob` / `web_fetch` / `read` / `edit` / `grep` / `web_search`。**省略 `tools` 则该 agent 没有任何工具。**

**挂载文件到会话**：文件经 Files API 上传后，用 `session.create.resources` 挂进会话容器：

```
session: {
  create: {
    environment_id,
    resources: [
      { type: 'file', file_id: 'file_abc123', path: '/workspace/data.json' },
    ],
  },
}
```

**复用已有 agent**：`agent: { id: 'agent_xxx' }`，跳过 `create`。

**多轮：恢复会话**——已有 `session_id` 后，下一次调用**只传 `session: { id }`**，**不要再传 `agent`**（会话已绑定 agent，两者同传会同步抛错）。

```
// Turn 2: continue the same Cloud session
const second = query({
  prompt: 'What is my favorite color?',
  options: {
    auth: accessTokenFromEnv(),
    experimentalCloudAgent: {
      session: { id: sessionId! },
    },
  },
});
```

**会话上下文存在云端**，脚本可在轮次之间重启或在机器间迁移——只要有 `session_id` 即可恢复。

**Python 高阶用法**：`QoderSDKClient` 提供更高层的 Cloud 会话管理——`connect()` 创建/解析 Cloud 会话，后续 `query()` 逐轮复用，无需手动跟踪 `session_id`。

> Cloud 运行时不支持 `client.set_model()`、`client.reload_plugins()`、MCP OAuth 等本地 CLI 控制方法——调用会抛 `ValueError`。

**消费 SSE 事件**：Cloud 运行时通过 SSE 推回会话事件流；SDK 把每个事件包装成 cloud agent 事件消息（TS：`cloud_agent_event`；Python：`CloudAgentEventMessage`）。

| 字段 | 说明 |
|---|---|
| `event` | Cloud 事件名（如 `user.message` / `agent.message` / `session.status_idle`） |
| `id` | SSE 流中的事件 ID，**可作重放锚点** |
| `data` | Cloud 事件载荷（含 `turn_id` 等字段） |
| `uuid`（Python） | SDK 生成的去重唯一 ID |
| `session_id` | 该事件所属的 Cloud 会话 ID |

**历史重放隔离**：复用已有会话时，SSE 会先重放历史轮次事件——SDK **按 `turn_id` 隔离**：只有**当前轮次**的 `session.status_idle` 才会产生终止 result，**历史事件不会提前结束本次查询**。

**SSE 调参**：

```
experimentalCloudAgent: {
  session: { id: sessionId },
  stream: {
    afterId: 'evt_xxx',         // start replay after this event ID
    deltaFlushIntervalMs: 250,  // delta merge / flush interval
  },
}
```

**异常关闭**：若 SSE 在当前轮次到达终止态前断开，SDK 会合成一个错误 result（`subtype != 'success'`、`is_error: true`），便于上游统一处理。

**终止态 result 内容**：

| 字段 | 说明 |
|---|---|
| `subtype` | `success` 或错误子类型 |
| `is_error` | 本轮是否异常结束 |
| `session_id` | Cloud 会话 ID（create 分支由 SDK 回填） |
| `result` | 本轮 Agent 文本回复（多个文本块拼接） |
| `usage` / `total_cost_usd` | 从本轮 `span.model_request_end.usage` 回填 |

**约束速览**：

- `agent` 与 `session` 各自把 `id` / `create` 视为互斥（TypeScript 由联合类型强制）。
- 传已有 `session.id` 时**不要**同时传 `agent`。
- `session.create` 必须显式含 `environment_id`。
- Cloud 运行时不支持本地 CLI 顶层选项：`model`、`agent`、MCP 服务器、`settings`、`hooks`、`plugins`、权限模式等会同步抛错。
- 不支持模型切换、插件重载、MCP OAuth 等运行时控制方法——只能迭代消息与关闭会话。

**错误码**：

| TS 码 / Python 异常 | 触发 |
|---|---|
| `cloud_agent_auth_requires_access_token` / `CloudAgentUnsupportedAuthError` | 非 PAT 认证（本地登录态 / job token） |
| `cloud_agent_api_error` / `CloudAgentApiError` | Cloud OpenAPI 非 2xx，或 SSE 通道失败 |

**对墨道的落地提示**：第十三章 13.8「其余补充说明」把 cloud-agent 列为「SDK 支持但未接入，需评估是否作为远端算力通道」。本篇给出了**评估所需的关键约束**：

1. **与现有能力互斥是核心决策点**——Cloud 运行时不支持 MCP / hooks / plugins / settings / 权限 / 检查点。这意味着**本项目的六个科研 MCP、十二个技能、权限链、审计 Hook 全部无法在 Cloud 运行时工作**。它不是「本地能力的远端版本」，而是**另一套能力更窄的运行时**。
2. **定位建议**：若未来接入，应定位为**「轻量远端任务的旁路通道」**（如长时仿真、批量文献处理），而**不是 Work 模式的主运行时**。主线（墨道）必须留在本地 runtime。
3. **PAT 认证是硬门槛**——需要用户在 `qoder.com/account/integrations` 生成 PAT，**与桌面应用的登录态是两套体系**。这意味着接入 Cloud 需要额外的产品级认证流程设计（与 14.6、06 板块账号体系联动）。
4. **实验性状态是排期依据**——「API 形态可能在次版本间变化」意味着**不宜在此阶段为此投入架构改造**。建议保持观望，待官方转正式后再评估。

### 14.15 Session Control（会话控制）

**官方地址**：`https://docs.qoder.com/en/cli/sdk/session-control`

**概念**：一个 session 对应 CLI 侧一份持久化的对话历史（含上下文、工具调用记录、压缩边界等），由 UUID 标识。`init` 系统消息包含当前 `session_id`，它同时是后续 resume/fork 操作的锚点。

**创建新会话**：

- **默认**：不传任何会话相关字段时，每次创建新会话。
- **指定 ID**：给 `sessionId` 传值，由调用方决定 UUID（适合宿主自管会话索引）。

**恢复会话**：

```
const q = query({
  prompt: 'Continue the previous conversation',
  options: {
    auth: accessTokenFromEnv(),
    resume: 'previous-session-id',
  },
});
```

不知道 ID 时，用 `continue: true`（Python：`continue_conversation=True`）恢复**最近修改的会话**。

> **不要把 `resume` 与 `continue` 同时传。**

**分叉会话**：从现有会话派生新会话，**保留原有上下文但获得新 session ID，原会话不受影响**。

```
const q = query({
  prompt: 'Based on the prior context, explore a different direction',
  options: {
    auth: accessTokenFromEnv(),
    resume: 'source-session-id',
    forkSession: true,
  },
});
```

可为分叉后的新会话指定 ID：

```
options: {
  auth: accessTokenFromEnv(),
  resume: 'source-session-id',
  forkSession: true,
  sessionId: 'my-new-session-id',
}
```

**字段参考**：

| 字段（TS / Python） | 类型 | 行为 |
|---|---|---|
| `sessionId` / `session_id` | string | 单独使用：以该 ID 创建新会话；配合 fork 字段：分叉后会话的 ID |
| `resume` / `resume` | string | 要恢复的会话 ID |
| `continue` / `continue_conversation` | boolean | `true` 恢复最近会话 |
| `forkSession` / `fork_session` | boolean | 与 `resume` 配合，表示分叉而非继续 |

**获取当前会话 ID**：监听 `init` 系统消息；Python 的 `ResultMessage` 也带 `session_id`，两者都可用于记账。

```
for await (const msg of q) {
  if (msg.type === 'system' && msg.subtype === 'init') {
    console.log('session_id:', msg.session_id);
  }
}
```

**用户数据目录**：用户数据目录存放会话历史、资源、日志等用户级 CLI 数据。通过 `options.env` 设 `QODER_CONFIG_DIR` 可选择该目录：

```
const q = query({
  prompt: 'Analyze this repository',
  options: {
    auth: accessTokenFromEnv(),
    env: {
      ...process.env,
      QODER_CONFIG_DIR: '/var/lib/my-agent/qoder',
    },
  },
});
```

**子智能体与会话的关系**：子智能体**不产生独立的可 resume 会话**——它们运行于父会话的上下文内，其消息通过 `parent_tool_use_id` / `parent_agent_id` 标识归属（见 14.13）。**「子 Agent 独立 session」在本 SDK 中不成立**；若需独立可恢复的执行单元，应通过 **fork** 创建平级会话。

**对墨道的落地提示**：本篇对第十三章 A5、F1、F5 有直接作用，并**纠正了一处需求表述**：

1. **「子 Agent 独立 session」这一表述需修正**——SDK 中子智能体**没有独立会话**，它是父会话内的执行分支，用 `parent_tool_use_id` 标识。如果需求的原意是「子智能体有独立上下文、能独立恢复」，正确做法是 **fork 出平级会话**（`resume + forkSession`），而非给子智能体分配 session。**建议据此修订 D1「建立智能体实例概念」的表述**。
2. **F1 fork 直接可用**——`resume + forkSession` 即为官方 fork 实现，无需自研。
3. **A5 `continue` 的边界场景可对齐官方**——官方未定义「空会话」「已结束会话」「跨项目 continue」的具体行为，属于 SDK 层未明确定义区域。**建议 A5 的实现以「官方行为 + 明确的前置校验」为准**，并在文档中如实标注这些边界为「SDK 未定义」。
4. **`QODER_CONFIG_DIR` 是会话数据落盘位置的关键开关**——本项目为桌面应用，若需控制会话数据的存放位置（如跟随用户选择的项目目录、或配合 F4 加密存储），这是官方入口。**注意：它影响的是 CLI 侧全部用户级数据，不只是本会话**，改它需谨慎评估。
5. **fork 是 F5「多设备会话同步」的备选方案**——在没有账号体系的前提下，可以通过导出/导入会话（配合 14.16）实现跨设备迁移，比自建同步协议成本低。但这**不解决「同时在线」问题**，F5 的完整落地仍依赖账号体系。

### 14.16 External Session Storage（外部会话存储）

**官方地址**：`https://docs.qoder.com/en/cli/sdk/session-storage`

**为什么需要**：默认 qodercli 把会话历史存在运行机器上。多实例、容器、无服务器部署下，下一个请求可能落到另一台机器读不到原会话。外部会话存储把每个会话**镜像**到应用自己控制的存储中。

> **镜像语义**：这是**额外的一份副本**——qodercli 仍写本地，任何宿主只要有 session ID 就能继续该会话。

**适用条件**：请求会在服务实例间迁移；本地磁盘临时或不可靠；应用必须控制访问、加密、备份或留存。**始终单机运行的应用，本地会话存储通常足够。**

**工作原理**：

```
first request
  query()
    -> qodercli writes the session locally
    -> the SDK mirrors new session entries to your store

later request, on any host
  query (with resume=session_id)
    -> the SDK loads session history from your store
    -> qodercli continues the session
```

两条性质：

- **写入是尽力而为（best-effort）**。SDK 后台镜像条目；写入失败会报告，但**永不中断正在进行的对话**。
- **条目是不透明的（opaque）**。你的存储按原样保存并返回 SDK 定义的 transcript 条目，**应用无需理解 qodercli 的本地文件格式**。

**快速开始**：`InMemorySessionStore` 只在进程内保数据，用于验证接线（查询能存能恢复），**无法演示跨主机恢复**（进程退出即丢）。要跨主机必须实现真实存储。

```
import {
  InMemorySessionStore,
  qodercliAuth,
  query,
} from '@qoder-ai/qoder-agent-sdk';

const store = new InMemorySessionStore();
const options = {
  auth: qodercliAuth(),
  cwd: '/path/to/project',
  sessionStore: store,
};

// First query: run and capture the session ID.
let sessionId: string | undefined;
for await (const message of query({
  prompt: 'Remember the number 42.',
  options,
})) {
  if (message.type === 'result') sessionId = message.session_id;
}
if (!sessionId) throw new Error('The first query did not return a session ID.');

// Later query: resume from the store and the model recalls prior context.
for await (const message of query({
  prompt: 'What number did I ask you to remember?',
  options: { ...options, resume: sessionId },
})) {
  if (message.type === 'result') console.log(message.result); // -> "42"
}
```

> **每个宿主必须使用相同的 `cwd`**，SDK 据此识别请求同属一个项目。

**在应用中使用存储**：给每个需要镜像或恢复的查询传 `sessionStore`（Python：`session_store`），然后选择会话识别方式——已知 ID 传 `resume`；要项目最近会话传 `continue: true`（**需要存储实现会话列举方法**）。

**会话管理函数**（作用于存储而非本地文件）：

| 函数 | 用途 | 外部存储要求 |
|---|---|---|
| `listSessions` | 按最近修改列出会话 | `SessionStore.listSessions` |
| `getSessionInfo` | 读取单个会话元数据 | `load` |
| `getSessionMessages` | 读取活动对话链 | `load` |
| `renameSession` / `tagSession` | 更新标题或标签 | `append` |
| `forkSession` | 从现有历史创建独立会话 | `load` 和 `append` |
| `listSubagents` | 列出子代理 ID | `SessionStore.listSubkeys` |
| `getSubagentMessages` | 读取单个子代理消息 | `load`；可用时用 `listSubkeys` |
| `deleteSession` | 删除会话及其子数据 | `SessionStore.delete`；缺失时外部不做任何事 |

**导入已有本地会话到存储**（如迁移此前未启用外部存储的机器）：`importSessionToStore(sessionId, store, { dir })`。注意**会话 ID 在前、store 在后**。`includeSubagents` 默认 `true`，`batchSize` 默认 `500`。

**实现存储接口**：

```
type SessionKey = {
  projectKey: string; // derived from cwd; identifies the project
  sessionId: string; // the session UUID
  subpath?: string; // set for subagent transcripts, e.g. "subagents/agent-<id>"
};

type SessionStoreEntry = {
  type: string;
  uuid?: string;
  timestamp?: string;
  [key: string]: unknown; // opaque transcript line — store and return unchanged
};

interface SessionStore {
  // Required
  append(key: SessionKey, entries: SessionStoreEntry[]): Promise<void>;
  load(key: SessionKey): Promise<SessionStoreEntry[] | null>;
  // Optional — implement only the features you need
  listSessions?(
    projectKey: string,
  ): Promise<Array<{ sessionId: string; mtime: number }>>;
  delete?(key: SessionKey): Promise<void>;
  listSubkeys?(key: Omit<SessionKey, 'subpath'>): Promise<string[]>;
}
```

**主会话没有 `subpath`；每个子智能体 transcript 复用相同的 projectKey 与 session ID，只是 `subpath` 不同。**

| 方法 | 启用的能力 |
|---|---|
| `append`、`load` | 镜像会话并按 ID 恢复 — **必需** |
| `listSessions` / `list_sessions` | 恢复最近会话；列出已存会话 |
| `delete` | 从存储中删除会话 |
| `listSubkeys` / `list_subkeys` | 完整恢复与检视子智能体 transcript |

**实现清单（关键纪律）**：

- **按 key 保持 append 顺序**，且 `load` 返回完整历史。**重放依赖顺序。**
- **键之间必须隔离**。绝不把一个 key 的条目返回给另一个 key。
- **`append` 必须幂等**。SDK 可能用同一批条目重试失败的写入，重试**不得重复历史**。
- **列举会话时 `mtime` 返回 Unix 毫秒时间戳**，且**只返回主会话**（无 `subpath` 者）。
- **级联删除**。删除主会话必须同时删除其子智能体 transcript。
- **`listSubkeys` / `list_subkeys` 只返回相对标识符**——**绝不返回绝对路径，绝不包含 `.` 或 `..`**。这些会成为存储键，路径穿越段会让 transcript 逃出自己的命名空间（**目录穿越风险**）。
- **同一会话的并发写入者在存储层串行化**（若多进程可写）。

**操作与调优**：

| 项 | 说明 |
|---|---|
| 失败处理 | 外部写入失败**永不中断进行中的对话**。最终重试失败后，SDK 发出镜像错误消息（TS：`system/mirror_error`；Python：`SDKMirrorErrorMessage`）。**若镜像完整性重要则需监控它**——写入失败时对话仍可能完成 |
| 读超时 | 外部读取默认等待 **60 秒**，用 `loadTimeoutMs` / `load_timeout_ms` 调整 |
| 刷写策略 | `sessionStoreFlush` / `session_store_flush` 默认 `batched`；设为 `eager` 会更早镜像，代价是更多存储请求 |

**约束（硬性）**：

- 显式 resume 的会话在存储中缺失时，SDK 仍可回退到同 ID 的本地会话。
- **存储不能与以下组合使用**：文件检查点（见 14.8）、自定义 transport、实验性 Cloud Agent 运行时（TypeScript 中还不能与 `persistSession: false` 组合）。TypeScript 中存储支持内置 Process 与 Worker transport；Python 需内置 subprocess transport。
- **存储只承载会话历史**。它不承载认证状态、应用配置、文件检查点或留存策略。

**官方提供的测试支持**：TypeScript SDK 仓库内置 `SessionStore` 一致性测试；Python 在 `qoder_agent_sdk.testing` 提供 `run_session_store_conformance`。**连接管理、权限、加密、备份、迁移与留存由应用自行负责。**

**对墨道的落地提示**：本篇对第十三章 F5「云同步」有直接价值，并**给出了一组必须在架构决策阶段确认的互斥关系**：

1. **本篇是「多设备会话同步」的官方解法，且无需账号体系即可先做**——只要有一个共享存储（自建服务、对象存储、甚至用户网盘），就能实现「同一项目在多台机器继续对话」。**这比 F5 原本设想的「账号体系驱动」路径成本低得多**，建议作为 F5 的第一阶段（用户级/自选同步盘），账号体系驱动的自动同步作为第二阶段。
2. **必须二选一：文件检查点 vs 外部会话存储**——两者**不可组合**。这是硬约束，直接影响 F2/F3（checkpoint/rewind）与 F5（云同步）的排期。**建议决策顺序**：先做 F1–F3（本地文件回滚），待用户对「跨设备继续对话」有明确需求时，再评估是否放弃文件回滚能力换取同步。**这个取舍必须写进架构决策记录**。
3. **`cwd` 必须一致是同步的前提**——每个宿主的 `cwd` 相同，SDK 才认作同一项目。这意味着**跨设备同步要求项目路径一致**，这对普通用户在 Windows/macOS 间同步是个真实障碍。**建议在产品层面提供「项目标识」抽象**，而非依赖物理路径。
4. **镜像失败是静默的（仅一条 `mirror_error` 消息）**——若同步是实现的功能，**必须监控该消息**，否则用户会遇到「明明同步了却丢历史」且无任何提示。这与本项目「无静默假成功」的原则一致，**应作为硬性要求**。
5. **子智能体 transcript 的恢复需要 `listSubkeys`**——若 E7 要做嵌套时间线的历史回看（不只是实时），存储必须实现该方法。**这应作为 E7 的隐含前置条件提前登记。**
6. **`listSubkeys` 的目录穿越风险需在实现时专项防护**——官方明确警告不得返回含 `.` / `..` 的路径。若自建存储，必须做白名单校验。这是一条**安全红线**。
7. **`importSessionToStore` 是平滑迁移路径**——已用本地存储的用户升级到同步能力时，可批量导入历史会话，无需用户重新对话。

## 十五、智能体改码执行边界（授权契约）

### 15.0 本章用途与使用方式

> **本章是给「让智能体帮你改代码」这件事用的授权契约。**

前面的章节回答的是「墨道的智能体系统怎么设计」；本章回答的是另一个问题：**当你把本项目的代码交给一个智能体去改时，它被允许做到哪里、绝对不许碰什么、碰到什么必须先回来问你。**

**使用方式（三步）**：

1. 从 **15.3** 的语法表里挑出一条指令，把 `{范围}` 替换成你的实际目录/文件。
2. 若本次任务需要越界（通常是 B 类），从 **15.6** 的授权模板里挑一条，一并附上。
3. 把指令与授权一起发给智能体，然后**只按 15.4 的验收方法检查**，不靠「看起来没问题」。

**三条使用纪律**：

| 纪律 | 说明 |
|---|---|
| **一次只授权一个模块** | 不要一次给「02 前端 + 03 后端」两个范围。跨模块任务拆成两轮，各自验收 |
| **默认最小授权** | 不确定时，从更严的档位开始（如先 `改动` 而非 `完整`）。授权是与任务绑定的，不是与项目绑定的 |
| **口头同意不算** | 任何 B 类动作必须体现为**明确的书面授权**（对话里明确写出即可），不接受「你看着办」这类模糊表述 |

### 15.1 三层边界模型

每个模块的边界都拆成三层。「不能做什么」在这三层里含义不同：

| 层 | 名称 | 含义 | 越界后能否恢复 | 判定方式 |
|---|---|---|---|---|
| **L1** | 改动范围 | 哪些文件/目录可以写 | 能（版本控制可还原） | 看 diff 的文件清单 |
| **L2** | 行为约束 | 不改动文件但违反设计契约的行为（解耦、边界、契约稳定性） | 能，但**返工成本高且会连带污染其他模块** | 看 diff 的代码内容与专项核查 |
| **L3** | 运行约束 | 影响真实数据、凭据、外部系统的动作 | **可能不可恢复**（已发请求、已删数据、已泄露密钥） | 看审计记录、看是否发生了外部副作用 |

**L3 与 L1/L2 的本质区别**：L1/L2 越界可以回滚重来，**L3 越界可能已经造成外部影响**。因此 L3 的默认档位是**全面禁止**，且需要独立白名单授权，不能靠「最小授权」类推。

> **为什么 L2 要单独存在**：最常见的失败不是「改了不该改的文件」，而是「改对了文件、但破坏了模块间的解耦契约」——例如在 UI 模块里直接写了一个 `fetch`、在对话框模块里直接调了 fs API。这类改动在单个模块内看是合理的，但会让后续重构成本陡增。L2 就是为拦这类问题而设。

### 15.2 档位定义

每个模块提供一个基准档位；**基准档是「不额外说明时」的默认授权**，不是上限。

| 档位 | L1 可写范围 | L2 约束 | L3 权限 | 适用场景 |
|---|---|---|---|---|
| **只读** | 无（禁止一切写入） | 不适用 | 全禁 | 方案设计、代码审查、问题定位 |
| **局部** | 指定的单个文件或子目录 | 完全遵守 L2 | 全禁（除 `读项目`） | 修一个 bug、改一个函数、调一处样式 |
| **改动** | 模块内 | 完全遵守 L2 | 全禁（除 `读项目`） | 模块内功能开发与重构 |
| **完整** | 模块内 + 授权清单内的跨模块改动 | 完全遵守 L2 | 需逐条授权 | 涉及模块接口变更的联调改造 |

**跨档不在档位里表达**——跨模块改动一律走 15.6 的独立授权清单，不通过提升档位来实现。这样「越界」永远是一个显式动作，不会被档位本身吞掉。

### 15.3 指令语法表

给智能体的指令一律用这个句式，模块号与 `_src/*.md` 的编号一致：

```
在 {模块范围} 内，授权档位 = {1..4 档位}，遵守 04 文档第十五章边界。
```

**可用的 6 条指令**（直接复制改范围即可）：

| 指令 | 含义 |
|---|---|
| `在 01 UI 范围内，授权档位 = 改动，遵守 04 文档第十五章边界。` | 允许在 UI 模块内自由改动 |
| `在 02 前端（桌面端原生 UI）范围内，授权档位 = 改动，遵守 04 文档第十五章边界。` | 允许在前端主进程/渲染层改动 |
| `在 03 后端（Work 模式服务端）范围内，授权档位 = 改动，遵守 04 文档第十五章边界。` | 允许在后端服务改动 |
| `在 04 Agent 范围内，授权档位 = 改动，遵守 04 文档第十五章边界。` | 允许在智能体层改动（**注意 04 是地基，L2 最严**） |
| `在 05 宣传范围内，授权档位 = 改动，遵守 04 文档第十五章边界。` | 允许在品牌资产/文案改动 |
| `在 06 订阅预付费范围内，授权档位 = 改动，遵守 04 文档第十五章边界。` | 允许在计费/权益/支付层改动 |

> **注意「04 文档」的双重含义**：在本套文档体系里，「04」既指 **04 模块（Agent 系统设计）**，也指 **本章的宿主文档本身就是 04 号文档**。建议指令里改写为更明确的说法，例如 `遵守《墨台-04-Agent系统设计实现策划案》第十五章边界`，避免歧义。

**联动类任务**（改动会牵动两个模块）必须显式声明，例如：

```
在 02 前端范围内做 X，需同步修改 03 后端接口 Y，
遵守 04 文档第十五章边界，跨模块授权见附录。
```

### 15.4 通用禁止项（L3 — 全模块适用，无例外）

以下动作**任何模块、任何档位下均禁止**，需要时必须在对话中逐条明确授权：

| # | 禁止项 | 避免什么 |
|---|---|---|
| **U1** | 删除或移动**项目根目录之外**的任何文件 | 误伤用户桌面/文档/下载目录 |
| **U2** | 执行**破坏性命令**：`rm -rf`、`del /S /Q`、`format`、`shutil.rmtree`、批量通配符删除 | 不可逆的数据丢失 |
| **U3** | 修改或导出**凭据类信息**：登录态、token、密钥、证书、本机账户配置 | 凭据泄露、账号被登出 |
| **U4** | **向外部服务发送请求**（未获授权时）：上传代码/数据、调用第三方 API、提交表单 | 数据外流、被外部系统记录 |
| **U5** | 修改 `.git/` 内部、强推（`push --force`）、`reset --hard`、`clean -fdx` | 丢失提交历史 |
| **U6** | 修改 `package.json` 的 `name`/`version`/依赖版本，或改动构建配置与产物布局 | 破坏构建链、锁文件失配 |
| **U7** | **安装新的运行时依赖**（含 `pip install` / `npm install <新包>`） | 依赖污染、体积膨胀、供应链风险 |
| **U8** | 修改 **04 模块已声明的隔离三件套**：`settingSources: []`、`strictMcpConfig: true`、`tools` 白名单 | **直接导致 SDK 继承本机全部配置，产生配置泄露（已实测）** |
| **U9** | 在**未授权时**修改权限档位、`canUseTool`、`disallowedTools` | 绕过权限链、静默提权 |
| **U10** | 修改 `app/verify/验证报告.md` 或任何验证记录、测试基线 | 掩盖失败，使验证失去意义 |
| **U11** | 修改 `_src/*.md` 之外的生成物后又不改源（或反之） | 源与产物不一致，下次重跑全部回退 |
| **U12** | 擅自把「待实现」项改写为「已实现」措辞 | 过度承诺，与能力边界声明冲突 |
| **U13** | 一次性跨 3 个及以上模块改动 | 无法归因、无法分段回滚 |
| **U14** | 在未说明失败风险的情况下执行**不可逆操作**（覆写大文件、迁移数据目录） | 静默数据损坏 |

> **U8 是本项目最特殊的一条**。它不是通用安全常识，而是本项目实测出的具体陷阱：隔离三件套缺任一项，SDK 会继承本机 qoderclicn 的全部配置。任何智能体「顺手简化一下配置」的行为都必须被拦下。

### 15.5 模块专项边界

#### 15.5.1 01 UI（界面层）

| 项 | 内容 |
|---|---|
| **基准档** | 改动 |
| **L1 范围** | UI 模块对应的样式表、图标资源、界面结构文件 |
| **L2 约束** | ① **颜色与间距不得硬编码** —— 必须走设计令牌（已知 9 处待归位项，见第十三章 A 组），不得新增第 10 处 ② 不改既有主题令牌的**语义**（改值可以，改名/改含义会连带影响全部引用点） ③ **不得直接发起网络请求** —— 数据一律经前端层提供的能力入口 ④ **不得直接读写文件系统** —— 含笔记区 |
| **L3** | 全禁 |
| **专项禁止** | 不得引入图表库、UI 框架、字体 CDN 等外部依赖（U7 的具体化）；不得改动第三方字体/图标文件的二进制内容 |
| **避免什么** | 样式失一致（同一含义两种颜色）、体积膨胀、把 UI 层变成事实上的逻辑层 |

> **L2 第 ① 项为什么是重点**：本项目已识别出 9 处硬编码颜色待回落到令牌体系。若智能体在改 UI 时又写了新的硬编码，就是**一边清理一边制造**——这是本模块最高频的返工来源。

#### 15.5.2 02 前端（桌面端原生 UI）

| 项 | 内容 |
|---|---|
| **基准档** | 改动 |
| **L1 范围** | 前端主进程与渲染层目录 |
| **L2 约束** | ① **主进程与渲染层的职责边界不得模糊** —— 渲染层不得直接调用 Node API ② **不得绕过既有 IPC 通道另建通道** ③ 新增能力前先确认**是否已有等价通道**，避免平行实现 ④ 涉及**破坏性改动的重构需先说明方案再动手**（本项目存在单文件超大脚本的技术债，局部改动容易引发连带回归，见 02 文档第十三章 A 组） |
| **L3** | 全禁 |
| **专项禁止** | 不得改动应用签名、更新配置、安装包配置；不得引入打包工具链替换（如自建 bundle 配置）除非获得专项授权 |
| **避免什么** | 双通道并存导致状态不一致、回归面不可控、打包产物不可信 |

> **L2 第 ④ 项是本模块的特有要求**。02 模块存在一个 30 万字符级的主线脚本，智能体在其中做「小改动」时极易顺手重构，而这类重构的回归面无法通过局部测试覆盖。

#### 15.5.3 03 后端（Work 模式服务端 + Chat 模式 API 调用）

| 项 | 内容 |
|---|---|
| **基准档** | 改动 |
| **L1 范围** | 服务端目录 |
| **L2 约束** | ① **不得在 Chat 模式路径引入智能体框架或子智能体机制** —— Chat 只做模型 API 调用（这是产品架构红线，不是偏好） ② **Work 模式与 Chat 模式的代码路径不得互相引用** ③ 接口**新增可以，破坏性变更需先说明并列出受影响调用点** ④ 知识库/向量等新能力不得改变既有数据文件格式，需另建 |
| **L3** | 全禁 |
| **专项禁止** | 不得在**真实用户数据**上执行迁移/删除（需专项授权）；不得修改支付回调的验签逻辑；不得改动数据库/数据文件的 schema 而不提供回退方案 |
| **避免什么** | 双模式架构被逐渐侵蚀（最容易发生）、接口契约破坏导致前端连锁失效、真实数据不可逆损失 |

> **L2 第 ① 项为什么是「架构红线」**：这是用户明确强调的产品级约束——**Chat 完全不碰智能体机制，只做 API 调用**。智能体在「优化」后端时，最容易的做法就是给 Chat 也套上 Work 那套框架，这在功能上「看起来更统一」，但直接违背产品定义。

#### 15.5.4 04 Agent（智能体系统 — 地基模块）

| 项 | 内容 |
|---|---|
| **基准档** | **局部**（本模块默认收紧，其余模块为改动） |
| **L1 范围** | 默认仅限 `app/src/server/qoder.ts`、`shared/domain.ts`、`skills-plugin/` 及其测试 |
| **L2 约束** | ① **隔离三件套零改动**（U8，本模块第一位） ② 不得改变既有「已实现」行为，除非任务本身即修正该行为 ③ 新增智能体定义不得复用现有名称 ④ 技能/工具白名单的**可用性由清单声明驱动**，不得散落硬编码 ⑤ 任何模型路由改动必须保留非法档位的回落逻辑 |
| **L3** | 全禁 |
| **专项禁止** | 不得引入新的智能体运行时/框架；不得改动 `runWorkTurn` 的对外签名（含 SSE 事件结构）而不通知前端；不得删除或跳过既有验证用例 |
| **避免什么** | **配置泄露（实测风险）**、智能体注册表被污染、SSE 契约变更导致前端静默失效、验证基线被削弱 |

> **为什么本模块基准档收紧到「局部」**：04 是其余模块的地基，改动面天然外溢。而且它包含本项目唯一一个「一改就产生安全后果」的配置（隔离三件套）。地基模块的默认授权应当更保守。

#### 15.5.5 05 宣传（品牌与物料）

| 项 | 内容 |
|---|---|
| **基准档** | 改动 |
| **L1 范围** | 品牌资产目录、文案文件 |
| **L2 约束** | ① **产品名称不得自行选定** —— 本项目存在**四套品牌名冲突**（墨台 / ChatScience / 墨砺 InkForge / 海报 CHATSCIENCE），统一决策属于 P0 未决项（见第十三章 A 组），智能体**不得在未决策时新增第五套用法** ② 物料中的能力宣称**必须能追溯到验证记录或已声明的能力边界** ③ 不得修改品牌提案原始资产文件的二进制内容 |
| **L3** | 全禁 |
| **专项禁止** | 不得对外发布/上传任何物料（U4）；不得在物料中写入具体的性能数字、未实现能力、竞品对标结论 |
| **避免什么** | 品牌名混用进一步扩散、宣传材料含未实现能力（合规风险）、原始资产被不可逆覆盖 |

> **L2 第 ① 项是本模块最实际的风险**。四套命名并存的现状下，智能体若「顺手统一」成它自己认为对的那个，会造成新的不一致。**命名必须由人决策，智能体只执行。**

#### 15.5.6 06 订阅预付费（计费与权益）

| 项 | 内容 |
|---|---|
| **基准档** | **局部**（计费语义改动风险高，默认收紧） |
| **L1 范围** | 计费/权益相关目录与配置 |
| **L2 约束** | ① **权益与余额两类数据结构必须分离**（设计结论，见第十三章 F 组），不得合并 ② 新增档位必须走声明式配置，不得硬编码在业务逻辑里 ③ 计量口径改动需列出受影响的既有数据 ④ 免费档与付费档的能力差异必须显式声明，不得用隐式开关 |
| **L3** | 全禁 |
| **专项禁止** | **不得执行任何真实支付、退款、订阅变更**（U4 的强化版，需逐笔专项授权）；不得修改金额、币种、税率常量；不得改动额度上限而不提供用户侧说明方案；**不得伪造计量数据用于测试以外用途** |
| **避免什么** | 涉及金钱的不可逆错误、用户权益被静默改变、账目不可追溯 |

> **本模块的 L3 是六个模块里最硬的**。其余模块的 L3 越界可以回滚数据，本模块的 L3 越界可能已经完成一笔真实交易。因此本模块**即便获得「完整」档，也不自动获得任何 L3 权限**。

### 15.6 越界授权模板

需要跨模块或触及 L3 时，从下面挑模板，**替换 `{}` 内的内容**，与任务指令一并发出。

**模板 A — 跨模块改动**（最常用）：

```
【跨模块授权】
源模块：{模块号与名称}
目标模块：{模块号与名称}
改动范围：{具体文件或目录清单}
接口影响：{受影响的方法/类型/事件，或写「无」}
回退方案：{如何撤销，或写「本次改动可整体丢弃」}
其他约束：仍适用第十五章通用禁止项 U1–U14，不得扩大范围。
```

**模板 B — 单个 L3 动作授权**：

```
【L3 动作授权】
动作：{具体要做什么}
对象：{精确的文件路径或数据范围}
风险说明：{执行后可能的不良后果}
可逆性：{可撤销 / 不可撤销}
执行前确认：需要 / 不需要
其他约束：仅授权本动作，不得执行清单外的其他 L3 动作。
```

**模板 C — 破坏性重构授权**（针对 02/04 模块）：

```
【重构授权】
模块：{模块号与名称}
重构内容：{要改什么，为什么必须重构}
验收标准：行为完全不变（除非任务本身要求变更行为）
不变量：{哪些外部可观测行为必须保持}
回归范围：{需要重新验证的既有功能清单}
回退方案：{如何撤销}
其他约束：仍适用第十五章边界，不得顺手扩大重构范围。
```

> **模板 C 的 `不变量` 字段是本项目最该填的一项**。经验教训是「重构时顺势改进」几乎必然发生——把「什么必须不变」写清楚，是唯一能约束住它的手段。

### 15.7 冲突裁决顺序

当两条规则给出不同答案时，按下列顺序裁决（**先出现者优先**）：

| 序 | 规则 | 说明 |
|---|---|---|
| 1 | **用户本轮指令** | 但**不得覆盖 U1–U14**——通用禁止项需要显式授权语句，不能靠「帮我改一下 X」这类泛指令推定 |
| 2 | **L3 禁止项**（15.4 + 各模块专项） | 涉及不可逆或外部影响，优先级高于功能需求 |
| 3 | **L2 设计契约** | 解耦、契约稳定性、语义一致性 |
| 4 | **L1 范围** | 只影响「改哪个文件」，是最外层 |
| 5 | **既有代码风格与惯例** | 在没有明确规则时，跟随最近邻实现 |
| 6 | **智能体自身判断** | **仅在以上均无规定时使用**，且须在回复中说明依据 |

**两个常用推论**：

- 「任务需要我改配置」**不构成** U8/U6 的豁免理由。需要时应走模板 B。
- 若任务与某条 L2 约束冲突（例如「就是要在 UI 里直接请求接口」），正确做法是**先回来确认**，而不是自行判断哪条更重要。

### 15.8 执行前自检清单

智能体在动手前必须逐条自检；**任一项答不上来就先提问，不要开工**：

| # | 自检项 |
|---|---|
| 1 | 本次的范围是**哪一个模块**？档位是哪个？ |
| 2 | 需要改动**哪些文件**？其中有没有跨模块的？ |
| 3 | 这些改动**是否触及 L3**？触及的话授权拿到了吗（模板 B）？ |
| 4 | 是否违反**任何 L2 约束**？在哪一条上需要确认？ |
| 5 | 若涉及 04 模块：**隔离三件套会被碰到吗？**（碰到即停） |
| 6 | 若涉及 02 模块：这是**局部修改还是重构**？重构需模板 C |
| 7 | 若涉及 03 模块：会不会让 **Chat 模式碰到智能体机制**？（碰到即停） |
| 8 | 若涉及 06 模块：会不会触发**真实支付/退款**？（会即停） |
| 9 | **回退方案**是什么？ |
| 10 | **验收方法**是什么？如何证明改对了？ |

**执行后必须报告**（缺一不可）：

| # | 报告项 |
|---|---|
| 1 | 实际改动的文件清单（与计划是否一致） |
| 2 | 是否发生任何越界；若发生，是主动还是误判 |
| 3 | 验证结果（跑了哪些用例、结果如何） |
| 4 | 未完成项与已知风险 |
| 5 | **是否有「已实现」措辞需要回写到策划案**（见 15.9） |

### 15.9 与能力边界声明的联动

本项目有一条不可违背的文档纪律（贯穿第九章与第十三章）：**「已实现」的判定以源码与验证报告为唯一依据，不得凭文档或意图宣称。**

因此智能体完成任务后：

| 情形 | 要求 |
|---|---|
| 任务把某个「待实现」项真正做完并验证通过 | **应**同步更新 04 文档中的状态标记与速查总表；**并说明改了哪几处** |
| 任务完成了部分 | **保持「部分实现」标记**，不得因为「主体已完成」就改标为「已实现」 |
| 任务只是重构，「行为不变」 | **不得改任何状态标记** |
| 任务新增了官方文档提及但项目未验证的能力 | **不得据此宣称已实现**（14.20 纪律三） |

> **这一步为什么必须由人工复核**：状态标记直接决定对外承诺。智能体（和写文档的人）都有一种自然的乐观偏差——把「跑通了」当成「已实现」、「已实现」当成「稳定」。**本章要求智能体主动报告「有哪些措辞需要回写」，但最终是否回写由人决定。**
